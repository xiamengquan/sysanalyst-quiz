
**问题**：正文 §4.5 与 §4 答卷块已明确「上下文图（即 0 层图）」为**同义**；易混表 A/B 两列却像两个不同概念，考生可能答「上下文图定边界、0 层图是 DFD 顶层」——逻辑重复且与教程矛盾。

### B-2 · 验证（Verification）定义中「确认」与 Validation 专名冲突

**文件**：`content/kb/第二篇-关键技术/第14章-软件实现与测试.md` §5.3（约 L116）

**现状**：
```markdown
**验证 Verification（答卷·定义）**：验证是确认软件实现是否正确地满足规格说明与设计文档的 V&V 活动（「是否正确地构建了产品」）。
```

**问题**：同章已将 Validation 译为「**确认**」；验证定义句再用「确认」作动词，考场上易写成「确认=Verification」或 V&V 对调——与本章 §5.3、§四易混表及第7章 V&V 题口径冲突。

**建议修改为**：
```markdown
**验证 Verification（答卷·定义）**：验证是检验软件实现是否正确地满足规格说明与设计文档的 V&V 活动（「是否正确地构建了产品」）。
```

**同步修改**（若易混表有类似措辞）：§四「验证 vs 确认」行保持「验证对照规格检验『是否正确构建产品』；确认对照用户需求检验『是否构建了正确产品』」——确保动词与专名不混。

**文件**：`content/kb/第二篇-关键技术/第10章-系统规划与分析.md` §5.2 四维表或 §5.2 末「补充」段

### S-2 · 数字签名定义：「加密」改为「签名运算」

**文件**：`content/kb/第一篇-基础知识/第09章-信息安全.md` §数字签名（约 L59–61）

**现状**：
```markdown
数字签名是基于非对称加密技术，用发送方私钥对消息摘要进行加密而形成的认证标识。
```

**建议修改为**：
```markdown
数字签名是基于非对称密码技术，发送方用私钥对消息摘要进行签名运算（数字签名算法）所形成的认证标识。
```

**理由**：概念边界更清晰——签名不提供保密性（2025 下真题考点）；「加密摘要」易与「加密载荷」混淆。

### S-5 · 死锁「作用」答卷句不符合准则 §1（表述优化）

**文件**：`content/kb/第一篇-基础知识/第03章-计算机系统.md` §死锁（约 L149）

**现状**：
```markdown
**死锁（答卷·作用）**：理解死锁定义与四条件是分析死锁产生原因、制定预防/避免/检测与恢复策略的基础。
```

**建议修改为**：
```markdown
**死锁四条件（答卷·作用）**：用于判断死锁是否可能发生，并据此选择破坏任一必要条件（预防）、银行家算法（避免）或检测与恢复策略。
```

**理由**：「作用」宜回答「用于……」而非「理解……是基础」；死锁本身非工具，四条件才是分析入口。
