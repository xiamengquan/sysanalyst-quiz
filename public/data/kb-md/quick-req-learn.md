## 1. L0 · 点：建立需求地图（先立坐标系）

### 要记住的三句话

1. **软件需求** = 用户对新系统在功能、行为、性能、设计约束等方面的期望。  
2. **三层**：业务（组织目标）→ 用户（角色任务）→ 系统（可实现的功能/非功能/约束）。  
3. **需求工程** = **需求开发**（获取→分析→定义→验证）+ **需求管理**（基线、变更、跟踪）。

### 业务 / 用户 / 系统需求（答卷·展开）

> 完整定义与举例见 `第11章-软件需求工程.md` §2.1。默写时用「X 是……；用于……」。

**业务需求（答卷）**  
业务需求是组织或投资方希望通过系统建设达成的高层业务目标、收益与项目范围描述。  
**用于**界定为什么做、做到什么程度、不做什么（项目视图与范围）。

**用户需求（答卷）**  
用户需求是最终用户（或角色）为完成其工作任务而对系统提出的目标、任务与交互期望。  
**用于**说明谁要用系统做什么，常以用例/场景表达。

**系统需求（答卷）**  
系统需求是为实现业务与用户需求，对系统必须具备的功能、非功能属性及设计约束所作的、可验证的规格说明。  
**用于**作为开发、测试与验收依据（含功能 + 非功能 + 设计约束）。

| 层次 | 一句话 | 勿写成 |
|------|--------|--------|
| 业务 | 组织要什么结果/范围 | 按钮字段细节 |
| 用户 | 角色要完成什么任务 | 空泛战略口号 |
| 系统 | 系统必须怎样（可测） | 「好用」「美观」等不可验证词 |

**关系**：业务定方向与范围 → 用户落实为角色任务 → 系统落实为可开发可测规格；三者应可跟踪。

### 五活动（含管理）

获取 → 分析 → 规格（定义）→ 确认验证 → **管理**（贯穿）。

### 自检口诀

「谁要什么」= 业务/用户；「系统必须怎样」= 系统需求；「改需求走哪」= 变更控制 + 跟踪矩阵。

## 2. L1 · 面：把需求分清类、说清质

### QFD 三类（别和三层搞混）

| 类型 | 用户怎么想 | 未满足 |
|------|------------|--------|
| 常规 | 明确要的 | 越少越不满 |
| 期望 | 理所当然没说清 | **特别不满** |
| 意外/兴奋 | 没指望 | 不做也不影响买；做了更惊喜 |

### FURPS+

F 功能（含安全特性）· U 可用 · R 可靠 · P 性能 · S 可支持；**+** = 实现/接口/操作/包装/授权等。

### IEEE 好需求（单条 vs 集合）

- **单条**：正确、无歧义、可检验、可跟踪  
- **集合**：完整、一致、可修改  
- 常考挖坑：**不可验证**的形容词（「美观」「好用」）不是合格系统需求

## 3. L2 · 面：怎么把需求「掏」出来并理顺

### 获取五法（案例默写四维）

访谈 / JRP(JAD) / 问卷 / 文档分析 / 观察 —— 用 **广度、深度、信息集成、用户参与** 对比，再贴题干选。

**四维答卷句（须能默写）**

| 维度 | 是…… | 用于…… |
|------|------|--------|
| 需求广度 | 覆盖面的宽窄 | 衡量能覆盖多少干系人/业务面 |
| 需求深度 | 细节与例外挖得是否充分 | 衡量能否澄清复杂任务与规则 |
| 信息集成度 | 多方信息当场对照收敛的程度 | 衡量冲突能否当场暴露并共识 |
| 用户参与度 | 用户直接投入并影响结论的程度 | 衡量是否共创、减少误解 |

完整定义与五法展开 → `第11章-软件需求工程.md` §三；默写表 → `案例必答-需求获取五法对比卡.md`。

### 分析时常考

- 冲突需求：优先级、干系人、业务规则外置  
- 原型：澄清界面/交互；风险是「原型当交付」或过早冻结  
- 范围 vs 需求：范围定边界；需求定边界内「要什么」

## 4. L3 · 面：用模型把需求「画/写」清楚

### 结构化（SA）

- **DFD**：外部实体、加工、数据流、数据存储；加工名单用**动宾**；作用含理解需求、支撑设计、存档  
- **数据字典**：元素/结构/流/存储/加工逻辑/外部实体 —— 给精确定义  
- **STD**：状态与转换；初态实心圆、终态双同心

### 面向对象（OOA）

- 用例：参与者 + 用例 + 通信；构建：识别参与者 → 合并出用例 → 细化 → 调整  
- 主事件流 vs 备选；业务用例 vs 系统用例  
- 用例宜编号，方便**需求跟踪**

## 5. L4 · 面：写成规格、验过、管住变更

| 产物/活动 | 记住一句 |
|-----------|----------|
| 用户原始需求说明书 | 与用户的协约（偏用户语言） |
| **SRS** | 开发/测试依据（外部行为与约束） |
| 需求验证 | 确认「写对了、可测、一致完整」 |
| 需求基线 | 评审批准后的约定，改须走变更 |
| 变更控制 | CCB 审批，评估影响再改 |
| 跟踪矩阵 | 需求↔设计↔代码↔测试；正向/反向 |

## 6. 从点到面：综合串题清单（自测）

合上书能答才算过关：

1. 举一例：同一项目的业务/用户/系统需求各一句  
2. 「登录要快」为何不合格？如何改成可验证需求？  
3. 干系人多、目标模糊、工期紧：五法里优先谁？为何？  
4. DFD 上「加工」命名错在哪（名词堆砌）？  
5. 需求变更后，跟踪矩阵至少要改哪两端？
