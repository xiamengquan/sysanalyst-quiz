**看完这一集你能做到**：判断网站什么时候该从整体式拆成微服务，并写出**拆分的代价与应对**。

**本讲核心结论**：**拆是为了独立，不是为了时髦**——只说「微服务好」，说不出代价，这道题只能拿一半分。网站架构题通常这样出：给一段业务背景，让你判断该用哪种架构、要不要拆、以及拆完之后会带来什么问题。答案从来不是「微服务更好」这五个字；真正拉开差距的，是你能不能说清楚**拆的代价**以及**教材给的应对办法**。

教材定位：**第十六章**讲架构原则、分类与模式，**第二十章**讲微服务系统，本讲把两章接到一起讲。

**本讲四件事**：

1. 架构设计的**八条原则**（其中「单一责任」和「有界上下文」最常考）
2. **三类架构**怎么选：整体式、微服务、无服务器
3. **三种架构模式**：B/S 架构、对等网络架构、MVC 与 MVP
4. 微服务的**七条特征**、**四条应对原则**，以及教材点名的一套**容错机制**

## 一、架构设计八条原则（01:42）

教材第十六章给出的八条原则：

| # | 原则 | 要点 |
| --- | --- | --- |
| 1 | **分离关注点** | 根据软件执行的**工作类型**把软件分离，把**核心业务行为**与**基础结构、用户界面逻辑**区分开 |
| 2 | **封装** | 应用程序的各部分通过封装相互隔离——只要维持相同的接口，就能用替代实现替换对象和包 |
| 3 | **依赖关系反转** | 依赖的方向应该指向**抽象**，而不是实现细节；遵循这条原则就能实现**依赖注入** |
| 4 | **显式依赖关系** | 方法和类要**显式要求**正常工作所需的协作对象，一般通过**构造函数**把需求说清楚 |
| 5 | **单一责任** | 对象**只应有一个责任**，并且**只能因为一个原因更改** |
| 6 | **避免自我重复** | 同一概念相关的行为**只在一处指定**，让它成为这行为的**单一权限** |
| 7 | **持久性无知** | 需要持久化的类型，它的代码**不受所选择的持久性技术影响** |
| 8 | **有界上下文** | 把大型应用分解为**独立的概念模块**；上下文之间通过**编程接口**通信，**而不是共享数据库** |

**必记的教材原话**：把**单一责任原则**应用到体系结构与逻辑终结点时，就得到了**微服务**——这句话是选型题的重要抓手。

**考试怎么考**：让你指出某段设计违反了哪条原则。打法是「**先说出原则名，再说明它要求怎么做**」，两句都要有。

## 二、三类架构：按开发与部署模式分（03:27）

| 架构 | 特点 |
| --- | --- |
| **整体式架构** | 整个软件作为**一段代码**开发，所有组件**相互依赖互联**；要改一个功能，就得**重新编写并编译整个代码** |
| **微服务架构** | 代码被开发成**松散耦合的独立服务**，通过 **API** 通信；每个微服务都有自己的**数据库**，并运行特定的业务逻辑 |
| **无服务器架构** | 底层基础结构的预配由**服务提供商**管理，用户**只为正在使用的资源付费**，扩展任务交给云提供商处理 |

教材也点出了两面：

- **整体式**：构建、测试、部署都简单；但代码量一大就难以管理和更新，**扩展不容易**，还可能有**单点故障**。
- **微服务**：可以**独立更新、修改和扩展**；但**部署多个服务本身就是一项挑战**，服务数量增加，**管理复杂性**也会明显上升。

教材原话：**应根据系统需求与开发资源条件，选择应用系统的结构类型。**

### 什么时候该拆，什么时候别拆（04:39）

| 时机 | 条件 |
| --- | --- |
| **用整体式的时机** | 要求**非常简单的用例**、应用只处理**有限的流量**——即企业确信**用户群和流量不会随时间呈指数级增长** |
| **用微服务的时机** | **复杂的用例**、预计未来流量**呈指数级增长**的应用程序；开发每个组件时还要牢记**单一责任与关注点分离** |
| **教材给的中间路线** | 有些团队**先采用整体式**体系结构，之后再**横向扩展到分布式的微服务**体系结构——答题时把这条说出来会显得更贴近工程实际 |

**判断题的答法就三步**：先给场景定性 → 再落选型 → 最后说代价，**顺序别乱**。

## 三、三种架构模式：别和分类混在一起（05:31）

注意：**分类**和**模式**是两个层次，别混答。一句话区分——**分类回答的是「怎么开发部署」，模式回答的是「内部结构长什么样」**。

### 1. 浏览器/服务器（B/S）架构

少数事务逻辑在前端实现，主要事务逻辑在**服务器端**实现，一般分为**三层**：

- **表现层**：完成用户与后台的交互，以及最终查询结果的输出；
- **逻辑层**：利用服务器完成客户端的应用逻辑功能；
- **数据层**：接受客户端请求后独立进行各种运算。

### 2. 对等网络（P2P）架构

- 两个或多个客户端**不经过服务器直接通信**；
- 具体分**完整连接拓扑**和**环形拓扑**两种形式；
- 架构中所有计算机都具有**相同的权限**，因此**即使某些节点出现故障，网络和通信仍然正常运行**。

### 3. 模型-视图-控制器（MVC）与模型-视图-表示器（MVP）

- **模型**提供数据，**视图**负责显示，**控制器/表示器**负责逻辑的处理；
- **表示器（Presenter）把模型与视图完全分离**：与具体的视图没有直接关联，而是通过**定义好的接口**交互——所以**变更视图时可以保持表示器不变**。

## 四、微服务系统的七条特征（06:49）

1. **服务自治性**：每个服务都有自己独立的**代码库、数据库和团队**；
2. **服务单一职责**：每个服务专注解决**一个特定的业务问题**；
3. **服务松耦合**：尽量减少彼此之间的依赖，可以**独立演化和变更**；
4. **分布式部署**：服务可以部署在不同的服务器或容器中，甚至**跨多个数据中心**；
5. **技术异构性**：每个服务可以使用**不同的技术栈**和工具；
6. **弹性和可伸缩性**：根据负载变化**自动调整和扩展服务的实例**；
7. **独立演化和部署**：每个服务都能**独立更新**，无需影响其他服务。

教材提醒（这就是答题的分寸）：这些特征带来了**灵活性、可扩展性、可维护性和可靠性**，但设计时要**充分考虑每一个特征的权衡与挑战**。

## 五、三类架构对照表（07:55）

最值钱的是第三列——**选型的分叉往往不在「选了什么」，而在「知道要付出什么」**。

| 架构 | 适合 | 代价 |
| --- | --- | --- |
| **整体式** | 要求非常简单的用例，只处理有限流量 | 改动要**整体重写并编译**；不易扩展；可能存在**单点故障** |
| **微服务** | 复杂用例，流量预计**指数增长** | 部署多个服务本身就是挑战；服务数量增加使**管理复杂性上升**；要保证**受事务影响的多个数据库之间的一致性** |
| **无服务器** | 多媒体处理、实时流媒体这类**按用量计费**的场景 | 底层**由云服务商掌控**，适用面受限 |

> 说明：代价一列是 UP 主按教材表述归纳的建议性说法，答题时请**落回教材原话**，别自己发挥。

### 拆的代价（三条，教材都点到了）以及应对（08:58）

**代价**：

1. **部署与运维**：用运行时实例部署多个服务本身就是一项挑战；服务数量增加，管理的复杂性也随之增加。
2. **数据一致性**：微服务需应用共享分区数据库，要保证**受事务影响的多个数据库之间的一致性**。
3. **故障传播**：服务之间的**调用链变长**，一个服务出故障，可能沿着调用链**扩散**。

**教材给的应对原则（四条）**：

| 原则 | 落地方式 |
| --- | --- |
| **隔离性** | 设计为**独立进程**，拥有自己的数据库与资源，可以用**容器**实现 |
| **自治性** | 每个服务有自己的**生命周期、状态和行为** |
| **弹性** | 自动扩展与缩放，配合**负载均衡与故障转移** |
| **可观察性** | 用**日志、指标和跟踪机制**收集与分析状态数据 |

**教材点名的一套容错机制**（写进答案是很实在的加分项）：**熔断、隔离、限流和降级、超时机制**——用来保证服务的**持续可用性**。

## 六、仿真题走一遍（10:08）

> 说明：按教材考点自造，非真题，用于演示答题路径。

**场景**：某电商平台最初采用整体式架构，随着功能增多，改一处就要整体编译发布；团队分布在两个城市；业务方预计未来流量会快速增长。管理层提出要拆成微服务。

1. **第一问：是否应该拆成微服务？说明判断依据。**——走法是先给场景定性：功能是否复杂？流量是否指数增长？团队是否分布式协作？
2. **第二问：拆分后会带来哪些新问题？**——从**部署运维、数据一致性、故障传播**这三条里找，别只说好处。
3. **第三问：架构上应遵循哪些原则来应对？**——答**隔离性、自治性、弹性、可观察性**，再补上**容错机制**。

## 七、答题模板：选型题三句（11:07）

1. **第一句：定性场景**——「该平台功能复杂，且流量预计快速（指数）增长」。先把场景说清楚，选型才有依据。
2. **第二句：给出选型**——「由整体式架构演进为微服务架构」。要给出**明确结论**，不要模棱两可。
3. **第三句：说清代价**——「部署与运维复杂性上升、多库一致性、故障传播，用**隔离性、自治性、弹性、可观察性**来应对」。**代价与应对一起说，这是得分的关键。**

三句就是一个完整答案，记得**分条编号写**，别写成一大段。

**变体**：如果题目还点到具体技术，就再补一句——「熔断、隔离、限流和降级、超时机制」。

## 八、五个常见失分（11:56）

1. **只写微服务的好处，不写代价**——不写代价等于只答了一半。
2. **不提数据一致性**——教材明确说了要保证受**事务**影响的多个数据库之间的一致性，这是拆分绕不开的问题。
3. **把架构当口号，不落到场景定性上**——选型就没有依据。
4. **混淆分类与模式**——一类回答「怎么开发部署」，一类回答「内部结构」，别混在一起答。
5. **只写原则名称**——写了「隔离性」，还要写它**怎么落地**（比如独立进程与容器）。
