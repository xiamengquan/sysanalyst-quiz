# 第一部分 方法论总纲（第 1 讲）

## 1.1 案例是题型，不是章节

- 教材里没有哪一章叫「案例分析」——案例拿的是**整本书的知识**，考的是**解决一个具体问题的能力**。
- 为什么三科里案例最容易翻车？综合知识不会还能蒙，论文可以提前准备，只有案例是**当场给你一个从没见过的系统**，要你在几十分钟里给出判断。

## 1.2 240 分钟怎么切成两段

- 上午是**连考**：综合知识＋案例共 **240 分钟**，中间不休息。综合知识交卷后，剩余时间**自动记入案例**。
- 案例实际可用 **90～120 分钟**：
  - 综合知识用满 150 分钟 → 案例只剩 90 分钟（三道题平均每题 30 分钟，含审题与检查）；
  - 综合知识 120 分钟交卷 → 案例有 120 分钟（多出的 30 分钟补给必答题和检查）。
- 注意：**三科独立计分，任何一科不到 45 分都不算过**——综合知识不能乱蒙。
- 建议：**按最紧的 90 分钟口径去练**，考场上只会更宽松；反过来练，一进考场就会慌。

## 1.3 五道做三道：一必答、四选二

- **第一题必答**（不做就没分），建议第一个写、写完整写满；**后四题选二**。
- 挑题依据是**设问**，不是背景——背景再熟悉，设问答不出来就不要选。
- 剩下两道**果断放弃，别回头看**：多做不加分，省下的时间更值钱。
- **选答题一旦开始写，中途换题最亏**（前面全作废）——所以开考前 5 分钟扫题定三道，一定不能省。

## 1.4 案例题只问三种问题

| 题型 | 内容 | 判断信号（设问动词） |
| --- | --- | --- |
| **找错题** | 图不用你画，挑出问题 | 指出、改正、补充 |
| **概念题** | 解释术语＋项目实例佐证 | 说明、简述、什么是×× |
| **论述题** | 选一种做法，说清理由与代价 | 设计、选择、说明理由 |

## 1.5 按点给分：一个得分点＝一个结论＋一句理由

> 案例是**按点给分**的，不是按字数给分。

- **结论**答「是什么」，一句话放每条第一句；**理由**答「凭什么」，结论才立得住。
- 例：题目问「这设计有什么问题」——「性能会有问题」（结论）＋「因为所有请求都打到同一个数据库实例，没有做读写分离」（理由），两句话才是一个完整得分点。
- **分条写＝把得分点送到阅卷人眼前**；一大段散文，阅卷人要自己找点。

## 1.6 四步把答案写出来

1. **定位考点**：读完设问，判断考哪一章、哪个知识点；
2. **列点**：能答的得分点先写草稿，别急着组织语言；
3. **每个点写成「结论＋理由」**：两句话写完一个点；
4. **补术语**：口语换成**教材的说法**——意是对的、词不是教材的词，看着就不像学过。

**对照示例（找错题）**：

- ❌「这数据流图画错了，应该改过来」——只有结论，算答一半；
- ✅「外部实体之间不应存在直接数据流，必须经过加工。去掉这条数据流，改为经加工中转」——结论、规则名、改法，三个得分点全在。

找错题固定顺序：**先说位置 → 再说规则 → 最后给改法**。

## 1.7 九十分钟怎么切（备考建议，非考试规定）

| 时间块 | 时长 | 要点 |
| --- | --- | --- |
| 审题与选题 | 5 分钟 | 五道全扫，**看设问不看背景**，定下做哪三道 |
| 必答题 | 25 分钟 | 按四步法写完整 |
| 选答第一道 | 25 分钟 | 挑最有把握的先写 |
| 选答第二道 | 25 分钟 | 写完要点就走，宁可少写也别空题 |
| 检查 | 10 分钟 | 题号、术语、空题 |

案例若有 120 分钟，多出的 30 分钟补给**必答题和检查**。

## 1.8 三种问法，三种答法

| 题型 | 答法 |
| --- | --- |
| **找错题** | ①错在哪（指出位置）②违反什么（规则名称）③怎么改（改正办法） |
| **概念题** | ①先定义（教材说法）②再举例（项目实例）③不展开——定义准确就够 |
| **论述题** | ①给方案 ②给理由 ③给代价（牺牲了什么、怎么补） |

每个设问按顺序写三句，就是一条完整的得分点。

## 1.9 机考这件事

- **全程机考**：答案在电脑上敲，**打字速度就是答题速度的一部分**。
- 图不用你画——指出问题、补充缺失、说明依据即可。
- **考前把官方模拟系统完整走一遍**：界面、切题、输入法提前摸熟。
- 机考改字方便但容易漏题：最后十分钟专查**题号和空题**。一切以官方模拟系统和当期考试说明为准。

## 1.10 五个失分点与六条底线

**五个失分点**：①答非所问（设问没读完就写）②只给结论不给依据 ③大段不分条 ④口语代替术语 ⑤整题空着（写一个点就有一分）。最容易犯的是①和⑤；②和④是同一个毛病——知道但没写到位。

**六条底线（守住 45 分）**：

1. 必答题完整写完；
2. 每个设问至少写一个点，绝不空题；
3. 分条写：一句结论＋一句理由；
4. 用教材的说法，不自造词；
5. 选答题看设问，不看背景熟不熟；
6. 最后十分钟留给检查：题号、术语、空题。

> **45 分不是靠发挥拿的，是靠不犯错守住的。** 先守底线拿 45，再靠专题把分推上 60。

# 第二部分 四大专题

# 专题一 结构化分析（第 2 讲｜教材第十一章）

> 核心定性：**图是题目给的，分在错误里**——考的不是画图，是挑错。图不用你画，你要有一套检查清单。

## 2.1 四种基本符号，多一个就是错

| 符号 | 含义 | 表示 | 挑错点 |
| --- | --- | --- | --- |
| **数据流** | 有名字、有流向的数据 | 箭头 | 必须连到**加工**上 |
| **加工** | 对数据流的变换 | 圆圈 | 至少**一进一出**，用**动词短语**命名 |
| **数据存储** | 可访问的存储信息 | 直线段 | 整套图里既要**读**也要**写** |
| **外部实体** | 系统之外的人、设备或其他系统 | 方框 | 实体之间**不能有直接数据流** |

考试怎么考：第一眼先**数符号**——四种之外出现的东西，基本就是得分点。

## 2.2 检查修改六原则（最值钱的一页）

1. **符号限定**：符号只限四种，且每个元素**必须有名字**；
2. **数据守恒**：每个加工至少一进一出，**输出不与输入同名**；
3. **按层编号**：编号体现**父图/子图对应关系**；
4. **父子图平衡**：子图与上层加工对应，**输入输出数据流必须一致**；
5. **读写俱全**：每个数据存储必须既有读又有写；
6. **不加控制流**：可加**物质流**帮助理解，**不可加控制流**。

拿到一张图，按这六条从第一条问到第六条。

## 2.3 三层图与编号规则

| 层 | 内容 | 编号 |
| --- | --- | --- |
| 顶层图 | 系统就是一个加工，只画外部实体与进出数据流（勾出**系统范围**） | — |
| 0 层图 | 对顶层加工第一次分解，引入新加工和数据存储 | 1、2、3… |
| 1 层图 | 对 0 层加工再分解，分到说清楚为止 | 1.1、1.2、2.1… |

编号本身就是考点——**编号乱跳＝父/子图对应关系错了**。

## 2.4 平衡与数据守恒

- **不平衡的例子**：父图只有「订单」输入，子图却多出「库存查询」——凭空多出的数据流就是埋的错。
- **要小心的情况**：父图一条「订单」，子图拆成「订单头＋订单明细」——**数据项的全体正好是父图那一条，仍算平衡**，别误判。
- **数据守恒**：只有输入没输出＝**黑洞**；只有输出没输入＝**奇迹**；输出与输入同名＝加工什么都没做；**所有输出必须能从输入直接获得或由加工产生**——凭空冒出的数据就是错误点。
- **挑错顺序**：先扫外部实体直连 → 再扫黑洞与奇迹 → 最后核对父子图平衡。

## 2.5 数据字典六类条目

数据字典是对图上**所有命名元素**给出确切解释：

| 条目 | 含义/属性 |
| --- | --- |
| **数据元素**（数据项） | 数据最小组成单位（课程号、课程名）；属性：名称、编号、别名、类型、长度、取值范围、取值含义 |
| **数据结构** | 描述元素间关系；特殊情况：**任选项、必选项、重复项** |
| **数据流** | 来源、去处、组成、流通量 |
| **数据存储** | 存储结构、有关数据流、查询要求——**只列结构，不列内部构成** |
| **加工逻辑** | 编号、名称、功能、输入/输出；借助**判定树、判定表、结构化语言** |
| **外部实体** | 来源和去向＋**实体数量** |

附加考点：数据字典由**数据管理员专人维护**，修改必须经过它。

## 2.6 四类典型错误与仿真题

| # | 错误 | 改法 |
| --- | --- | --- |
| 1 | 实体直连 | 中间必须**经过加工** |
| 2 | 黑洞（或有出无进的「奇迹」） | 补上缺失的一侧 |
| 3 | 只写不读 | 读写都有 |
| 4 | 夹带控制流 | 控制流不能出现在数据流图上 |

**仿真题（在线教育平台）**：学员↔辅导老师直连（错一）；「生成报表」只有输入没有输出（错二，数据守恒）；「选课记录」只写不读（错三）。三处正好对应三类典型错误。

**三句模板**：①错在哪（指出位置）②违反什么（规则名称）③怎么改（可执行改法）。一处错三句，分条编号写。

**五个失分点**：只说错不说规则、漏父子图平衡、控制流当数据流、字典条目写不全（来源/去处/取值范围最易漏）、开始重画新图。

# 专题二 面向对象建模（第 3 讲｜教材第十一章）

> 核心结论：**图不难画，难在关系的判定**——会判定的人先问：这是一定会执行的，还是看情况才发生的。

## 3.1 用例图只有三种元素

**参与者（Actor）**——存在于系统外部、与系统交互的**任何事物**，三类来源：

1. **其他系统**（如办公系统同步数据）；
2. **硬件设备**（读写器、传感器）；
3. **时钟**（定时触发）——**最易漏**：题干出现「每天凌晨自动…」「每月一号定时…」，参与者必写「时钟」。

**用例（Use Case）**——系统对外提供的一项服务。识别三个坑：①命名用**动词＋名词**（「开通课程」，不能只写「课程」）；②**不能把步骤当用例**（「验证学员信息」不能单独对外提供）；③只识别**系统用例**，业务用例不管。

**通信关联**——参与者与用例（或用例与用例）之间的关系，箭头指向被动接受方；**信息流不由通信关联表示**，它默认存在且双向。

## 3.2 用例的三种关系

| 关系 | 触发条件 | 判定关键词 |
| --- | --- | --- |
| **包含** | 从两个以上用例提取**公共行为**，抽出**抽象用例** | **一定会执行**，少了它基本用例不完整 |
| **扩展** | 一个用例混合了**多种不同场景**，拆成基本用例＋扩展用例 | **看情况才执行** |
| **泛化** | 多个用例有类似结构行为，抽象成**父用例**，子用例**继承**全部结构与行为 | 父子同类 |

**判定口诀**：一定会走的是**包含**；看情况才走的是**扩展**；父子同类的是**泛化**。

教材提醒：三种关系都会**增加用例个数**、增加复杂度——**用例模型完成之后才调整**，建模之初不要急着抽象。

## 3.3 用例建模的主要工作是「写」，不是「画」

> 教材原话：**用例建模的主要工作是书写用例规约，而不是画图。**

用例描述的组成（补描述题照此逐项检查）：

| 组成 | 要点 |
| --- | --- |
| 用例名称 | 与用例图相符，写上编号 |
| 简要说明 | 为参与者传递了什么价值 |
| 事件流（主体） | **主事件流**＝典型成功路径（不含条件分支）；**备选事件流**＝失败情况/分支路径，**单独抽出来写** |
| 非功能需求 | 单列小节，**可度量、可验证** |
| 前置条件 | 执行前必须存在的系统状态 |
| 后置条件 | 执行完系统可能处于的一组状态 |
| 扩展点 | 写出用例名与使用条件 |
| 优先级 | 用户对该用例的期望值 |

## 3.4 分析模型四步

1. **定义概念类**：**名词短语法**——从需求描述挑名词/名词短语作候选；
2. **确定类之间的关系**：六种关系判定清楚，用类图记录，形成**领域模型**；
3. **为类添加职责**：只找**主要职责**，不必求全（答多不加分，答偏会扣分）；
4. **建立交互图**：最常用**顺序图**（元素：对象、参与者、生命线、激活、消息——**消息是顺序图的灵魂**）；行为复杂、状态转换多时加**状态图**。

前三步统称**类-责任-协作者（CRC）建模**。

## 3.5 类的六种关系

| 关系 | 要点 |
| --- | --- |
| **关联** | 不同类的**对象实例**之间的结构关系（不是类与类之间）；用名称、角色、**多重性**、导向性描述 |
| **依赖** | 乙的变化可能引起甲的变化 → 甲依赖乙；产生于：发消息、做数据成员、做操作参数 |
| **泛化** | 一般与特殊（父类/子类）；**继承是泛化的反关系** |
| **实现** | 把**说明和实现**联系起来（接口是行为的说明，类含实现） |
| **聚合**（共享聚集） | 整体-部分；**部分可属多个整体，生命周期可以不同**（汽车—车轮：车坏轮还能用） |
| **组合**（组合聚集） | 整体-部分；**部分只属一个整体，生命周期相同**（公司—部门：公司倒闭部门无所谓） |

**聚合 vs 组合一句判定**：部分的生命周期**跟不跟着整体走？——跟是组合，不跟是聚合。**

**多重性细节**：一个类的多少个对象可与另一个类的**一个对象**相关联；**`*` 等价于 0..多**。

## 3.6 高频错误、仿真题与模板

**四类高频错误**：①把步骤当用例 ②包含与扩展划反（箭头方向跟着错）③只写主事件流漏备选流 ④聚合组合不提生命周期。四条都能在教材第十一章找到原话——**直接引用教材说法最稳**。

**仿真题（在线培训系统）**：参与者四类（学员、客服人员＝人；办公自动化系统＝其他系统；时钟＝每天凌晨定时触发）；「学习课程」「参加课程测试」都要验证权限——公共行为且必做 → **包含**，「验证权限」是抽象用例。

**判定题三句模板**：

1. **给结论**：「应使用包含关系，验证权限为抽象用例」——先说关系名，不要上来就解释；
2. **给依据**：「这是从两个以上用例抽出的公共行为，而且一定会执行」——落在教材说法上；
3. **给画法**：「箭头由基本用例指向抽象用例，标注 include」——方向说清楚，不留歧义。

三句一个得分点，**分条编号写**；列举题（补参与者/用例）不用第三句；题目出现「**说明理由**」四字，必须补第二句——只给结论通常拿一半分。

**五个失分**：漏外部系统和时钟、只写关系名不写方向、漏备选事件流和前后置条件、聚合组合不提生命周期、不落到题目场景（每条带上题干具体名字）。

# 专题三 架构风格选型（第 4 讲｜教材第十二章）

> 核心结论：**选风格，就是选构件和连接件**——只报风格名一分拿不到。

## 4.1 风格的定义与价值

> **体系结构风格**＝描述某一特定应用领域中系统组织方式的**惯用模式**；定义一个**系统家族**：**一个词汇表（构件＋连接件类型）＋ 一组约束（如何组合）**。

- 风格的价值：**促进设计的重用**——说「客户机/服务器模式」，不用细节对方就懂。
- 答题两句话：词汇表那句答「**构件和连接件是什么**」；约束那句答「**它们怎么组合**」。

对比：❌「本系统采用分层架构比较合适」（无依据）；✅「**构件**是层，**连接件**是层间协议，**代价**是性能与灵活性」。

## 4.2 六类风格

| 类别 | 风格 |
| --- | --- |
| 1. 数据流 | 批处理、管道与过滤器 |
| 2. 调用与返回 | 主程序与子程序、面向对象、层次型、客户机/服务器 |
| 3. 以数据为中心（仓库） | 仓库、黑板 |
| 4. 虚拟机 | 解释器、规则系统 |
| 5. 独立构件 | 进程通信、事件系统 |
| 6. 面向服务 | 服务、服务总线、松散耦合标准接口 |

要点：

- **批处理**：每步是单独程序，前步完成才开始，数据**整体**传递。
- **管道与过滤器**：**构件是过滤器，连接件是管道**（必写，不能只说「用管道过滤器比较好」）。题干信号：顺序处理、数据转换、每步输出接下一步输入。加分原话：数据流体系结构**没有概念上的程序计数器**，指令执行由**输入参数的可用性**确定。
- **主程序与子程序**：单线程控制；构件＝主程序和子程序，连接件＝**过程调用**。
- **面向对象**：数据与操作封装在抽象数据类型/对象中；**构件是对象**。
- **层次型**（最常考）：每层为上层服务、作下层客户；**连接件＝层间交互协议**。两个优点必背：①**每层最多只影响两层**；②相邻层接口相同则**各层实现方法可不同**——支撑**软件重用**。
- **客户机/服务器**：基于**资源不对等**、为**共享**而提出；胖客户机/瘦服务器。
- **仓库**：**中央数据结构＋一组独立构件**。
- **黑板**：解决复杂的**非结构化问题**，综合运用**多种知识源**；传统应用＝**信号处理（语音识别、模式识别）**——可直接引用。
- **虚拟机**：人为构建运行环境，解析运行自定义语言，增加灵活性；**解释器**仿真硬件执行，**缺点执行效率低**；**规则系统**（典型例子专家系统）：规则集、规则解释器、规则/数据选择器、工作内存。
- **独立构件**：构件是独立个体、**不直接通信**，降低耦合。**进程通信**：连接件＝**消息传递**（点到点、异步/同步、远程过程调用）；**事件系统**：构件**触发或广播事件**，其他构件的过程**注册**，事件触发时自动调用——关键原话：**事件的触发者并不知道哪些构件会被这些事件影响**。
- **面向服务（SOA）**：客户机/服务器架构的设计方法，强调**松散耦合＋独立的标准接口**；功能定义成**独立服务**，通过**服务总线或流程管理器**连接。

## 4.3 六类风格一张表（第三列才是拉开差距的地方）

| 风格 | 构件 / 连接件 | 代价 |
| --- | --- | --- |
| 管道与过滤器 | 过滤器 / 管道 | 不适合交互式应用；**数据格式必须统一** |
| 层次型 | 层 / 层间协议 | 层数多**性能下降**；跨层调用**破坏约束** |
| 仓库与黑板 | 中央数据结构＋独立构件 / 独立构件对中央数据的操作 | 中央数据结构成为**瓶颈与单点** |
| 事件系统 | 独立构件 / 事件广播与注册 | **不能假定处理顺序**，不知道哪些过程会被调用 |
| 面向服务 | 服务 / 服务总线 | **划分与治理成本**；接口设计错了很难改 |

> 代价一列是建议性归纳，答题落回教材原话更稳。**只答优点不答代价，通常只能拿一半分。**

## 4.4 五问定风格

1. **数据整批走还是逐步转换？** 整批＝批处理；逐步＝管道与过滤器；
2. **要分层、共享资源吗？** 分层可控＝层次型；资源不对等为共享＝客户机/服务器；
3. **围绕一份共享数据转吗？** ＝仓库；再综合多知识源求解非结构化问题＝黑板；
4. **要解析自定义语言或规则吗？** ＝虚拟机（解释器/规则系统），代价执行效率；
5. **构件要解耦吗？** 消息传递＝进程通信；广播事件＝事件系统；跨系统集成＝面向服务。

## 4.5 仿真题与四句模板

**仿真题（数据处理平台）**：夜间批量清洗汇总生成报表＋高峰期异常交易告警。①批量部分＝**管道与过滤器**（风格名→构件连接件→理由）；②告警与批量**需求不同、风格可以不同**（批处理 vs 及时响应，别硬套一种）；③第三问问的就是**代价**。

**四句模板**：

1. **给结论**：「批量处理部分采用管道与过滤器风格」；
2. **给结构**：「构件是过滤器，连接件是传输数据流的管道」；
3. **给理由**：「清洗、汇总、报表正好是顺序三步，每步输出接下一步输入，与场景匹配」；
4. **给代价**：「不适合交互式应用；各步骤数据格式必须统一」。

一条一分，分条编号写；**第二、三句是绝大多数人漏掉的**。

**五个失分**：只报风格名、理由写通用好话（要写题干场景为什么匹配）、漏代价这一问、风格名记混/自造术语（只用教材名字）、混合需求只给一种风格。

# 专题四 数据库设计（第 5 讲｜教材第五章）

> 核心结论：数据库题**一半考流程，一半考范式**；判范式的前提动作（先求候选键）很多人直接跳过去了——跳过去后面全错。

## 5.1 设计五阶段（第一问主要得分点）

| 阶段 | 任务 |
| --- | --- |
| **规划** | 必要性与可行性分析，确定数据库在企业和信息系统中的地位 |
| **需求分析** | 摸清**数据要求**与**处理要求**，整理成需求说明书；数据称**源数据**，由**数据字典**管理 |
| **概念设计** | 抽象成**不依赖任何 DBMS** 的数据模型；先做各应用**视图**，再**视图集成**，形成单一概念数据模型 |
| **逻辑设计** | 概念模型 → 某种 DBMS 的**逻辑模型**并优化（E-R 图转成 DBMS 支持的逻辑结构） |
| **物理设计** | 挑最适合的**物理结构**（**存储结构和存取方法**）；含存储记录结构、数据存储安排、访问方法、完整性安全性分析与设计、数据库程序设计 |

考试考「某阶段做什么」或「漏了哪个阶段」——打法：**阶段名称＋该阶段任务**，两句都要有。

## 5.2 实体联系图三要素

教材定义：**实体联系模型（E-R 图）是描述概念世界、建立概念模型的实用工具**。

| 要素 | 表示 | 说明 |
| --- | --- | --- |
| 实体 | **矩形框** | 框内写实体名称 |
| 属性 | **椭圆形** | 连线与实体相连 |
| 联系 | **菱形框** | 框内写联系名称，连线上**注明类型**（1:1、1:n、m:n） |

**属性分三类（画图题高频失分点）**：

| 类型 | 画法 | 例子 |
| --- | --- | --- |
| 单值属性 | 普通椭圆 | 普通属性 |
| 多值属性 | **外面再套一个椭圆（外实内虚）** | 学员的**多个兴趣** |
| 派生属性 | **虚线椭圆** | 计算出来的：总成绩、平均成绩 |

考法：指出图里属性画错——先分清**多值还是派生**，再看**椭圆虚实**，两句话说完。

## 5.3 判范式之前，必须先求候选键（图示法）

1. **画有向图**：顶点是属性，**弧是依赖关系**；
2. **找入度为零的属性集**，从它出发尝试**遍历**所有节点；
3. 能遍历全部 → 就是**候选键**；遍历不全 → **并入中间顶点**，直到能遍历所有顶点。

为什么必须先求候选键：**非键属性＝不属于任何候选键的属性**——键定错，非键属性范围跟着错，结论站不住。

> 教材原话：**求关系模式的候选键是进行范式界定的基础，也是系统分析师应该掌握的基本技能。**

## 5.4 四档范式，逐级加严

| 范式 | 条件 |
| --- | --- |
| **1NF** | 所有属性只含**原子值**，每个分量不可再分 |
| **2NF** | 1NF＋每个**非键属性完全依赖**于候选键（消除**部分依赖**） |
| **3NF** | 2NF＋消除非键属性对候选键的**传递依赖** |
| **BCNF** | 进一步消除**主属性**对候选键的部分依赖和传递依赖 |

> 教材原话：**实际应用中，一般只要达到第三范式**——答题判到 3NF 就够，不要过度设计。

**两个教材例子**：

- **选课关系**（学号、课程号、成绩、学分）：候选键＝学号＋课程号；课程号单独决定学分 → **部分函数依赖**，不满足 2NF；拆成「学号-课程号-成绩」＋「课程号-学分」。
- **学生关系**（学号、姓名、系号、系名称、系地址）：学号→系号→系名称/系地址 → **传递依赖**，不满足 3NF。

套路：**先写候选键 → 指出是部分依赖还是传递依赖 → 给出拆法**。

## 5.5 范式判定四步表（顺序不能跳）

| 步骤 | 内容 |
| --- | --- |
| ① 求候选键 | 有向图＋入度为零＋遍历 |
| ② 查 1NF | 有没有非原子值（可再分复合项）？ |
| ③ 查 2NF | 非键属性是否完全依赖候选键？有没有**部分依赖**？ |
| ④ 查 3NF | 非键属性之间有没有**传递依赖**（甲→乙→丙）？ |
| ⑤ 给拆法 | 出问题的属性**拆出去单独成表**，说明**保留什么作外键** |

2NF 是 3NF 的前提，跳过 2NF 直接判 3NF 一定出错。考法：「属于第几范式？为什么？如何分解？」三问连着走。

## 5.6 反规范化（反着来的考点）

- 教材说法：**非规范化可以改善系统性能**，但代价是**数据冗余**和**更新异常**。
- 答题两面：**何时该反**——查询频繁跨表连接、更新很少；**换来**减少连接次数、查询性能改善；**付出**数据冗余与更新异常。
- 性能优化着手点：硬件升级、**数据库设计**（逻辑设计＋物理设计两方面入手）、索引优化策略。

## 5.7 仿真题与三句模板

**仿真题（在线教育平台）**：①选课关系候选键＝学号＋课程号组合，判范式（部分依赖）；②学员关系沿「学号→所在系→系名称/系地址」找传递依赖并分解；③查询性能不足可否反规范化——**两面都答，缺一面不完整**。

**三句模板**：

1. **定候选键**：「候选键为学号与课程号的组合」——先定键，后面才站得住；
2. **指出依赖**：「学分只由课程号决定，构成对候选键的部分函数依赖」——**说清是哪一种依赖**，别笼统说有问题；
3. **给拆法**：「拆为：学号-课程号-成绩 与 课程号-学分，两张表」——给**可执行的结果**。

变体：补设计阶段的题答「阶段名称＋任务」；问反规范化再补一句两面话。

**五个失分**：不写候选键直接判范式、部分/传递依赖说反、只判范式不给拆法（**拆法才是这一问的主体**）、属性分类画错（多值外实内虚、派生虚线椭圆）、阶段名写了任务没写。

# 第三部分 网站架构演化（第 6 讲｜教材第十六、二十章）

> 核心结论：**拆是为了独立，不是为了时髦**——只说「微服务好」，说不出代价，只能拿一半分。

## 6.1 架构设计八条原则（第十六章）

| # | 原则 | 要点 |
| --- | --- | --- |
| 1 | 分离关注点 | 按**工作类型**分离：核心业务行为 vs 基础结构、用户界面逻辑 |
| 2 | 封装 | 各部分通过封装隔离；接口不变即可替换实现 |
| 3 | 依赖关系反转 | 依赖指向**抽象**而非实现细节 → 可实现**依赖注入** |
| 4 | 显式依赖关系 | 显式要求协作对象，一般通过**构造函数**说明 |
| 5 | **单一责任** | 对象**只有一个责任**，**只因一个原因更改** |
| 6 | 避免自我重复 | 相关行为**只在一处指定**，成为该行为的**单一权限** |
| 7 | 持久性无知 | 持久化类型的代码**不受持久性技术影响** |
| 8 | **有界上下文** | 大型应用分解为**独立概念模块**；上下文之间走**编程接口**，**不共享数据库** |

> 必记原话：把**单一责任原则**应用到体系结构与逻辑终结点时，就得到了**微服务**——选型题的重要抓手。

考法：指出设计违反哪条原则——**原则名＋它要求怎么做**，两句都要有。

## 6.2 三类架构（按开发与部署模式分）

| 架构 | 特点 | 两面 |
| --- | --- | --- |
| **整体式** | 整个软件一段代码，组件相互依赖；改一个功能要**重写并编译整个代码** | 构建测试部署简单；代码大了难管理更新、**扩展不容易**、可能**单点故障** |
| **微服务** | **松散耦合的独立服务**，走 **API**；每个服务**自带数据库**，运行特定业务逻辑 | 可**独立更新修改扩展**；**部署多个服务本身是挑战**，服务多了**管理复杂性上升** |
| **无服务器** | 底层基础设施**由服务商管理**，按使用付费，扩展交给云 | 用户省心；适用面受限 |

教材原话：**应根据系统需求与开发资源条件，选择应用系统的结构类型。**

**何时拆**：

- 用**整体式**：用例非常简单、只处理有限流量、用户群和流量**不会指数级增长**；
- 用**微服务**：用例复杂、预计流量**呈指数级增长**；开发每个组件牢记**单一责任与关注点分离**；
- **中间路线**：先整体式，之后**横向扩展到分布式微服务**——答题说出来更贴工程实际。

判断题三步：**先给场景定性 → 再落选型 → 最后说代价**，顺序别乱。

## 6.3 三种架构模式（别和分类混：分类答「怎么开发部署」，模式答「内部结构长什么样」）

- **B/S 架构**：主要事务逻辑在服务器端，一般**三层**——表现层（用户交互、结果输出）、逻辑层（应用逻辑）、数据层（独立运算）。
- **对等网络（P2P）**：客户端**不经服务器直接通信**；**完整连接拓扑**与**环形拓扑**两种；所有计算机**权限相同**，某些节点故障网络仍正常运行。
- **MVC 与 MVP**：模型提供数据、视图负责显示、控制器/表示器负责逻辑；**表示器把模型与视图完全分离**（通过定义好的接口交互）——**变更视图时保持表示器不变**。

## 6.4 微服务七条特征（第二十章）

①服务**自治性**（独立代码库、数据库、团队）②**单一职责** ③**松耦合**（独立演化变更）④**分布式部署**（可跨数据中心）⑤**技术异构性**（不同技术栈）⑥**弹性可伸缩**（自动调整实例）⑦**独立演化和部署**。

> 教材分寸：特征带来灵活性、可扩展性、可维护性和可靠性，但**要充分考虑每个特征的权衡与挑战**——这句话本身就是答题分寸。

## 6.5 三类架构对照表＋代价与应对

| 架构 | 适合 | 代价 |
| --- | --- | --- |
| 整体式 | 简单用例、有限流量 | 改动整体重编译；不易扩展；单点故障 |
| 微服务 | 复杂用例、流量指数增长 | 部署挑战；管理复杂性上升；**多库一致性** |
| 无服务器 | 多媒体处理、实时流媒体等按用量计费 | 底层由云商掌控，适用面受限 |

**拆的三条代价**：①**部署与运维**（服务数量增加，管理复杂性增加）②**数据一致性**（共享分区数据库，保证**受事务影响的多个数据库之间的一致性**）③**故障传播**（调用链变长，故障沿调用链扩散）。

**四条应对原则**：**隔离性**（独立进程＋自己的数据库资源，用**容器**实现）、**自治性**（自有生命周期、状态、行为）、**弹性**（自动扩缩容＋负载均衡＋故障转移）、**可观察性**（日志、指标、跟踪机制）。

**容错机制（加分项）**：**熔断、隔离、限流和降级、超时机制**——保证服务持续可用性。

## 6.6 仿真题与三句模板

**仿真题（电商平台）**：整体式→改一处整体编译、团队分布两市、流量预计快速增长，管理层要拆微服务。①先定性：功能复杂？流量指数增长？团队分布式协作？②新问题：部署运维、数据一致性、故障传播，别只说好处；③原则：隔离性、自治性、弹性、可观察性＋容错机制。

**选型题三句模板**：

1. **定性场景**：「该平台功能复杂，且流量预计快速（指数）增长」；
2. **给出选型**：「由整体式架构演进为微服务架构」——明确结论，不模棱两可；
3. **说清代价**：「部署与运维复杂性上升、多库一致性、故障传播，用隔离性、自治性、弹性、可观察性来应对」——**代价与应对一起说，这是得分的关键**。

变体：题目点到具体技术，再补「熔断、隔离、限流和降级、超时机制」。

**五个失分**：只写好处不写代价、不提数据一致性、架构当口号不落场景定性、混淆分类与模式、只写原则名称不写落地（如独立进程与容器）。

# 第四部分 综合实战与真题带练（第 7、8 讲）

## 7.1 综合题的本质（第 7 讲）

> 综合题**不是四道题拼在一起，而是一条主线走四步**：出题人给一个业务场景，沿**需求 → 建模 → 架构 → 数据**逐问推进。最难的不是不会，而是**看不出这一问考哪一块**——认领错考点，写得再满也拿不到分。

**结构**：①业务背景（不是废话，是每问的共同前提）＋②三到四问（各指一个专题，**问与问有依赖**——前一问补出的实体，往往是后一问要用的对象，**别各答各的**）。

**典型分工**：第一问需求（补图/补项/漏了什么环节）；第二问建模（补参与者与用例/类关系）；第三问架构（选风格/质量属性/要不要拆）；第四问数据（判范式给分解/设计阶段任务）。

## 7.2 审题三步（最值钱）

**第一步：圈动词**——动词决定交出什么：

| 动词 | 打法 |
| --- | --- |
| 指出 | 列清单，一条条写清楚 |
| 说明 | 给定义＋一句为什么 |
| 设计 | 给结构＋说明 |
| 判断并给出 | 判定和结果两步都写，缺一步扣一步的分 |

**第二步：认领考点**——关键词定位：需求（需求获取/数据字典/数据流图/需求变更/需求跟踪，第十一章）；建模（参与者/用例/包含扩展/类与关系，十一章第五节）；架构（架构风格/质量属性/选型拆分，十二、十六、二十章）；数据（E-R 图/候选键/范式分解/反规范化，第五章）。笨办法：问「怎么组织**数据**」归数据，问「怎么组织**系统**」归架构。

**第三步：判断题型**——概念说明题（定义＋解决什么问题，两句就够）；分析补全题（补对象＋理由）；设计产出题（结构＋关键元素，看出层次）；判定题（定基准→指出问题→给结果）。**认领题型比认领章节更快**——先看清是判定还是补全，就知道该写什么形态。

## 7.3 需求抓手（十一章五段）

**获取**（用户访谈、问卷调查、采样、情节串联板、联合需求计划 JRP＋需求记录技术）→ **分析**（结构化分析/面向对象分析）→ **定义**（需求规格说明书：严格定义/原型方法）→ **验证与变更**（需求评审与需求测试；变更受控；需求跟踪建立联系文档）→ 管理。

答题要领：**不需要背全五段，找出题目缺的那段，点出来＋补一句为什么缺了它会有问题**。

## 7.4 时间与顺序（看着是技巧，实际是分数）

1. **先扫全卷**：五选三（第一题必答，其余四选二），先定最有把握的两道，**不边答边选**；
2. **按问给时间**：每道大题 20～25 分钟；写不完先放下回头补，别卡死；
3. **留尾巴检查**：最后 5 分钟查每问是否都有**结论、依据、结果**。

顺序：必答题（稳基本盘）→ 最有把握的选做 → 最后啃最硬的。案例总时长按「综合知识＋案例连考共 240 分钟」折算，时间感要自己练出来。

## 7.5 四专题速查表（考前抄一遍）

| 专题 | 教材 | 常见问法 | 模板 |
| --- | --- | --- | --- |
| 需求 | 第十一章 | 补数据流图、补数据字典 | 补对象＋理由 |
| 建模 | 十一章第五节 | 补参与者与用例、判定关系 | 判定＋理由 |
| 架构 | 十二、十六、二十章 | 选风格、说质量属性、判断要不要拆 | 定性＋选型＋代价 |
| 数据 | 第五章 | 判范式、给分解 | 定性＋依赖＋拆法 |

**判定清单（四样齐全才算答完）**：①**有结论**（别让阅卷者猜立场）②**有依据**（来自哪条规则，教材原话最好）③**有结果**（可执行产物：拆法、图结构、清单）④**有分寸**（该说代价说代价、该说限制说限制，别把话说满）。缺结论含糊、缺依据无据、缺结果空泛、缺分寸不专业。

## 7.6 仿真题（设备巡检系统，三问走通四模板）

①需求过程漏了什么（补全题）：需求零散＝**获取阶段**没走完整方法；反复变更＝**变更控制和需求跟踪**没建立。②补参与者与核心用例（判定题）：巡检员/班长/管理员；上报巡检结果、审核巡检单、统计巡检数据；**必须调用用包含，偶尔发生用扩展**。③设备规模增长架构怎么调整（选型题）：定性（规模增长、查询压力上升）→ 选型（整体式→分布式微服务）→ 代价（部署运维复杂性、多库一致性、故障沿调用链传播）与应对（隔离、自治、弹性、可观察性）。

## 7.7 综合题四步模板

1. **认领**——这问属于需求/建模/架构/数据？认领错了后面全白写；
2. **回忆**——调出该专题教材抓手（定义、规则、步骤）；
3. **落模板**——按题型选模板（补全/判定/设计/说明），**模板决定产出形态**；
4. **收口检查**——对照判定清单四样，缺一样补一样，再进下一问。

每步只有一句话要做；练熟之后综合题变得很**机械**——**机械正是考场上最可靠的状态**。

**五个失分**：认领错考点、只写结论不给依据、跨问依赖没接住、时间卡死硬题、不分条编号（**成本极低、收益极高**）。

## 7.8 四问示范（第 8 讲｜智慧停车管理系统）

> 背景：某市智慧停车系统，覆盖路侧停车位与封闭停车场；车主查询车位、预约、入场停车缴费、开票；巡检员巡查、处理异常订单；管理员定价、统计、对账；**各停车场已有系统**。业务背景不是废话——后面四问都要回到背景找依据。

**第一问（需求·补全题）**：需求过程哪些环节被忽略？

1. **获取**：需求由业务方口头提出，没走用户访谈、问卷、联合需求计划等获取方法；
2. **定义**：没形成需求规格说明书，口头需求无法确认，也没有基线可比；
3. **验证**：缺少需求评审与需求测试，问题拖到上线后才暴露；
4. **变更**：需求反复变更，变更控制与需求跟踪没建立。（教材第十一章）

**第二问（建模·补全＋判定）**：参与者＝车主、巡检员、管理员、**支付平台（外部系统）**；核心用例＝查询车位、预约车位、入场停车缴费、开票、巡查状态、处理异常、统计对账；关系判定——**缴费包含查询订单**（每次缴费必先查订单，必做步骤）；**开票扩展缴费**（并非每笔都开票，偶发分支）。**判定关键：说清这一步是必做还是偶发。**（十一章第五节）

**第三问（架构·选型题，三步缺一不可）**：定性——覆盖范围扩大、高峰查询压力大、**各停车场系统异构**；选型——按**业务边界**拆独立服务，查询侧做**读写分离与缓存**；代价与应对——部署运维复杂性上升、跨库一致性、故障沿调用链传播；用隔离性、自治性、弹性、可观察性＋熔断、限流和降级、超时机制。**只写选型不写代价，只能拿一半分。**（第十二章）

**第四问（数据·范式题）**：定候选键——订单号唯一决定一条记录，候选键＝订单号；指依赖——停车场名称依赖停车场编号，而停车场编号不是候选键，存在**传递依赖**；给分解——**订单表**（订单号、车牌号、车位编号、停车场编号、入场时间、出场时间、金额）＋**停车场表**（停车场编号、停车场名称），消除传递依赖达第三范式。**定键、指依赖、给拆法，三步依据都不能省。**（第五章）

## 7.9 排版三原则（比答案本身更先被看到）

1. **分条编号**：每条单独成行＋序号，采分点一眼看见；
2. **结论先行**：第一句就说判定，不要铺垫——阅卷者不猜你的立场；
3. **依据跟上**：每条结论后接一句**教材依据**——依据往往比结论更好拿分。

两个反例：一整段不分条（采分点被埋）；先讲一大段背景再给结论（**结论放最后容易被当成没答**）。

经验：每问答 **3～5 条**、每条 **2 行以内**——宁可多分条，不要多铺陈；超三行重点就散了。

## 7.10 真题精讲：网络约车调度平台（第一问 12 分）

> 考生回忆版真题；官方不公布标准答案，解析按教材考点组织，仅供参考。

**背景**：网络约车调度服务平台——乘客、司机、平台管理员三类参与者；需求含注册与身份认证、信用管理、违章审核、**银行支付对接**、订单全流程、**短信/微信/邮件三种提醒**；需求明确，决定采用微服务架构。

**第一问（12 分，两件事）**：①100 字以内说明一个微服务包含什么；②300 字以内讲清与单体相比的**两个优势、两个挑战**。

**一个微服务包含什么**：围绕**一项业务能力**构建——这项业务的**完整处理逻辑**、自己的**数据存储**、对外暴露的**轻量级接口**、**独立运行独立部署的进程单元**。

**优势两条**：①**独立部署与弹性扩展**——单体整体部署整体扩容，微服务**只扩展压力大的那个服务**；②**服务自治与技术异构**——单个服务故障**不扩散**，可靠性与容错性更高。

**挑战两条**：①**分布式复杂性**——调用链变长；每个服务有自己的库，**跨服务数据一致性难保证**；②**运维与测试难度上升**——部署、监控、服务注册发现、链路追踪都要配套。

**第二、三问（填表/填图）识别思路**：第二问——先按**参与者与业务过程**归大类，再按**单一职责**拆到服务粒度；第三问——按**任务与子任务**找顺序（入口、处理、收口），子任务全部测试通过才上线交付。

**骨架三步模板**：

1. **定义**——一句话说清微服务是什么、里面包含什么；定义对了，对比才有锚点；
2. **分条对比**——优势两条＋挑战两条，每条写成「**单体怎样，微服务怎样**」，一条一个得分句；
3. **结合题干收口**——回题干找依据：订单峰值、支付对接、多种提醒方式。

三步对应真题第一问的 12 分；**概念说明题只写前两步就够，多写反而稀释重点**。（教材第二十章）

**五个失分**：没有分条编号、只写结论不写依据、几问合成一篇答、用例关系只写名称（要写为什么是包含而不是扩展）、范式不指出具体依赖（只说不满足 3NF 等于没有判定）。

# 附录 C：失分点全清单（合并去重）

1. **认领/审题错**：答非所问、认领错考点、把架构题当数据题答——写得再满也不对路；
2. **只给结论不给依据**：说不清违反什么规则，等于答一半；
3. **不分条编号**：采分点埋在一段话里，阅卷者漏看；
4. **口语代替术语**：不用教材说法、自造词；
5. **漏前提动作**：判范式不先求候选键；
6. **概念混淆**：部分依赖 vs 传递依赖、包含 vs 扩展、聚合 vs 组合（不提生命周期）、分类 vs 模式、多值 vs 派生属性画法；
7. **漏答整块**：只写主事件流漏备选流和前后置条件、漏代价这一问、漏数据一致性、漏外部系统与时钟；
8. **不给结果**：只判范式不给拆法、原则只写名称不写落地；
9. **不落场景**：理由写通用好话、答概念不落题干具体名字；
10. **节奏失误**：时间卡死硬题、中途换题、整题空着、重画新图、几问合成一篇答。
