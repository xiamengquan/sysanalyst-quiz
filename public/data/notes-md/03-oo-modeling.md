## 一、用例图只有三种元素（01:34）

用例图里只有三种东西，没有第四种。

### 1. 参与者（Actor）

- **定义**：存在于系统外部、并与系统进行交互的**任何事物**——不只是人。
- **三类来源**（02:30）：
  1. **其他系统**：系统需要与外部系统交互时，外部系统就是参与者。例如本系统要与公司办公系统同步数据。
  2. **硬件设备**：与系统交互的读写器、传感器等都是参与者。
  3. **时钟**：当系统需要定时触发时，时钟就是参与者——**这一条最容易漏**。题干只要出现「每天凌晨自动做什么」「每月一号定时生成什么」，参与者里就一定要写「时钟」。

### 2. 用例（Use Case）

- **定义**：系统中执行的一系列动作，这些动作会生成对特定参与者可见的价值结果。说白了，用例就是**系统对外提供的一项服务**。
- **识别时的三个坑**（03:40 前后，教材专门点名）：
  1. **用例命名**要用「动词＋名词」形式，例如「开通课程」，不能只写「课程」。
  2. **不能把用例里的步骤当成用例**：如「验证学员信息」只是「开通课程」用例里的一步，不能单独对外提供。
  3. **只识别系统用例，业务用例不用管**：业务用例含大量人工活动，信息系统实现不了。

### 3. 通信关联

- 表示**参与者与用例之间**、或**用例与用例之间**的关系，箭头指向被动接受方。
- 教材特别提醒：**信息流不是由通信关联来表示的**，它默认存在且是双向的。

**考点**：给一段业务描述，补遗漏的参与者或用例——少写一个就少一个得分点。

## 二、用例的三种关系（03:40）——最常被画错的地方

### 1. 包含关系（include）

- **触发条件**：可以从两个或两个以上的用例里**提取公共行为**时，用包含。
- 抽出来的叫**抽象用例**。
- **判定关键词**：**一定会执行**——少了它基本用例就不完整。

### 2. 扩展关系（extend）

- **触发条件**：一个用例明显**混合了两种或两种以上不同的场景**时，把它拆成一个基本用例＋一个或多个扩展用例。
- **判定关键词**：**看情况才执行**。

### 3. 泛化关系

- **触发条件**：多个用例共同拥有类似的结构和行为时，把共性抽象成父用例，其余作为子用例。
- 子用例**继承**父用例全部的结构和行为。

### 判定口诀（04:27）

> **一定会走的是包含；看情况才走的是扩展；父子同类的是泛化。**

### 教材提醒

这三种关系都会**增加用例的个数**，从而增加模型的复杂度。所以一般是**用例模型完成之后才调整**，建模之初不要急着抽象。

## 三、建模的主要工作是「写」，不是「画」（04:49）

教材原话（第十一章），也是本讲最想让你记住的一句：

> **用例建模的主要工作是书写用例规约，而不是画图。**

一份用例描述通常包括：

| 组成部分 | 要点 |
| --- | --- |
| 用例名称 | 要和用例图相符，并写上编号 |
| 简要说明 | 描述该用例为参与者传递了什么价值 |
| 事件流 | 主体部分：**主事件流**是能满足目标的典型成功路径，通常不含条件和分支；**备选事件流**（也叫扩展事件流）是失败情况、分支路径——写的时候把分支全部抽出来，别混进主线 |
| 非功能需求 | 单列一小节，**一定要可度量、可验证**，否则就是摆设 |
| 前置条件 | 执行前必须存在的系统状态，不满足就启动不了 |
| 后置条件 | 用例执行完系统可能处于的一组状态 |
| 扩展点 | 如果包含或扩展了别的用例，写出用例名和使用条件 |
| 优先级 | 说明用户对该用例的期望值 |

**答题方法**：补描述题就照这几项逐条检查，缺哪几项、写哪几项。

## 四、分析模型：四步走完（06:05）

用例模型之后是分析模型，建立分析模型大致四步：

1. **定义概念类**：最常用的方法是**名词短语法**——阅读需求描述，把名词或名词短语挑出来，作为候选的概念类或属性。
2. **确定类之间的关系**：六种关系判定清楚，再用类图记录下来，形成**领域模型**。
3. **为类添加职责**：教材提醒，这一阶段只能找到**主要的职责**，不必求全。
4. **建立交互图**：多个对象的行为用交互图表示，其中最常用的是**顺序图**。
   - 顺序图基本元素：对象、参与者、生命线、激活、消息（**消息是顺序图的灵魂**）。
   - 当对象行为复杂、存在多种状态转换时，还要用**状态图**。

前三步有学者统称为「**类－责任－协作者（CRC）建模**」。

**考试提醒**：概念类只挑主要的，职责只写主要的——答多了不加分，答偏了会扣分。

## 五、类的六种关系（07:14）

### 1. 关联（Association）

- 提供不同类的对象之间的**结构关系**，在一段时间内把多个类的**实例**连接在一起。
- 教材强调：关联体现的是**对象实例之间**的关系，不是两个类之间的关系。
- 描述关联可用：**名称、角色、多重性、导向性**。

### 2. 依赖（Dependency）

- 两个类甲和乙：如果乙的变化可能引起甲的变化，就说**甲依赖于乙**。
- 产生依赖的场景：发消息、做数据成员、做操作参数。

### 3. 泛化（Generalization）

- 描述**一般事物和它的特殊种类**之间的关系，即父类和子类。
- **继承是泛化的反关系**。

### 4. 实现（Realization）

- 把**说明和实现**联系起来：接口是对行为而非实现的说明，类里包含实现的结构。

### 5. 聚合（共享聚集，Aggregation）

- 表示**整体与部分**的关系：**部分可能同时属于多个整体**，部分与整体的生命周期**可以不相同**。
- 教材例子：**汽车和车轮**——车子坏了，车轮还能用。

### 6. 组合（组合聚集，Composition）

- 也表示整体与部分，区别在于：**部分只能属于一个整体**，**生命周期相同**——部分随着整体的创建而创建、消亡而消亡。
- 教材例子：**公司和部门**——公司倒闭了，也就无所谓部门。

### 聚合 vs 组合：一句判定（08:43）

> 判定聚合还是组合，只需问一句：**部分的生命周期跟不跟着整体走？——跟是组合，不跟是聚合。**
> 这一句就是判定题的全部答案。

### 常考细节：多重性

- 指定的是一个类的**多少个对象**，在一段特定时间内可以和另一个类的**一个对象**相关联。
- **`*` 等价于 0..多**。

**考试打法**：题目让你「说明两个类之间是什么关系并说明理由」——先给关系名，再给判定依据，**两句缺一不可**。

## 六、四类高频错误（09:21）——本专题丢分大头

1. **把步骤当成用例**：「验证学员信息」只是「开通课程」事件流里的一步，不能单独对外提供。
2. **包含与扩展划反**：判定错了，箭头方向也就跟着反了。
3. **只写主事件流，漏掉备选事件流**：失败情况和分支路径必须单独抽出来写。
4. **聚合与组合凭感觉选，不提生命周期**。

> 这四条全部能在教材第十一章找到对应原话。答题时直接引用教材的说法是最稳的写法。

## 七、仿真题走一遍（10:02）

> 说明：仿真题按教材考点自造，非真题，用于演示答题路径。

**场景**：某公司要开发在线培训系统。学员登录后选课、学习课程、参加课程测试；客服人员为学员开通课程、解答咨询；系统每天凌晨自动生成学习进度报表；还需与公司办公自动化系统同步学员名单。

**第 1 问：该系统的参与者有哪些？**

按三类来源过一遍：

- 人：学员、客服人员
- 其他系统：办公自动化系统
- 时钟：每天凌晨的定时触发

共四个。

**第 2 问：「学习课程」和「参加课程测试」都需要先验证学员权限，该用哪种关系？**

- 先判断：一定会执行，还是看情况才执行？
- 两个用例都要验证 → 是**公共行为**，而且**一定会走** → **包含关系**，「验证权限」是**抽象用例**。

**第 3 问：补充「开通课程」用例描述的缺失项**

对照用例描述的组成项逐条检查，缺什么补什么。

## 八、答题模板：判定题的三句（11:14）

把上面的第 2 问抽象成模板，判定题用三句写完：

1. **第一句给结论**：「应使用包含关系，验证权限为抽象用例」——先把关系名说出来，不要上来就解释。
2. **第二句给依据**：「这是从两个以上用例抽出的公共行为，而且一定会执行」——依据要落在教材的说法上。
3. **第三句给画法**：「箭头由基本用例指向抽象用例，标注 include（包含）」——方向说清楚，不留歧义。

**注意事项**：

- 三句一个得分点，**分条编号写**，不要合并成一段。
- 补参与者、补用例这类**列举题**不用第三句，逐条列举即可。
- 记住一个信号：题目出现「**说明理由**」四个字，就一定要写第二句——只给结论通常只能拿一半分。

## 九、五个常见失分（12:07）

1. 只写参与者里的人，**漏掉外部系统和时钟**——一题少两个得分点。
2. 关系名写了、**方向没写**——包含与扩展的箭头方向是相反的，说不清等于没答。
3. 用例描述只写正常流程，**漏掉备选事件流和前置/后置条件**。
4. 聚合组合只答「整体与部分」，**不提生命周期**——判定不完整。
5. 答一堆课本概念、**没有落到题目场景**——每条都要带上题干里的具体名字。

## 十、一页纸带走（12:45）

| 内容 | 速记 |
| --- | --- |
| 三种元素 | 参与者、用例、通信关联——用例图里没有第四种 |
| 三种用例关系 | 一定会走的是**包含**；看情况才走的是**扩展**；父子同类的是**泛化** |
| 六种类关系 | 关联、依赖、泛化、聚合、组合、实现——聚合与组合看**生命周期** |
| 三句模板 | 给**结论**、给**依据**、给**画法** |

教材第十一章那句话再念一遍：**用例建模的主要工作是书写用例规约，而不是画图。**

面向对象建模讲的是需求侧（怎么描述系统）；下一集换到架构侧：六种架构风格各自长什么样、构件和连接件分别是什么、选型题到底怎么答（教材第十二章）。还是同一套结构：教材抓手 → 错误清单 → 仿真题 → 答题模板。
