**看完这一集你能做到**：自己判定一个关系模式到底到第几范式，并给出分解。

**本讲核心结论**：数据库题**一半考流程，一半考范式**，通常两问——

1. 第一问：设计或补充概念模型，画**实体联系图**；
2. 第二问：给一个关系模式，问它属于**第几范式**、该怎么**拆**。

两问各有各的答法，混在一起答最容易丢分。很多同学画得出图，却判不出范式——因为判范式有一个**前提动作（先求候选键）**，很多人在考场上直接跳过去了。

教材定位：第五章第四节讲**设计流程**，第五章第二节讲**规范化**，本讲把两处接到一起讲。

**本讲四件事**：

1. 设计的五个阶段：规划、需求分析、概念设计、逻辑设计、物理设计
2. 实体联系图的三要素：实体、属性、联系（属性还要再分三类）
3. 候选键怎么求——教材给了一种很快的方法：**图示法**
4. 范式怎么判定，以及什么时候该反着来（**反规范化**）

## 一、设计分五个阶段（01:39）——第一问的主要得分点

| 阶段 | 任务 |
| --- | --- |
| **1. 规划** | 建立数据库的**必要性与可行性**分析，确定数据库系统在企业和信息系统中的地位 |
| **2. 需求分析** | 摸清用户的**数据要求**和**处理要求**，整理成需求说明书；这些数据称为**源数据**，通常由**数据字典**来管理 |
| **3. 概念设计** | 把需求抽象成一个**不依赖任何数据库管理系统**的数据模型；教材特别提到：先做各个应用的**视图**，再做**视图集成**，最后形成单一的概念数据模型 |
| **4. 逻辑设计** | 把概念模型转化成某种数据库管理系统上的**逻辑模型**，并对它做优化；目的是把概念设计阶段画好的实体联系图，转换成与具体 DBMS 所支持的数据模型相符合的逻辑结构 |
| **5. 物理设计** | 给逻辑模型挑一个最适合应用环境的**物理结构**，主要指**存储结构和存取方法**；具体包括：设计存储记录结构、确定数据存储安排、设计访问方法、做完整性和安全性的分析与设计、数据库程序设计 |

**考试怎么考**：让你说明某个阶段做什么，或指出题目里漏掉了哪个阶段。打法是「**阶段名称＋该阶段的任务**」两句都要有。

## 二、实体联系图只有三样东西（02:46）

教材定义：**实体联系模型（也叫实体联系图）是描述概念世界、建立概念模型的实用工具**。

| 要素 | 表示 | 说明 |
| --- | --- | --- |
| **实体**（实体型） | **矩形框** | 框内写实体名称 |
| **属性** | **椭圆形** | 用一条连线把它和实体连起来 |
| **联系** | **菱形框** | 框内写联系名称，连线上还要**注明联系的类型**：一对一、一对多还是多对多 |

要再记一句话：概念设计阶段，先做各个应用的**视图**，再做**视图集成**，最后形成一个单一的概念数据模型——这句话本身就是考点。

### 属性分三类，画法各不相同（03:35）——画图题的高频失分点

| 类型 | 画法 | 例子 |
| --- | --- | --- |
| **单值属性** | 普通的椭圆形，用连线与实体相连 | 普通属性 |
| **多值属性** | 在原椭圆**外面再套一个椭圆（外实内虚）** | 一个学员的**多个兴趣** |
| **派生属性** | **虚线椭圆** | 从基本属性**计算**出来的：总成绩、平均成绩 |

**考试怎么考**：让你指出图里某个属性画错了。判法是先分清它是**多值**还是**派生**，再看椭圆的**虚实**，两句话就能说清。

## 三、判范式之前，必须先求候选键（04:44）——本集最硬的部分

**这一步跳过去，后面全错。** 教材给了一个很快的方法，叫**图示法**：

1. **第一步**：把这关系的**函数依赖用有向图**表示出来——**顶点是属性，弧是依赖关系**。
2. **第二步**：找出**入度为零**的属性集，从它出发尝试**遍历**所有节点。
   - 能遍历全部节点 → 这入度为零的属性集就是**候选键**。
   - 遍历不全 → 把一些**中间顶点并进来**，直到能遍历所有顶点，这集合才是候选键。

**为什么非要先求候选键？** 因为范式里说的「**非键属性**」，指的就是**不属于任何候选键**的属性——键定错了，非键属性的范围就跟着错，结论自然站不住。

教材原话：**求关系模式的候选键是进行范式界定的基础，也是系统分析师应该掌握的基本技能。**

## 四、四档范式，逐级加严（05:50）

| 范式 | 条件 |
| --- | --- |
| **第一范式（1NF）** | 所有属性只包含**原子值**，每个分量都是**不可再分**的数据项 |
| **第二范式（2NF）** | 在 1NF 基础上，每个**非键属性**都**完全依赖**于候选键——即消除**部分依赖** |
| **第三范式（3NF）** | 在 2NF 基础上，消除非键属性对候选键的**传递依赖** |
| **BC 范式（巴斯-科德范式）** | 进一步消除**主属性**对候选键的部分依赖和传递依赖 |

**必须记住的教材原话**：「目前共定义了多个范式，但在实际应用中，**一般只要达到第三范式**。」——答题判到第三范式就够了，**不要过度设计**，判到第四、第五范式反而会把自己绕进去。

### 两个教材例子，吃透就够用（06:44）

**例 1：不满足第二范式的「选课」关系**——属性：学号、课程号、成绩、学分

- 学号＋课程号共同决定**成绩**，而**课程号单独**就能决定**学分**；
- 候选键是「学号＋课程号」的组合；**学分只依赖其中的一部分**——这就是**部分函数依赖**，所以不满足 2NF；
- **拆法**：拆成「学号、课程号、成绩」和「课程号、学分」两张表。

**例 2：不满足第三范式的「学生」关系**——属性：学号、姓名、系号、系名称、系地址

- 学号决定**系号**，系号又决定**系名称**和**系地址**；
- 系名称与系地址是**通过系号间接决定**的——这就是**传递依赖**，所以不满足 3NF。

把这两例连起来就是答题套路：**先写候选键是什么 → 再指出哪一条依赖是部分依赖还是传递依赖 → 最后给出拆法**，三步写完这一问就完整了。

## 五、范式判定表：四步走完（07:52）

考场上照着走，**顺序不能跳**（第二范式是第三范式的前提，跳过第二范式直接判第三范式一定出错）：

| 步骤 | 检查内容 |
| --- | --- |
| **第一步：求候选键** | 画函数依赖的**有向图**，找**入度为零**的属性集，尝试**遍历**全部节点 |
| **第二步：查 1NF** | 有没有属性**不是原子值**、是可再分的复合项？ |
| **第三步：查 2NF** | 非键属性是否**完全依赖**候选键？有没有只依赖其中一部分的**部分依赖**？ |
| **第四步：查 3NF** | 非键属性之间有没有**传递依赖**——即「甲决定乙、乙又决定丙」这种链？ |

**最后一步：给出拆法**——把出问题的属性**拆出去单独成表**，并说明**保留什么作为外键**。

**考试怎么考**：给出关系模式和**函数依赖集**，问「属于第几范式？为什么？如何分解？」——三问连着，一步步往下走就行。

## 六、反着来的考点：反规范化（08:57）

教材的说法：从某种意义上来说，**非规范化（反规范化）可以改善系统的性能**，但代价也很实在——会带来**数据冗余**和**更新异常**。

答这一问必须两面都答：

- **为什么要反着来/什么时候该反**：查询**频繁跨表连接**、而**更新很少**的时候；
- **换来什么**：减少**连接次数**，查询性能明显改善；
- **付出什么**：**数据冗余**，以及随之而来的**更新异常**。

教材还给了**性能优化**的几个着手点：硬件升级、**数据库设计**、索引优化策略——其中数据库设计这一项又可以从**逻辑设计**和**物理设计**两方面入手。

## 七、仿真题走一遍（09:46）

> 说明：按教材考点自造，非真题，用于演示答题路径。

**场景**：某在线教育平台有「选课」关系，属性为学号、课程号、成绩、学分；另有「学员」关系，属性为学号、姓名、所在系、系名称、系地址。已知学号与课程号共同决定成绩，课程号决定学分，学号决定所在系。

1. **第一问**：指出选课关系的**候选键**，并判断它属于**第几范式**。——走法很固定：先求候选键，再看有没有部分依赖，最后给拆法。
2. **第二问**：学员关系存在什么问题，如何分解？——思路是沿着「学号 → 所在系 → 系名称/系地址」这条链找**传递依赖**。
3. **第三问**：如果查询性能不足，是否可以考虑**反规范化**？——这一问要**两面都答**：换来什么、付出什么，缺一面就不完整。

---

## 八、答题模板：范式题三句（10:50）

1. **第一句：定候选键**——「候选键为学号与课程号的组合」。先定键，后面的话才站得住。
2. **第二句：指出依赖**——「学分只由课程号决定，构成对候选键的**部分函数依赖**」。要把**是哪一种依赖**说清楚，别笼统说有问题。
3. **第三句：给拆法**——「拆为：学号-课程号-成绩 与 课程号-学分，两张表」。要给出**可执行的结果**。

三句就是一个完整答案，记得**分条编号**，别写成一大段。

**变体**：

- 补设计阶段的题：不用这三句，答「**阶段名称＋该阶段的任务**」即可。
- 题目还问反规范化：再补一句两面话——「换来查询性能，付出数据冗余与更新异常」。

## 九、五个常见失分（11:43）

1. **不写候选键直接判范式**——没有键就谈不上部分依赖和传递依赖，结论站不住。
2. **部分依赖和传递依赖说反了**——只依赖键的一部分是**部分依赖**；甲决定乙、乙决定丙是**传递依赖**。这两个词别混。
3. **只判范式不给拆法**——题目问的是「如何分解」，**拆法才是这一问的主体**。
4. **属性分类画错**——多值属性是**外实内虚**（双椭圆），派生属性用**虚线椭圆**，别搞反。
5. **阶段名写了、任务没写**——只写「概念设计」四个字不够，要写出**它到底做什么**。

## 十、一页纸带走（12:30）

| 内容 | 速记 |
| --- | --- |
| **五个阶段** | 规划 → 需求分析 → 概念设计 → 逻辑设计 → 物理设计 |
| **三个要素** | 实体用**矩形**、属性用**椭圆**、联系用**菱形** |
| **判范式顺序** | 先**求候选键** → 再看**部分依赖**（2NF）→ 最后看**传递依赖**（3NF） |
| **三句模板** | **定候选键**、**指出依赖**、**给拆法** |

再记教材第五章的两句话：实际应用中**一般只要达到第三范式**；**非规范化也可以改善性能**（但带来冗余与更新异常）。

数据库设计讲的是**数据怎么组织**；下一集回到系统层面，讲一个很常见的题——**网站架构怎么演化**：什么时候该从整体式拆成微服务？要解决的坑也很典型——只说微服务好，说不出**拆分的代价**（教材第十六、二十章）。学完能拿到三种架构的取舍对照。还是同一套结构：教材抓手 → 错误清单 → 仿真题 → 答题模板。
