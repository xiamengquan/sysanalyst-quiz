0. 方法说明：第一性原理 × 费曼，用在应试上

必会 · 默写卡（M）

  1. 需求三层：业务需求（组织目标，为什么做）→ 用户需求（用户要完成的任务）→ 系统需求（功能 + 非功能，SRS 的主体）。
  2. 需求获取五法与选型：访谈（一对一深挖，灵活费时）；问卷（大样本广度）；联合需求计划 JRP（多方 workshop 高效共识）；原型法（需求模糊时可视化确认——把「用嘴确认」换成「用眼看」）；现场观察（拿一手实际流程）。口诀：说不清→原型；多方分歧→JRP；深挖→访谈；量大→问卷；流程脱节→观察。
  3. 结构化分析与 DFD：DFD 四要素：外部实体（方框，边界外数据源/汇）、加工（圆角框，数据变换）、数据存储（开口矩形，静态数据）、数据流（箭头）；父图子图平衡；数据字典定义各要素含义。
  4. 用例建模与 include/extend：参与者（系统外交互角色，含人/设备/外部系统）+ 用例（参与者完成的完整目标功能）；include=必然复用的子功能；extend=有条件才触发的可选扩展；用例规约=前置条件+主流程+备选流+后置条件。
  5. SRS 内容与作用：范围、功能需求（输入-处理-输出）、非功能需求（性能/安全/可靠性/易用性/可维护性）、约束、接口；作用：开发与测试的依据、验收标准、需求基线。只写「做什么」不写「怎么实现」。
  6. 需求验证四法：需求评审（正式评审会，最常用）；原型验证（运行演示确认理解一致）；测试设计验证（设计测试用例反推需求可测性）；形式化验证（数学证明，成本高，用于安全关键系统）。
  7. 需求评审六查：正确性、完整性、一致性（无冲突）、无二义性（每条可唯一理解）、可验证/可测试性（「快速响应」不合格，「P95≤2s」合格）、可跟踪性（每条可溯源到上层需求）。
  8. 需求跟踪矩阵：正向跟踪（需求→设计→代码→测试用例，保每条被实现验证）；反向跟踪（设计/代码→需求，防镀金与冗余）；用途：变更影响分析、覆盖率检查。
  9. 需求变更控制 CCB：提出书面变更申请 → CCB（变更控制委员会）评估影响（成本/进度/质量/风险）→ 批准或拒绝 → 更新需求基线与跟踪矩阵 → 通知全部干系人。基线后任何口头直改都是变更失控。
  10. 需求状态与基线：状态链建议→批准→实现→验证→完成（或拒绝/延期）；基线=通过正式评审并冻结的版本，基线化后进入配置管理；需求管理三件套=变更控制 + 状态/版本跟踪 + 跟踪矩阵。

逐点讲透 · 一通到底（编号 = /track 知识点 id，先懂后背）

01 需求三层（req-p01）

  • 第一性拆解：软件的本质矛盾——出资人、使用者、机器说的不是一种语言。老板说目标（效率提升 30%），用户说任务（我要少跑腿），机器只懂指令（输入→处理→输出）。这三者之间天然存在两道翻译鸿沟，于是需求必须分三层，每层对应一次翻译。不是教科书规定分三层，是翻译链本身有三站。
  • 费曼讲法：装修房子。业务需求 =「住得舒服还省钱」（目标）；用户需求 =「老婆要书房、我要大厨房」（每个人的任务清单）；系统需求 = 施工图纸——哪面墙拆、插座留几个、预算多少。图纸里不会写「住得舒服」，因为施工队看不懂愿望，只看得懂尺寸。SRS 就是图纸。
  • 一通到底：为什么验收标准必须挂在系统层？因为只有「尺寸」（P95≤2s）可施工可验收，「舒服」（快速响应）没法验收。为什么业务需求不能直接开发？因为愿望没有接口。三层就是为了让每句话落在能被执行的那一层。
  • 考场回扣：问「分哪几层」→ 三层各一句 + 各举一例；问「这条需求有什么问题」→ 先判它断在哪层（把业务目标写进 SRS = 不可验证；只有系统功能不挂业务目标 = 为做而做）。

02 需求获取五法与选型（req-p02）

  • 第一性拆解：获取的根本困难不是「用户不愿意说」，而是用户自己也不知道自己要什么（认知鸿沟）。五种方法本质是五种「绕过这个鸿沟」的物理手段：访谈（帮个体想清楚）、问卷（大样本统计共性）、JRP（让分歧方当场对撞出共识）、原型（把「说不清」变成「看了再说」）、观察（他说的不算，看实际怎么做）。
  • 费曼讲法：你问朋友「想吃什么」，他说「随便」——这就是需求模糊。对策同构：盯着他冰箱做菜（观察）；端两盘让他尝（原型）；全家开饭桌会（JRP）；挨个问（访谈）；发群里投票（问卷）。
  • 一通到底：选型题的答案为什么是「场景→方法」一一对应？因为每种方法只解鸿沟的一种形态：说不清→原型（表达题降维成选择题）；多方分歧→JRP（共识要同场达成）；深挖个体→访谈；量大→问卷；说的和做的不一致→观察。没有万能法，所以答案永远是「挑 2–3 个 + 理由」。
  • 考场回扣：案例给场景挑方法，每法配一句「因为该场景存在 XX 鸿沟」。铁律：用户「说不清想要什么界面」→ 原型法，写问卷就丢分。

03 结构化分析与 DFD（req-p03）

  • 第一性拆解：复杂系统的唯一破解法是分解——但分解后各部分必须能拼回去。DFD 就是「分解而不丢信息」的记账系统：数据从哪来（外部实体）、到哪去（外部实体）、谁加工（加工）、中间放哪（数据存储）、沿什么走（数据流）。四要素各管一个「不变式」：数据不凭空出现、不凭空消失。
  • 费曼讲法：快递系统图。客户（外部实体）交件→分拣中心（加工）→仓库（数据存储）→派送（加工）→收件人（外部实体）。每一个包裹（数据流）都必须可追问：「从哪来、到哪去、中间谁碰过、存没存过」——答不上任一问，就是图画漏了。
  • 一通到底：为什么必须「父图子图平衡」？因为分解只是换视角，总量守恒：父图的一条入流在子图里可以拆成几条，但不能凭空多出或消失——这正是「分解不丢信息」不变式的图上体现。为什么填图判据是「名词人/组织=实体，名词表/库=存储，动词=加工」？因为四要素的定义本来就是这么切的。
  • 考场回扣：补图题按守恒检查进出；名词动词判类型；父图子图平衡是标准扣分点。

04 用例建模与 include/extend（req-p04）

  • 第一性拆解：DFD 管数据流，但用户买的不是数据流，是结果。用例 =「参与者完成一个完整目标」——以目标为单位切片，天然对齐验收。而目标之间有两种复用关系：必经的公共步骤（include）和锦上添花的分支（extend）。这不是 UML 规定，是「复用」的两种物理形态：必然复用 vs 条件复用。
  • 费曼讲法：点外卖。「下单支付」是每个订单必经（include 进所有下单流程）；「改配送地址」只有想起来才做（extend 挂在旁边）。员工入职必走「签合同」（include），可能触发「申请工位调整」（extend）——必经的写进主流程，看情况的画虚线挂旁边。
  • 一通到底：为什么 include 箭头从基用例指向被包含、extend 反向？因为 include 是「我必然调用你」（主流程依赖子步骤），extend 是「我可能被你触发」（扩展等待条件）。方向就是依赖方向。为什么 extend 有条件？因为它不是目标的一部分，是例外处理。
  • 考场回扣：判据一句话——必然 = include，看情况 = extend；画图注意箭头方向与虚线实线。

05 SRS 内容与作用（req-p05）

  • 第一性拆解：模型画完为什么还要写 SRS？因为图是给人看的沟通工具，契约必须能逐条引用、逐条验收——「条目化 + 可追溯」是 SRS 存在的唯一理由。它只写「做什么」不写「怎么实现」，因为实现是设计的事——需求与设计的分界线就是「What / How」。
  • 费曼讲法：SRS = 装修合同。合同写「瓷砖什么规格、哪天完工、达不到怎么赔」，不写「工人几点上班、用什么瓦刀」——后者是施工队（设计师）的家务事。合同写愿望（「高端大气」）没法验收，写规格（「≥800×800 全抛釉」）才能。
  • 一通到底：为什么非功能需求（性能/安全/可靠性）必须进 SRS？因为它们同样是「做什么」的一部分——系统做出来的东西不仅要功能对，还要够快够稳。为什么验收要靠它？因为它是三方（甲方/开发/测试）唯一共同的书面基准——基线的物理载体。
  • 考场回扣：问「SRS 应包含什么」→ 范围/功能/非功能/约束/接口 + 一句「只写做什么」；问「SRS 的作用」→ 开发测试依据、验收标准、需求基线。

06 需求验证四法（req-p06）

  • 第一性拆解：为什么需求要「验证」？因为错误修复成本随阶段指数增长——需求期改一句话，上线后改一个系统。验证的本质是在便宜的阶段模拟昂贵的失败。四个方法 = 四种模拟手段：评审（人多眼杂模拟误读）、原型（运行模拟使用）、测试设计（提前写判卷标准模拟验收）、形式化（数学证明模拟一切）。另外分清：验证 = 需求写对了吗（对内部一致性）；确认 = 做的是用户要的吗（对外部正确性）。
  • 费曼讲法：盖楼前验图纸。图纸会审（评审）、搭样板间（原型验证）、先出验收清单（测试设计验证）、结构力学计算（形式化验证）。没人等楼盖塌了再改——因为那时最贵。
  • 一通到底：为什么「评审」最常用？因为成本最低收益最大——一群人找错比一个人找错快一个数量级。为什么形式化只用于安全关键系统？因为数学证明最贵，只有「错一次就死」的场景才付得起。
  • 考场回扣：选型按「错误代价 × 预算」推理；辨析题死抠「验证 vs 确认」两个方向。

07 需求评审六查（req-p07）

  • 第一性拆解：评审为什么恰好查这六样？因为需求文档的失效模式就六种：写错了（正确性）、写漏了（完整性）、互相打架（一致性）、能有多种理解（二义性）、没法判对错（不可验证）、不知道为什么有这条（不可跟踪）。六查 = 失效模式清单，一条对应一种死法。
  • 费曼讲法：相亲简历六查：年龄学历别造假（正确）、别漏写婚史（完整）、前后别矛盾（一致）、「性格开朗」这种话要问清（二义）、承诺要能考证（可验证）、每句话有出处（可跟踪）。
  • 一通到底：为什么「快速响应」不合格而「P95≤2s」合格？「快速」每个人标准不同（二义）且无法判卷（不可验证）；「P95≤2s」唯一可判。改写二义句的套路 = 加量化指标 + 明确主体 + 明确边界条件——这就是评审改错题的标准答案生成器。
  • 考场回扣：改错题先标失效类型再改写；写「不可验证」时必须给出改写后的合格版本才算答满。

08 需求跟踪矩阵（req-p08）

  • 第一性拆解：需求从提出到上线要经过十几道工序，信息在传递中必然衰减。跟踪矩阵 = 全程记账：每条需求正向记「被我实现了吗」（防漏），反向记「这段代码为谁而写」（防多）。它解决的是规模化协作的根本问题——几十人几千条需求，靠记忆和口头必然丢。
  • 费曼讲法：装修记账本。正向：每笔预算都花了没（防漏花）；反向：这笔 8000 块是给谁家项目的（防乱花）。年底对账，一本账查两边。
  • 一通到底：为什么变更影响分析靠它？因为改一条需求前必须知道「它牵连哪些设计、代码、用例」——矩阵就是这个牵连关系的索引。为什么能查镀金（需求外的多余功能）？反向一查，没有需求认领的功能立刻现形。
  • 考场回扣：答「如何确保需求被完整实现」→ 正向跟踪；答「如何防止实现多余功能」→ 反向跟踪；答「变更前评估影响」→ 查矩阵定位牵连面。

09 需求变更控制 CCB（req-p09）

  • 第一性拆解：需求为什么必须控变？因为基线之后的随意改动会让前面所有验证作废——改一处的实际代价是重验整条链。CCB 流程五步（申请→评估影响→批准/拒绝→更新基线与矩阵→通知干系人）本质是一道把「口头随口改」降级为非法操作的行政法规：让改动的代价显式化、决策显式化、同步显式化。
  • 费曼讲法：已封版的书稿要改内容。不能直接在排版文件上乱改（改了别人不知道、校对全白做）——必须提交修改申请→主编评估影响多大→批不批→改完出新版→通知所有还在校对的人。口头一句「顺手改一下」就是事故之源。
  • 一通到底：为什么必须有 CCB 这个组织而不能开发自改？因为变更影响是全局的，只有跨职能委员会能看到全部代价（成本/进度/质量/风险四维评估）。为什么最后一步「通知干系人」不可省？不同步 = 别人还在按旧版工作 = 变更等于没控。
  • 考场回扣：诊断题看到「口头答应改需求」「开发直接改了」= 变更失控信号词，答五步流程 + 「基线后任何修改必须走 CCB」。

10 需求状态与基线（req-p10）

  • 第一性拆解：几百条需求在流水线上，怎么知道哪条走到哪了？状态机（建议→批准→实现→验证→完成/拒绝）给每条需求装上里程表；基线 = 通过正式评审后冻结的版本号——它是「从自由修改切换到受控变更」的分界线。状态管单条、基线管全局，合起来需求管理三件套（变更控制 + 状态跟踪 + 跟踪矩阵）就闭环了。
  • 费曼讲法：图书出版状态流：投稿→录用→排版中→校对完→上架（或退稿）。基线 =「下厂印刷」那一刻——印了之后要改，就得走勘误（变更）流程，不能直接改版。
  • 一通到底：为什么基线是分界线？基线前文档还是草稿，改了没人受影响；基线后它是合同，改动引发重验连锁——所以基线后的世界由 CCB（p09）统治、由矩阵（p08）记账。三件套互为因果：矩阵记账、基线定界、CCB 控变。
  • 考场回扣：问「需求管理包括什么」→ 三件套各一句；问「基线的含义」→ 正式评审通过并冻结、后续改动走变更控制。

必会 · 默写卡（M）

Web 篇（10 张）

  1. 前后端分离：后端只出数据 API（JSON），前端独立负责渲染与交互；收益：前后端并行开发、一套 API 多端复用；代价：首屏性能与 SEO（SSR 缓解）、接口契约管理。
  2. MVC vs MVP vs MVVM：判据=视图 V 与模型 M 是否直接对话。MVC：V 可直接读 M；MVP：V 与 M 完全隔离，Presenter 中介；MVVM：ViewModel 用双向绑定（观察者）自动同步 V——「双向绑定」只属于 MVVM。
  3. 负载均衡层次与策略：DNS（地理级）→ 反向代理（Nginx，应用入口）→ 应用集群 → 数据层（读写分离/分库）；策略：轮询、最少连接、源 IP 哈希（会话粘滞）、加权。
  4. REST 约束：资源由 URI 唯一标识、统一接口（GET/POST/PUT/DELETE）、无状态（请求自带全部上下文）、可缓存、分层系统。无状态≠不保存业务数据（是服务端不存会话状态）。
  5. 缓存三问题：穿透（查不存在的数据绕过缓存→布隆过滤器/空值缓存）、击穿（单个热点 key 过期瞬间高并发→互斥重建/逻辑过期/热点永不过期）、雪崩（大量 key 同时失效或缓存宕机→TTL 加随机错峰/多级缓存/缓存集群高可用）。判据三字诀：不存在=穿透，单个热点=击穿，一大片=雪崩。
  6. 会话与令牌：Session（状态存服务端，需粘滞或集中存储 Redis）；JWT（自包含签名令牌 Header.Payload.Signature，无状态适配分布式；缺点难吊销→短有效期+刷新令牌）。
  7. XSS 与 CSRF：XSS=向页面注入恶意脚本在用户浏览器执行→输出转义、CSP、HttpOnly Cookie；CSRF=借用户已登录身份伪造跨站请求→CSRF Token、SameSite Cookie、校验 Referer。
  8. API 网关：路由转发、统一鉴权、限流熔断入口、响应聚合、日志监控；限流三算法：计数器、漏桶（恒速）、令牌桶（允许突发）；业务逻辑不下放网关。
  9. 同步与异步：同步 RPC/HTTP（实时强一致、耦合高）；异步消息队列（解耦、削峰、最终一致，须幂等消费）；选型：主交易链路→同步，旁路动作（通知/积分/日志）与峰值缓冲→异步。
  10. 单体到微服务演进判据：单体适合小团队快交付低复杂度；演进信号：模块耦合发布互相拖累、局部热点需独立扩展、团队并行受限；路径：先模块化单体解耦→按业务边界（限界上下文）拆→独立部署，反对一步到位。

微服务篇（9 张）

  1. 微服务特征与 SOA 对比：四字诀「小（单一职责按业务拆）、独（独立进程独立部署）、轻（轻量通信 REST/消息）、去（去中心化治理与数据）」；SOA=ESB 集中智能总线，微服务=去中心化、管道保持笨。
  2. 拆分原则与粒度：按业务能力/限界上下文拆（不按技术层拆）；数据库随服务走；粒度以一个小团队（两个披萨）可独立开发部署运维为准；按技术层拆=分布式单体（最差结局）。
  3. 注册与发现：注册中心（Nacos/Consul/Eureka）：服务启动注册元数据→消费者查询实例列表→心跳健康检查自动剔除故障实例；客户端发现（消费者自行负载均衡）vs 服务端发现（中间负载均衡器选）。
  4. 通信与事件驱动三部件：同步 REST（通用）/gRPC（内部高性能二进制）；异步消息队列（解耦削峰）；事件驱动架构：事件源（产生并声明事件）→事件管理器（事件队列/绑定表，登记与派遣）→事件处理器（注册处理过程，事件触发时被调用）；口诀「源-管-理」（2020上案例五真题考部件名）。
  5. 治理四保护：限流（入口过载，令牌桶允许突发）、熔断（依赖故障快速失败，断路器三态：关闭→打开→半开试探恢复）、降级（保核心弃边缘返回兜底数据）、灰度（按比例放量，秒级回滚）。
  6. 可观测三支柱：日志（集中聚合检索，ELK）、指标（时序监控告警，Prometheus）、链路追踪（全局 TraceId 串起跨服务调用链，定位慢点与故障环）；「一次下单慢在哪」→链路追踪。
  7. 配置中心与容器编排：配置中心（集中配置动态下发不重启生效——限流阈值/灰度开关热更新）；容器（Docker 镜像保证环境一致性）；K8s 三大能力：滚动更新、自愈、弹性伸缩（HPA）。
  8. 每服务一库（数据自治）：每个微服务独占自己的库；跨服务取数只走对方 API 或订阅事件，禁直连他库；代价：跨库 JOIN 消失→字段级冗余/事件最终同步/聚合服务。
  9. 最终一致 Saga 与 TCC：Saga=本地事务序列+失败时补偿事务（逆向回滚，补偿须幂等）；TCC=Try 预留→Confirm 提交→Cancel 释放（应用层两阶段，不锁数据库资源）；判据：资金强一致→TCC/2PC；高并发允许秒级不一致→Saga/消息最终一致。

逐点讲透 · 一通到底（编号 = /track 知识点 id，先懂后背）

Web 篇（web-p01~p10）

01 前后端分离（web-p01）

  • 第一性拆解：不分离的老架构（JSP/模板渲染）里，HTML 是后端字符串拼出来的——改一个按钮样式要重发整个应用。分离的物理动因：终端变多了（App、小程序、PC 各要一套界面），后端不可能为每种终端拼一次页面。把「数据」和「界面」切开，后端只出 API，每种终端各养各的界面——一次开发，多端复用。代价也随之而来：首屏要等 JS、搜索引擎爬不到数据（SEO）、接口契约要管理。
  • 费曼讲法：中央厨房（后端）只管做标准化半成品（JSON 数据），门店（前端）自己摆盘——学校店、商场店、机场店（Web/小程序/App）各自装修，厨房不用改灶台。代价：外卖包装盒（首屏加载）要自己解决。
  • 一通到底：为什么「一套 API 多端复用」是第一收益？因为数据的生产成本不变，界面的形态在膨胀——切开让膨胀不传导回生产端。为什么 SSR（服务端渲染）能缓解 SEO？因为爬虫只认现成 HTML，SSR 就是厨房替门店把摆盘先做了。
  • 考场回扣：论证题按「收益（并行开发/多端复用）+ 代价（首屏/SEO/契约）+ 缓解（SSR/接口文档）」三段答。

02 MVC vs MVP vs MVVM（web-p02）

  • 第一性拆解：三个架构只回答一个问题——视图（V）和模型（M，数据/业务）要不要直接认识对方。直接认识 = MVC（简单但视图与数据耦合）；彻底隔离靠中间人翻译 = MVP（解耦但中间人写大量胶水代码）；让中间人变成「自动同步器」= MVVM（双向绑定，声明一次自动同步）。演进方向就是把人肉同步换成机制同步。
  • 费曼讲法：三对情侣沟通方式。MVC：两人在一个屋直接说话（快但吵架互相拖累）；MVP：中间架个传话人（隔离彻底，传话人累死）；MVVM：装一部联动电话，一边改另一边自动响（双向绑定）——联动电话就是 ViewModel 的观察者机制。
  • 一通到底：为什么「双向绑定」是 MVVM 的独有指纹？因为 MVC/MVP 里数据变了要有人手动刷新视图——只有 MVVM 把「谁变了通知谁」做成了框架机制（观察者）。考题给特征问模式，抓这条判据就够：V 与 M 是否直接对话 / 是否有自动同步机制。
  • 考场回扣：判据一句话——V 可读 M = MVC；完全隔离靠 Presenter = MVP；双向绑定 = MVVM。

03 负载均衡层次与策略（web-p03）

  • 第一性拆解：一台服务器有物理上限（CPU/连接数），扩容只有两条路：买更好的机器（垂直，贵且有顶）或上多台（水平，便宜但要有人「分活」）。负载均衡就是分活的制度——而且分活发生在每一层：域名单独扛地理级、Nginx 扛应用入口、数据库还要读写分离。策略（轮询/最少连接/IP 哈希/加权）只是同一制度下的不同分法。
  • 费曼讲法：银行大厅。大堂经理（反向代理）把客户往空闲窗口引（最少连接）；普通排队叫号（轮询）；老客户固定找熟悉他的客户经理（IP 哈希，会话粘滞）；VIP 通道插队（加权）。总行按城市分流量（DNS）。
  • 一通到底：为什么「IP 哈希」能做会话粘滞？因为同一 IP 恒定落在同一台机器，Session 就不用搬家——这直接连通 p06（会话与令牌：粘滞是 Session 的补偿手段）。为什么分层分？因为不同层的瓶颈不同，单点分不动全局。
  • 考场回扣：问「如何支撑高并发」→ 层次（DNS→反代→应用集群→数据层）+ 按场景挑策略各配一句理由。

04 REST 约束（web-p04）

  • 第一性拆解：REST 的每条约束都是为「互联网级别的规模化」付出的纪律：资源唯一标识（URI）让任何请求可寻址；统一接口（GET/POST/PUT/DELETE）让所有人不用读文档就会用；无状态让任何一台服务器都能处理任何请求——水平扩展的前提；可缓存让重复请求不出网；分层让中间设施可插入。无状态是其中最常考的一条，也是最容易误解的一条。
  • 费曼讲法：无状态 ≠ 失忆。餐厅服务员不记你上次点了什么（无状态），但每张菜单你把桌号、菜名、忌口全写在单子上（请求自带全部上下文）——换任何服务员都能立刻上菜。这就是为什么能随便加人手（扩容）。
  • 一通到底：为什么无状态支撑水平扩展？会话状态存在服务端内存里，就等于把请求「锁」在某台机器上——负载均衡没法自由分发（连接 p03 的粘滞问题）。所以分布式系统的第一课都是「把状态赶出服务进程」：要么客户端带（JWT），要么集中放（Redis）——这正是 p06 的两种方案。
  • 考场回扣：问「REST 有哪些约束」→ 五条各一短句；追问「无状态的含义」→ 服务端不存会话状态，≠ 不保存业务数据。

05 缓存三问题（web-p05）

  • 第一性拆解：缓存为什么有效？因为访问有热点、磁盘比内存慢几个数量级。但它天然带来新矛盾：缓存里的数据可能不存在/过期/集体失效。三种故障对应三种物理事件：穿透 = 查一个根本不存在的 key，缓存永远挡不住（每次都穿到数据库）；击穿 = 一个超级热点恰好过期，瞬间全部流量砸库；雪崩 = 大批 key 同一时刻过期或缓存整体宕机。三个词的边界就是「不存在 / 单个热点 / 一大片」。
  • 费曼讲法：前台挡问询。有人问一个根本不存在的部门（穿透）——前台必须记住「没这个部门，别再往里跑了」（空值缓存/布隆过滤器）；明星员工突然请假（击穿）——指定一人先顶上别让全员都冲办公室（互斥重建）；整层楼集体断电（雪崩）——排班错开假期（TTL 加随机）+ 备用楼层（多级缓存/集群）。
  • 一通到底：为什么对策一一对应？因为故障机理不同：穿透是「负结果没缓存」→ 缓存负结果或提前拦截；击穿是「单点失效瞬间放大」→ 只放一个人去重建；雪崩是「失效时间相关」→ 打散失效时间 + 冗余。对策是机理的逆操作，理解机理就不必背对策。
  • 考场回扣：诊断题抓三字诀对号——不存在=穿透（布隆/空值），单热点=击穿（互斥重建），一大片=雪崩（TTL 错峰/多级/集群）。

06 会话与令牌（web-p06）

  • 第一性拆解：HTTP 本身无状态（p04），但业务需要「认得你是谁」。两种物理方案：Session = 状态存服务端，发个号牌（SessionID）给浏览器——问题是多台服务器时号牌只在一台有效（要粘滞或集中存 Redis）；JWT = 把身份信息签名后直接发给用户携带——服务器不存任何东西，验签即可，天然适配分布式，代价是签发后无法收回（难吊销）。
  • 费曼讲法：游乐园。Session = 手环 + 闸机登记本（登记本只在总台，分园要打电话核对或复印登记本=集中存储）；JWT = 塑封的通票，写着「张三，身高够，有效期到 17:00」加防伪章（签名）——任何闸机自己验章就放行，但票发出去了收不回，只能让它短时效 + 到期续票（刷新令牌）。
  • 一通到底：为什么 JWT 难吊销？因为验证不查库（这正是它快的理由）——吊销就得查库，自相矛盾。所以标准解是「短有效期 + 刷新令牌」：让坏票自然过期。为什么分布式首选 JWT？因为无状态与 p04 的 REST 无状态是同一个原则：状态赶出服务进程。
  • 考场回扣：选型题抓判据——单体/需强控会话→Session（配 Redis 集中存）；分布式/无状态扩展→JWT（配短时效+刷新令牌防吊销）。

07 XSS 与 CSRF（web-p07）

  • 第一性拆解：Web 安全的两类经典攻击，差别在攻击面完全不同：XSS 攻击「你的浏览器」——把恶意脚本注入页面，在你的浏览器里执行（偷 Cookie、改页面）；CSRF 攻击「你对其他站的登录态」——不偷不破，只是借你已登录的身份，诱导你的浏览器替攻击者发一个带 Cookie 的请求。一个要注入代码（防转义/防执行），一个只借身份（防「请求带了我的 Cookie 却不是我的本意」）。
  • 费曼讲法：XSS = 有人往公告栏贴了一张假通知，落款是物业，住户看了照做（注入+执行）；CSRF = 骗子不碰你家门锁，只是穿着你常去银行的衣服替你喊了一嗓子「转账」，银行一听声音（Cookie）是你，就照办（借身份发请求）。
  • 一通到底：为什么对策一一对应？XSS 的命门在「脚本被当正文执行」→ 输出转义（脚本变文本）、CSP（白名单禁外域脚本）、HttpOnly（JS 读不到 Cookie，偷无可偷）；CSRF 的命门在「请求不带本意证明」→ 每次会话发个随机 Token 要求带回（骗子拿不到 Token）、SameSite（跨站不带 Cookie，声音对不上）、校验 Referer（查来电归属）。
  • 考场回扣：判据——注入脚本在浏览器执行 = XSS（防转义/CSP/HttpOnly）；借登录态伪造请求 = CSRF（Token/SameSite/Referer）。别把两者对策写串。

08 API 网关（web-p08）

  • 第一性拆解：服务一多，每个服务都要做鉴权、限流、日志——同一件事写 N 遍必然漂移。网关的本质是把「进门手续」从各家业务里抽出来统一办：路由转发、统一鉴权、限流熔断入口、响应聚合、日志监控。但有一条铁律：业务逻辑不下放网关——因为网关是全局单点，业务进去就把「变化最快的部分」锁死在「最难改的地方」。
  • 费曼讲法：小区门卫室。查出入证（鉴权）、高峰限流放行（限流）、登记访客（日志）、帮你确认 3 号楼还是 5 号楼（路由）——但门卫不帮你搬家（业务逻辑），搬家公司才是干活的。
  • 一通到底：为什么限流算法网关必备？因为网关是所有流量的漏斗口，过载保护在入口做最便宜（连通 mic-p05 四保护：限流管「太多」）。为什么计数器/漏桶/令牌桶三选一按场景？计数器简单但临界突刺；漏桶恒速整形；令牌桶容忍突发——业务高峰有波动的互联网场景几乎总选令牌桶。
  • 考场回扣：答「网关职能」→ 五职能各一短语 + 一句「业务逻辑不下放」；选限流算法给场景配理由（要容忍突发→令牌桶）。

09 同步与异步（web-p09）

  • 第一性拆解：一次调用的两个维度被混在一起谈，拆开看：等待关系（调用方要不要挂起等结果）和耦合关系（两边要不要同时在线）。同步（HTTP/RPC）= 必须等 + 必须同时在线，换来即时结果与简单逻辑；异步（消息队列）= 发完就走 + 各自在线各自处理，换来解耦、削峰、可重试，代价是结果延迟（最终一致）与消费要幂等。
  • 费曼讲法：同步 = 打电话办社保（对方不接你只能等着）；异步 = 寄挂号信（投进信箱就走，对方晚点处理，信箱高峰期也不堵你家门）。挂号信的回执 = 消息确认；防止对方重复办两遍 = 幂等（同一封信别办两次事）。
  • 一通到底：为什么主交易链路用同步、旁路用异步？主链路（下单扣款）要即时结果决定下一步；旁路（通知/积分/日志）晚几秒无感却占了主链路的等待预算——把旁路从主链路摘出去，就是异步的全部意义。为什么必须幂等？网络重试必然造成消息重复投递，不幂等 = 重复扣款。
  • 考场回扣：论证题给动作分类（下单/扣款→同步；短信通知/积分→异步 MQ + 幂等消费），各配一句「延迟可接受/需即时结果」。

10 单体到微服务演进判据（web-p10）

  • 第一性拆解：微服务不是更先进，是另一种代价结构：单体用「部署简单/事务容易/调试直观」换「局部修改全局重发/模块只能整体扩容」；微服务反过来。所以什么时候该拆？当且仅当「耦合的痛」超过「分布式的痛」——模块互相拖累发布、局部热点要独立扩容、团队并行互相阻塞。三个信号全是痛感证据，不是技术潮流。
  • 费曼讲法：大排档到美食广场。几个兄弟合伙（单体）最灵活，但生意火了——卖面的一改菜单全档口重新开业（整体部署），冷饮排队挡住炒菜（局部热点）；拆成独立档口（微服务）各开各的、各自排号（独立扩容），但客人要点三趟单（跨服务调用），账要月底并（分布式事务）。
  • 一通到底：为什么演进路径是「先模块化单体→按边界拆→独立部署」而不是一步到位？因为拆分的依据（业务边界/限界上下文）本身要在模块化中才能摸清——没边界知识就硬拆 = 拆出一堆互相调用的小单体（最差结局，连通 mic-p02）。先分好家再分家产，不能先分家产。
  • 考场回扣：论证题不答「微服务好」，答「演进信号是否出现」：①耦合拖累发布②热点需独立扩展③团队并行受限——出现则拆，并给「模块化先行」的路径。

微服务篇（mic-p01~p09）

11 微服务特征与 SOA 对比（mic-p01）

  • 第一性拆解：SOA 和微服务都是「拆」，差别在智能放在哪。SOA 时代（ESB 总线）：把协议转换、消息路由、编排逻辑都塞进总线——总线越来越聪明，成了新上帝（单点+瓶颈）。微服务反其道：「把智能放进服务，管道保持笨」——通信管道只做裸传输（HTTP/消息），治理逻辑（注册、发现、熔断）下沉到服务自身和基础设施。四字诀「小独轻去」就是这个反叛的纲领。
  • 费曼讲法：SOA = 所有快递都经一个超级分拨中心，分拨中心还会替你改地址、拆包裹、贴新单（集中智能）——它一堵全国电商瘫痪。微服务 = 快递直发 + 各家自建物流部（去中心化），高速公路（管道）只管通车不管货。
  • 一通到底：为什么「去中心化」能 scalable？因为中心化的智能是全系统唯一的大脑，规模越大越堵、挂了全停；分布式智能让每个服务自治，故障与流量都被隔离在局部。这连通 mic-p03（注册中心也是要高可用的组件，不是业务中枢）。
  • 考场回扣：对比题一表三行——智能位置（ESB 集中 vs 服务自治）、通信（重协议 SOAP vs 轻量 REST/消息）、数据（共享库 vs 每服务一库）。

12 拆分原则与粒度（mic-p02）

  • 第一性拆解：拆分的唯一正确依据是业务边界（限界上下文），因为业务边界内的数据和语言天然内聚、变化频率一致——按它切，服务间接口稳定；按技术层切（前端一个服务、后端一个服务、DBA 一个服务）看起来工整，实际每次改需求都要跨所有服务联动——这就是「分布式单体」：拆了服务没拆耦合，还白付了分布式税。粒度判据 = 两个披萨团队可独立开发部署运维。
  • 费曼讲法：公司按「业务部门」分（销售部/财务部）还是按「工种」分（所有写 PPT 的一个部、所有打字的 一个部）？按业务分，一个部门能独立把事办完；按工种分，办一件小事要三个部门跑流程——后者就是分布式单体。
  • 一通到底：为什么「数据库随服务走」是拆分的硬指标？服务可以共享代码库但共享一个数据库 = 数据层还是耦合的——别人的表结构一改你就崩。所以「每服务一库」（连通 mic-p08）是拆分真正的分界线。
  • 考场回扣：诊断题看到「按技术层拆」「服务共享数据库」= 反模式信号词；答「按限界上下文拆 + 数据库随服务走 + 两披萨粒度」。

13 注册与发现（mic-p03）

  • 第一性拆解：服务实例「生灭无常」（扩容、宕机、滚动更新），调用方不可能写死地址——就像人不可能背下所有人的电话。注册中心 = 电话簿 + 活人确认机制：服务启动时登记（注册），调用方查簿拨号（发现），定期「你还在吗」（心跳）自动把死号划掉（健康检查剔除）。发现模式两种：客户端拿全表自己选（客户端发现，调用方智能）vs 中间负载均衡器代选（服务端发现，簿子智能）。
  • 费曼讲法：外卖平台骑手调度。骑手上线就「接单中」（注册），平台随时知道每个骑手在哪（发现），骑手断线 30 秒系统自动停派单（心跳剔除）——顾客不用自己记住骑手电话。
  • 一通到底：为什么心跳必须有？因为「下线」这个事件经常没有告别（宕机是静默的）——主动登记不可靠，必须靠周期性确认兜底。为什么注册中心本身要集群化？它是全局依赖，单点 = 所有服务的电话簿一起烧（连通 mic-p01 去中心化：连「电话簿」都不许成为上帝）。
  • 考场回扣：答「服务实例动态变化如何调用」→ 注册中心三机制（注册/发现/心跳剔除）+ 两种发现模式挑一个说理由。

14 通信与事件驱动三部件（mic-p04）

  • 第一性拆解：服务间通信选型回到 p09 的同一对矛盾：同步（REST/gRPC）要即时结果、异步（消息/事件）要解耦削峰。事件驱动是异步的架构化形态，固定三部件：事件源（状态变了就声明事实「订单已支付」，不关心谁听）→ 事件管理器（队列/绑定表，负责登记、路由、派遣）→ 事件处理器（订阅感兴趣的事件，被触发时执行）。本质是「发布事实」取代「调用动作」——发布方与响应方彻底解耦。
  • 费曼讲法：外卖平台广播。「商家出餐了」（源）→ 平台派单系统登记并派出（管理器）→ 骑手 App 响应接单（处理器）。商家只管广播事实，不用认识任何一个骑手。口诀「源-管-理」（2020 上案例五真题原题问部件名）。
  • 一通到底：为什么事件驱动比直接调用解耦更彻底？调用 =「我点名要你做事」（发布方依赖响应方存在）；事件 =「我宣布事实，谁需要谁自理」（发布方连谁在听都不知道）——新增响应方（加个短信通知）零改动发布方。这就是「开闭原则」在分布式上的化身。
  • 考场回扣：填部件名题背死「事件源/事件管理器/事件处理器」+ 口诀源-管-理；论证题「新增多种下游处理零改动」→ 事件驱动 + 三部件各一句。

15 治理四保护（mic-p05）

  • 第一性拆解：分布式系统的故障是常态不是意外（机器会坏、网络会抖、流量会尖峰）。四保护是四种不同故障的四种对位药：限流管「请求太多」（入口拒绝超额，保护自己）；熔断管「依赖坏了」（快速失败不再傻等，保护自己不被拖死）；降级管「资源不够时舍什么」（保核心弃边缘，是熔断/过载后的自救策略）；灰度管「新版本有风险」（小比例验证，出事秒回滚）。四者管四种病，不可互相替代。
  • 费曼讲法：防洪体系。限流 = 水闸（来水超量就关小）；熔断 = 保险丝（下游电器短路就断开，不让整屋烧）；降级 = 停掉花园洒水保厨房用水（舍边缘保核心）；灰度 = 新换的水管先只接厨房试一周（出问题只淹厨房）。
  • 一通到底：为什么熔断器是三态（关闭→打开→半开）？因为「坏没好」只能试探得知：打开期间定期放一个请求去探（半开），成功才恢复（关闭）——自动恢复必须靠低成本试探，这和心跳（mic-p03）是同一哲学：静默的世界只能靠周期性确认。
  • 考场回扣：判据背死——限流管「太多」、熔断管「坏了」、降级是「舍什么」、灰度管「发布风险」；给故障场景挑对位保护并各配一句。

16 可观测三支柱（mic-p06）

  • 第一性拆解：几十个服务接力完成一次请求，出问题必答三问：「哪里错了」（日志）、「整体健康度如何」（指标——趋势、告警、容量）、「这次慢/错在哪一环」（链路追踪）。三支柱对应三种信息形态：离散事件（日志）、聚合时序（指标）、单次全路径（追踪）——少一支柱就有一类问题变成盲区。
  • 费曼讲法：医院三件套。病历本（日志：逐条记录发生了什么）；体检表/体温曲线（指标：总体健康度与趋势）；这次就诊的全程导诊单（追踪：挂号→验血→B 超→复诊哪一步卡了两小时）。一次「下单慢在哪」只有导诊单（TraceId）能答。
  • 一通到底：为什么跨服务必须「全局 TraceId」？每个服务只看到自己一段，没有统一编号串不起全程——诊断「慢」必须把 12 段接力时间拼成一条时间线，才能定位最慢一环。为什么指标不能替代日志？指标是聚合值（平均/分位），丢了个案细节；日志有个案但没有「趋势视野」。
  • 考场回扣：三支柱对三问——错了查日志（ELK 集中检索）、健康度看指标（Prometheus 告警）、慢在哪用链路追踪（TraceId 串全程）。

17 配置中心与容器编排（mic-p07）

  • 第一性拆解：几十个服务 × 多环境（测试/预发/生产）= 配置爆炸，而微服务最常用的动作「改限流阈值、切灰度开关」必须不重启生效——配置中心 = 把配置从代码里抽出来集中管理 + 动态推送。容器解决另一个根源问题：「在我机器上是好的」= 环境不一致——镜像把应用和依赖整体打包，处处一致。K8s 在容器之上再回答「几十个容器谁来管」：滚动更新（不停机换版）、自愈（挂了自动拉起）、弹性伸缩（HPA 按负载加减实例）。
  • 费曼讲法：配置中心 = 总台的音响控制台（调音量不用挨个房间拆音箱）。容器 = 整机装箱（连家具带说明书打包，搬到哪个城市都原样复现）。K8s = 物业总控（哪家断电自动修、装修不停水换新、人多了自动加开班车）。
  • 一通到底：为什么「动态下发不重启」是刚需？因为治理动作（限流阈值、灰度比例）是分钟级要调的运营参数，重启 = 服务闪断，等于用保护动作制造故障。为什么容器镜像能终结「环境不一致」？因为它把「环境」本身也打包了——不一致的根源（各机器依赖不同）被整体冻结。
  • 考场回扣：答「如何管理多环境配置」→ 集中存储/环境隔离/动态下发不重启；答「K8s 能力」→ 滚动更新/自愈/HPA 三件套各一句。

18 每服务一库（mic-p08）

  • 第一性拆解：服务拆了、库还共享 = 数据层耦合未断（mic-p02 的硬指标）。每服务独占一库后，出现新物理现实：跨库 JOIN 消失了、跨库事务没有了。取数只剩两条合法通道：走对方 API（同步拼装）或订阅对方事件在本地留副本（最终同步）；一致性让位给最终一致（连通 mic-p09）。这是微服务为自治付的最大税，也是所有分布式数据问题的源头。
  • 费曼讲法：几家合租（共享库）→ 分家各住（每服务一库）。原来一个客厅共用不用问（JOIN），现在要朋友家的东西只能打电话去借（API）或他寄一份给你存着（事件同步副本）——寄到的可能是昨天的（最终一致）。
  • 一通到底：为什么宁可付税也要自治？因为共享库意味着任何一家改表结构全家崩、任何一家慢查询全家慢——数据层耦合是最深的耦合，服务层拆得再开也白拆。字段冗余（订单存下单时的商品名）为什么正当？跨服务实时取历史快照既慢又可能已被改——冗余换来了不可变性。
  • 考场回扣：答「微服务间如何取数」→ API 调用或事件订阅留本地副本，禁直连他库；问「为什么订单存冗余字段」→ 快照不可变 + 避免跨服务实时查询。

19 最终一致 Saga 与 TCC（mic-p09）

  • 第一性拆解：每服务一库后，跨服务写操作没有数据库事务可用了。两条人造补偿路线：Saga = 把大事务拆成本地事务序列，每步成功推进，某步失败则倒放补偿事务逐步逆向抵消（本质：用「撤销键」替代「回滚键」）；TCC = 每个参与者实现 Try（预留资源）→ Confirm（真扣）/ Cancel（释放），在业务层预演两阶段提交——资源不锁死，锁的是「额度」。判据：资金类强一致 → 2PC/TCC；高并发容忍秒级延迟差 → Saga/消息最终一致。
  • 费曼讲法：订「机票+酒店+租车」打包行程。Saga = 逐个下单，订租车失败就逐个退：先退酒店再退机票（补偿倒放）；TCC = 先让三家都占住名额不扣款（Try），三家都占住才统一扣款（Confirm），有一家占不住就全部释放（Cancel）。占住不扣 = 锁额度不锁库存。
  • 一通到底：为什么 Saga 的补偿必须幂等且能接受「中间态可见」？Saga 过程中外部能看到「机票订了酒店没订」的中间状态（不像数据库回滚那样无人知晓）——设计时就要让中间态无害。为什么 TCC 比 2PC 在高并发下更好用？2PC 锁数据库资源同步阻塞（等全员投票）；TCC 锁业务额度、失败即刻释放，不占数据库连接干等。
  • 考场回扣：选型一句话——资金强一致 → TCC/2PC；高并发可容忍最终一致 → Saga/消息补偿；答 Saga 必带「补偿事务 + 幂等」两个词。

必会 · 默写卡（M）

  1. 三级模式两级映像：外模式/概念模式/内模式；外-概念映像（逻辑独立性）、概念-内映像（物理独立性）。
  2. ER 建模与联系转化：实体（矩形）/属性（椭圆）/联系（菱形）1:1/1:N/M:N；转关系模式：1:N 联系并入 N 端加外键；M:N 联系必须单独建关系模式（两端主键+联系自身属性）；1:1 并入任意一端。
  3. 范式判定：1NF 属性原子不可再分；2NF 消除非主属性对码的部分函数依赖（联合主码场景高发）；3NF 消除传递依赖；BCNF 每个决定因素都包含码。口诀：部分依赖→2NF，传递依赖→3NF。
  4. 反范式设计：有意引入冗余（冗余列/派生列/历史快照）换查询性能；代价：冗余一致性维护；适用：读多写少、JOIN 代价高、报表统计；快照式冗余（订单存下单时商品名与单价）最正当。
  5. 视图与索引：视图=虚表，只存「定义」不存数据；作用：简化查询、行列级权限、逻辑独立性。索引 B+ 树有序→等值/范围快；代价：写放大+空间；联合索引最左前缀。
  6. 事务 ACID：原子性（全做或全不做，undo）、一致性（约束不被破坏，是目的）、隔离性（并发互不干扰，锁+MVCC）、持久性（提交即落盘，redo/WAL）。
  7. 并发问题与隔离级别：脏读（读未提交）、不可重复读（同行值变——他人 update 提交）、幻读（行数变——他人 insert/delete）；级别：读未提交＜读已提交＜可重复读（MySQL 默认）＜串行化。
  8. 封锁协议与死锁：两段锁 2PL（先全部加锁再统一解锁）保证可串行化调度但不防死锁；死锁四条件：互斥、占有且等待、不可剥夺、循环等待；预防：一次封锁法/顺序封锁法；DBMS 检测+牺牲最年轻事务。
  9. 分布式事务 2PC/TCC：2PC 两阶段：准备（投票）+提交，强一致；缺陷：同步阻塞、协调者单点、资源锁定长；TCC=Try 预留/Confirm 提交/Cancel 释放（应用层两阶段不锁库）；判据：资金强一致→2PC/TCC，高并发容忍秒级不一致→消息最终一致。
  10. CAP 与 BASE、分库分表：CAP：分区容错 P 为网络必然（必选），实际在 C 与 A 权衡（CP=ZooKeeper 宁停不错；AP=Eureka 保可用返回略旧）；BASE=基本可用、软状态、最终一致。拆分：先垂直按业务拆库，单表过大再水平按行分片（哈希/范围）；分片键选查询最高频且分布均匀列；读写分离主写从读，复制延迟→强一致读强制读主库。

逐点讲透 · 一通到底（编号 = /track 知识点 id，先懂后背）

01 三级模式两级映像（db-p01）

  • 第一性拆解：数据库要同时伺候三种眼光的人：用户只关心自己的视图（外模式）、设计者管全局逻辑结构（概念模式）、DBA 管磁盘上的物理存放（内模式）。三层若焊死，任何一层改动都殃及全体——映像就是层间的「转换插头」：外-概念映像换插头不动磁盘（逻辑独立性）、概念-内映像换磁盘布局不动程序（物理独立性）。这是「分层解耦」（Web 篇 p02 同款思想）在数据库的最早实践。
  • 费曼讲法：公司组织。员工手册（外模式：每个岗位看到自己那部分）、组织架构图（概念模式：全局逻辑）、工位与办公设备的实际摆放（内模式：物理实现）。工位重新摆放（换硬盘/调索引）不用改组织架构图（物理独立性）；部门合并改名（逻辑调整）员工手册翻译一下就行（逻辑独立性）。
  • 一通到底：为什么「物理独立性」值钱？存储技术几十年换了 N 代（B 树→SSD→列存），应用层代码一行没改——因为程序只面向概念模式编程。为什么视图能提供安全隔离（连通 p05）？因为外模式本来就只暴露局部——用户看不到的东西等于不存在。
  • 考场回扣：背死两层映射的方向——外-概念=逻辑独立性、概念-内=物理独立性；论证「存储结构变化不影响应用」答物理独立性。

02 ER 建模与联系转化（db-p02）

  • 第一性拆解：建库第一步是把现实抽象成模型：实体（矩形，独立的「东西」）、属性（椭圆，描述）、联系（菱形，实体间的关系），联系要标基数（1:1 / 1:N / M:N）。落到关系模式（表）时，基数决定外键放哪：1:N 并入 N 端（联系天然属于「多」的一方）；M:N 必须单独建表（因为它既不属于任何一方——一个订单既不属于用户也不属于商品，它是独立的「事实」）；1:1 任意并一端。
  • 费曼讲法：租房登记。一个房东对多套房（1:N）：租约信息记在「房」的档案里（N 端），因为每套房只对应一份现租约；「学生选课」（M:N）：一个学生选多门课、一门课多个学生——选课这个「事实」得单开一张表，两边主键都抄进来，还要记成绩这个「联系自己的属性」。
  • 一通到底：为什么 M:N 不能并入任何一端？并入学生表则一个学生对应多门课变成一格塞多个值（违反原子性，1NF 都过不了）；并入课程表同理。「联系自身有属性」是 M:N 单独建表的铁证——成绩记在哪端都放不下。为什么 1:N 并 N 端不单独建表？因为 N 端每条记录本来就只关联一个 1 端对象，外键一列就表达了全部信息，单独建表是纯冗余。
  • 考场回扣：转化判据死背——1:1 并任一端、1:N 并 N 端加外键、M:N 单独建关系模式（两端主键+联系属性）；M:N 是高频扣分点。

03 范式判定（db-p03）

  • 第一性拆解：范式是「消除冗余引发的异常」的三级阶梯。冗余会造成三种异常：改一处漏一处（更新异常）、该删的删不干净（删除异常）、没数据就没处放（插入异常）。2NF 消除「部分依赖」（非主属性只依赖联合主码的一半——半冗余）；3NF 消除「传递依赖」（非主属性 A 决定 B，B 又依赖码——间接冗余）；BCNF 收紧到「每个决定因素都含码」。每一级都是对「依赖必须直来直去依赖整码」的进一步收紧。
  • 费曼讲法：通讯录混乱的典型：「学号+课号→成绩」没问题（2NF 过），但表里又存「学号→学生住址」——住址只依赖一半主码（部分依赖，卡 2NF）；再存「院系名→院系电话」，而院系电话跟着「学号→院系名→院系电话」拐弯依赖（传递依赖，卡 3NF）。每一级都是把「拐弯的依赖」拉直、拆表。
  • 一通到底：为什么判范式从「函数依赖」下手而不是看表长什么样？范式本来就是依赖结构的分类——判定三步法：属性可再分吗（1NF）→ 有非主属性只依赖半张主码吗（2NF）→ 有 A→B→码 的传递链吗（3NF）。考试判定题就是这三问的快问快答。
  • 考场回扣：口诀——部分依赖卡 2NF、传递依赖卡 3NF；规范化路径答「拆出依赖的属性组单建表、原处留键」。

04 反范式设计（db-p04）

  • 第一性拆解：范式追求「无冗余」，但无冗余 = 查询时到处 JOIN = 慢。反范式是清醒的违法：故意引入冗余（冗余列/派生列/历史快照）换取读性能——前提是明确付代价（写时要同步多处、有一致性风险）。它是「空间换时间」在数据层的版本，与 Web 缓存（web-p05）是同一哲学：读多写少的场景，把准备成本前置。
  • 费曼讲法：订单里存「下单时的商品名和单价」。商品后来改名、调价，订单必须显示当时的样子——这不是疏忽，是快照：历史事实不可变，冗余在这里最正当。报价单里手抄当天汇率也是同理。
  • 一通到底：为什么「读多写少」是反范式的前提？冗余的税在写时征（改一处要同步 N 处），收益在读写省 JOIN——写多读少时代税超过收益，账是亏的。为什么「派生列」（存总价而不存明细算价）要慎用？派生值可能与新明细不一致——除非业务接受容忍或加触发器维护。
  • 考场回扣：论证题按「读多写少场景 + 冗余/快照类型 + 一致性维护代价说明」三段答；历史快照是最稳的答案。

05 视图与索引（db-p05）

  • 第一性拆解：视图 = 只存「定义」不存数据的虚表——它存在的三个理由全是同一原理（p01 外模式）的应用：简化（常用复杂查询起个名）、权限（只暴露行列的局部，看不到=不存在）、逻辑独立性（底层改结构，视图翻译保住上层程序）。索引 = 额外维护一份有序查找结构（B+ 树）——用写时的额外维护 + 空间，换读时的 O(logN)，又是一次空间换时间。
  • 费曼讲法：视图 = 餐厅「今日套餐」页——菜单（基表）没变，按场景挑几道装订成册；撤了套餐页不影响后厨。索引 = 书后面的关键词索引页——查「范式」不用翻 300 页，翻索引直接到页码；代价是正文每改版，索引页都要重排（写放大）。
  • 一通到底：为什么 B+ 树又快又适合数据库？节点只存键不存数据→一页内存能放更多键→树更矮→磁盘 IO 次数更少（数据库的命是 IO）；叶子节点串成链表→范围查询顺着扫。为什么联合索引有「最左前缀」？B+ 树先按第一列排、再按第二列排——跳过第一列查第二列 = 在排好序的电话簿里直接按名字找，没序可依只能全扫。
  • 考场回扣：答「视图作用」→ 简化/权限/逻辑独立性 + 一句「虚表不存数据」；答「索引代价」→ 写放大 + 空间，查询列和高选择性列才建。

06 事务 ACID（db-p06）

  • 第一性拆解：多人同时用同一个库，必须有「操作不可分割」的保证，否则转账扣了一半断电就是灾难。ACID 四条各守一道防线：原子性（全做或全不做——undo 日志回滚）；一致性（约束不被破坏——它是前三条共同服务的目的）；隔离性（并发事务互不干扰——锁 + MVCC，连通 p07/p08）；持久性（提交即落盘——redo 日志/WAL 先写日志再写数据）。
  • 费曼讲法：转账 500 元 =「扣我 500」+「加你 500」两步。原子性 = 要么两步都完成要么都装没发生（绝不允许钱凭空消失在中间态）；一致性 = 账目总额守恒、约束不破；隔离性 = 别人在你转账时查余额不能看到半完成状态；持久性 = 提示「转账成功」的瞬间，断电也不能丢。
  • 一通到底：为什么说「一致性是目的、其他三条是手段」？原子性防半途、隔离性防互扰、持久性防断电——三者合力才保证「从一个合法状态到另一个合法状态」。为什么 WAL（先写日志）能实现持久性又快？顺序写日志比随机写数据页快几个数量级——先记流水账再慢慢整理账本，崩溃了按流水账重放。
  • 考场回扣：四条各配「实现手段」（undo/锁+MVCC/redo-WAL）与一句白话解释；「一致性是目的」是简答题的加分句。

07 并发问题与隔离级别（db-p07）

  • 第一性拆解：隔离性若做绝（完全串行）性能就死，于是按「容忍哪些并发毛病」分级。三种毛病机理各异：脏读 = 读到别人还没提交、可能回滚的数据（读了假货）；不可重复读 = 同一行读两次值变了（别人 UPDATE 提交了——针对「值」）；幻读 = 同一条件读两次行数变了（别人 INSERT/DELETE——针对「数量」）。四个隔离级别就是「逐级封杀」：读未提交全裸、读已提交封脏读、可重复读再封不重复读、串行化封杀一切。
  • 费曼讲法：看股票大屏。还没收盘的价格你就按它下单（脏读——可能撤单作废）；刷新前后同一支股票价格变了（不可重复读）；再刷新多上市了三支新股、列表变长（幻读）。想看多稳的数据，就得多等多排队（隔离级别越高并发越差）。
  • 一通到底：为什么「值变」和「行数变」算两种毛病？因为防的机制不同：防值变要锁住行（行锁/MVCC 版本），防行数变要锁住「范围」（间隙锁）——范围锁代价大得多，所以 MySQL 默认可重复读仍可能出现幻读（除非用间隙锁）。毛病清单决定级别阶梯，每升一级多堵一种。
  • 考场回扣：三读判据一句话背死——未提交=脏读、同行值变=不可重复读、行数变=幻读；「MySQL 默认可重复读」是常考锚点。

08 封锁协议与死锁（db-p08）

  • 第一性拆解：实现隔离级别的经典手段是锁。两段锁 2PL（事务分两段：先集中加锁、后集中解锁，中间不许交叉）能保证调度可串行化（结果等价于某种排队串行执行）——但它不防死锁：因为两段锁只管「加解锁的顺序规范」，不管「谁等谁」的拓扑，两个事务互相持有对方要的锁就死锁了。死锁四条件（互斥/占有且等待/不可剥夺/循环等待）缺一不可，破坏任一条即预防（一次封锁法破坏「占有且等待」、顺序封锁法破坏「循环等待」）。
  • 费曼讲法：两段锁 = 出租车司机一整天的规矩：上车先把你今天要用的所有钥匙都拿到手（加锁段），收车再统一归还（解锁段）——绝不中途交一把再领一把。但两个司机各拿了对方也要的钥匙，就僵住了（死锁）——规矩本身不管这事，要另外定「每人按编号顺序拿钥匙」（顺序封锁）。
  • 一通到底：为什么 DBMS 常选「检测+牺牲」而不是预防？预防（一次封锁）要预先知道全部要锁什么、顺序封锁要全局排号——约束都太重伤并发；检测（等图找环）只在死锁真发生时触发，代价小——检测+牺牲最年轻的事务（回滚成本最低者）是工程折衷的典型。
  • 考场回扣：背死「2PL 保证可串行化、不防死锁」+ 四条件名 + 两个预防法各破坏哪条；牺牲策略答「回滚代价最小（最年轻）」。

09 分布式事务 2PC/TCC（db-p09）

  • 第一性拆解：分库分表后（p10），跨库写没有本地事务可用。2PC（两阶段提交）：协调者先问全员「能提交吗」（准备/投票），全员 yes 才发「提交」令——强一致，代价是投票期间所有参与者锁着资源干等（同步阻塞）、协调者挂了全员卡死（单点风险）。TCC（Try-Confirm-Cancel）：把锁资源改成「预留额度」，业务层两阶段（连通 mic-p09——同一套方案在应用层的镜像）。判据同款：资金强一致选 2PC/TCC，高并发容忍延迟选消息最终一致。
  • 费曼讲法：2PC = 团长组织旅游订房：先挨个问每家酒店「能留房吗」（都先锁着房不退）——全说能，才发「都订」；一家说不能，发「都放」。锁房期间谁都不能接待别人（阻塞）；团长手机没电全团傻等（单点）。TCC = 改成「先占名额不付款，全占住再统一扣款」——占名额比锁房子松得多。
  • 一通到底：为什么 2PC 的阻塞不可避免？两阶段的语义就是「用等待换一致」——必须全员表态期间冻结一切，这是强一致的定价。为什么 XA 在互联网高并发场景退场？锁住数据库资源等全员投票 = 高峰期连接池被锁耗干——所以互联网把两阶段上移到应用层（TCC 锁额度不锁库）或干脆放弃强一致（Saga/消息，连通 mic-p09）。
  • 考场回扣：2PC 两阶段各一句 + 三缺陷（阻塞/单点/锁资源久）；选型判据与微服务篇 p09 合用一套。

10 CAP 与 BASE、分库分表（db-p10）

  • 第一性拆解：单库三堵墙：数据量超单机、写压力超单机、可用性扛不住单点——于是分库分表（先垂直按业务拆、再水平按行分片）+ 读写分离（主写从读）。分布式一上来，CAP 定律限定死：网络分区（P）必然发生必须选，真正的选择只在 C（每次读到最新）与 A（每次都有响应）之间——分区发生时两者不可兼得：CP 宁可拒绝服务（ZooKeeper），AP 返回可能略旧的数据（Eureka）。业务多数容忍旧数据 → BASE（基本可用/软状态/最终一致）成为互联网默认口径。
  • 费曼讲法：连锁奶茶店菜单。分区 = 城东城西店网络断了。CP = 总部规定「联不上网就停售」（宁停不错——银行、库存扣减）；AP =「先按手抄旧菜单卖」（保可用、可能卖完的还在卖——评价、推荐）。选哪个看业务「错一秒的代价」。分片键 = 分单规则——按区域分单（范围）、按尾号分单（哈希），规则定错就有人天天跨城跑（跨分片查询）。
  • 一通到底：为什么「P 必选」不是选择题？网络故障是物理必然（交换机会坏、光缆会断），不存在「不分区」的选项——CAP 的真命题是分区发生时 C 和 A 二选一。为什么分片键要「查询最高频 + 分布均匀」？分片键决定数据路由——不均匀 = 热点分片独扛 90% 负载（白分）；不是高频查询条件 = 大部分查询全分片广播（白分）。读写分离的复制延迟为什么能用「强制读主」兜底？改完立即读的场景（改密码后登录）不能容忍旧数据——按业务标记强制路由到主库，是延迟问题的标准对策。
  • 考场回扣：CAP 只选 C/A + 各举一例（CP=ZooKeeper/AP=Eureka）；分库分表答「先垂直后水平 + 分片键两条件 + 复制延迟强制读主」。
