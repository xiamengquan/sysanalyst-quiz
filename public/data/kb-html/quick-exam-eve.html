二、试题一必答 · 两手准备

A. 需求获取七法：定义 · 用法 · 效果

需求获取（总定义）：通过调查、交流与观测等手段，从干系人处收集并初步整理业务目标、用户任务与约束条件，形成原始需求素材的过程。作用：把隐含的业务与用户期望显性化，为分析、建模与规格说明提供输入。

方法 定义（是什么） 用法（怎么做） 效果（用于什么） 四维倾向
用户访谈 分析人员与干系人一对一（或小范围）交流，通过结构化/非结构化提问收集需求 准备提纲 → 主持（结构与非结构结合）→ 会后整理归档 深入了解特定角色的目标、任务与痛点，澄清模糊表述 广度中；深度高；集成中；参与中高
JRP/JAD 在引导人主持下，短时间召集关键干系人共同研讨并当场达成一致的工作坊技术 严格议程、控制发言、引导人中立、避免堆砌术语 快速收敛多方观点、当场暴露并处理冲突，缩短确认周期 广度中高；深度高；集成高；参与高
问卷调查 向较大范围对象发放统一题项并回收统计，批量收集需求或态度 题项可理解、可统计；宜与访谈结合互证 短时间扩大样本面，获取可量化的共性倾向 广度高；深度低；集成低；参与中
文档分析 研读制度、报表、接口说明、遗留系统文档提取业务规则与数据需求 先文档后访谈/观察，交叉验证防止文档过时 低成本复用已有知识，发现书面规则与现状差距 广度中；深度中；集成中；参与低
观察/实地调研 到业务现场跟随真实操作，记录实际流程、例外与环境约束 跟岗记录、注意被观察效应、对照口述差异 发现用户「说不清」「不好意思说」的真实做法与隐性规则 广度低中；深度高；集成中；参与中
采样 从总体按规则（简单随机/分层/聚类/系统）抽取代表性样本调查 与问卷组合；写清抽样方法与总体匹配 控制成本，用样本结果推断总体特征 广度视样本设计；深度低中；集成低；参与中
情节串联板 用故事板/分镜/场景串联呈现用户交互与业务流程（被动、主动、交互式三型） 画分镜 → 逐格确认 → 修改再确认；可与原型、JAD 配合 消除用户对界面与流程的想象盲区，便于讨论确认 广度低中；深度中高；集成中；参与中高

四维定义（必背）：需求广度=覆盖干系人与业务面的宽窄；需求深度=对任务规则与异常挖得是否充分；信息集成度=多方信息当场对照、冲突暴露并收敛共识的程度；用户参与度=用户直接投入并影响结论的程度。

答卷套路：先问卷（+采样）扩面 → 访谈/观察加深 → 情节串联板或原型对齐界面 → JAD 收敛冲突；每点回扣题干约束（工期/成本/地理分布/说法冲突）。

B. 需求三层与需求管理

三层定义：

层次 定义 服务对象 典型产物
业务需求 组织/投资方希望达成的高层业务目标、收益与范围（why） 管理层、投资方 项目视图与范围
用户需求 角色为完成任务对系统的目标与交互期望（what） 最终用户 用例/用户故事/场景
系统需求 可验证的功能+非功能+设计约束规格（how） 开发/测试 SRS

需求管理三件（定义+用法+效果）：

  1. 需求基线：评审批准后的需求约定并版本化。用法：评审通过 → 冻结编号 → 后续改动必须走变更流程。效果：成为开发与管理的桥梁，防止需求无序漂移。
  2. 变更控制（CCB）：变更控制委员会对变更做影响评估与审批。用法：提交变更申请 → CCB 评估影响（范围/工期/成本/测试）→ 审批或否决 → 更新基线与下游工件。效果：变更可控、可追溯，避免「口头改需求」导致返工。
  3. 需求跟踪矩阵：需求来源、设计、实现与测试用例的双向映射。用法：建「需求↔设计↔代码↔测试」链并双向维护。效果：变更影响分析、覆盖率审计，保证前向与后向都可追溯。

C. 加工逻辑三件套（数据字典「加工逻辑」条目）

总定义：DFD 中每个「加工」的内部逻辑，可用三种工具之一描述，三者描述同一逻辑、可互相转换。

工具 定义（是什么） 用法（怎么写） 效果（好在哪/限在哪）
结构化语言 介于自然语言与程序语言之间的伪码，只用顺序、判断（IF-THEN-ELSE）、循环（WHILE）三种结构 按执行顺序书写；动词明确，避免「处理」等空洞词 适合含顺序步骤或判断循环的加工；不够图形直观

D. 数据流图 DFD（定义+绘制+纠错）

  • 定义：用外部实体、加工、数据流、数据存储四种元素描述系统逻辑的数据流模型，自顶向下分层分解。
  • 用法（绘制四步）：画系统输入输出（边缘标出）→ 画内部从输入连处理 → 为数据流命名（避免空洞词）→ 为加工命名（动宾短语）。
  • 分层规则：顶层图定边界与外部实体 → 0 层图分解主要加工 → 逐层细化；父图与子图数据流必须平衡。
  • 纠错四类（案例必考）：①父子图不平衡；②黑洞（只有输入无输出）；③奇迹（只有输出无输入）；④多余连线（外部实体与数据存储直接连线）。
  • 需求阶段三作用：理解表达用户需求；概括内部逻辑作设计基础；存档与修改开发计划的依据。
  • 配套：数据字典 DD 精确定义六类条目（数据元素/数据结构/数据流/数据存储/加工逻辑/外部实体），消除二义性、支撑一致性检验。

E. 结构化分析（SA）· 知识补全

SA（答卷·定义）：结构化分析是面向数据流、自顶向下逐层分解的需求分析方法，以 DFD（功能模型）+ 数据字典（数据词典）+ STD（行为模型）为核心。作用：理清数据从哪来、经何加工、存何处，形成分层可验证的分析模型。

四要素与命名改错（改错题常考）：

要素 图形 命名要点 错误示例（改错题）
外部实体 矩形 □ 名词，且在系统边界外（供应商✓）；内部模块画成实体 ✗ 「订单模块」当外部实体
加工 圆角矩形 动宾短语（校验订单✓） 「订单」「数据」当加工名 ✗
数据存储 开口矩形 名词（订单库✓） 无名存储 ✗
数据流 带箭头实线 具体名词短语（合格订单✓） 「流」「信息」空洞名 ✗

口诀：加工必动宾，数据流有名，外部在界外，存储可读写。

分层图（0 层 vs 1 层）：

层次 别名 画什么 加工编号
0 层 上下文/顶层图 整系统当一个加工，只连外部实体与数据流 0 或系统名
1 层 首次分解 拆成子加工+数据存储 1、2、3…
2 层及以下 继续分解 某 1 层加工展开成子图 1.1、1.2…

作用口径：0 层界定系统边界；1 层把黑盒打开看清内部功能与存储。

数据字典六类条目 + 数据结构符号（填空常考）：

符号 含义
= 由…组成
+ 同时出现（与）
[A|B] A 或 B 选一（任选）
{…} 必选项
{…}*（或 m{…}n） 重复 0..n 次（指定次数）

示例：订单 = 订单号 + 顾客名 + 日期 + {明细}。四作用：列表、相互参照、内容检索、一致性检验（专人/数据管理员维护）。

SA 三模型关系（选择/简答）：

  • 功能模型：DFD——系统「做什么、数据怎么流」
  • 行为模型：STD / 控制规格说明——状态如何随事件迁移
  • 数据模型：E-R 图 + 数据字典——数据长什么样 三模型相互印证，共同构成分析说明书。

改错清单（案例画图题按此排查）：父子图不平衡、黑洞、奇迹、多余连线、加工用名词命名、数据流无名、外部实体直连数据存储、菱形/泳道混入 DFD（那些是流程图/活动图元素，不是 DFD）。

F. 面向对象分析（OOA）· 知识补全

OOA（答卷·定义）：面向对象分析是从参与者目标与问题域对象职责的视角建立分析模型的方法，以用例模型与分析类模型为核心。作用：理清谁用系统、系统为谁完成何目标、对象如何协作。

系统分析建模（答卷·整段可背）：

  • 定义：系统分析建模是在系统分析（需求分析）阶段，用图形与文字模型描述待建系统的功能、数据或对象及其关系与行为，以准确理解问题域并形成可交付分析模型的过程。
  • 作用：澄清并结构化用户需求；发现遗漏、冲突与二义性；在干系人与开发方之间建立对「系统做什么」的共同理解；为设计、实现与测试提供可跟踪依据。

OO 建立系统分析模型四步（案例高频·必背）：

  1. 定义概念类；
  2. 确定类之间的关系；
  3. 为类添加职责；
  4. 建立交互图。

前三步合称 CRC（类–责任–协作者）建模；第四步用交互图（序列图）描述动态协作。CRC 卡三栏=类名/职责/协作者。

用例模型三要素：

要素 含义 命名
参与者 Actor 与系统交互的外部角色（人、外部系统、设备、时钟） 名词：收银员、支付网关
用例 Use Case 系统为参与者完成的有价值目标的一次完整交互 动宾：提交订单
通信关联 参与者与用例的交互线 箭头指向主动发起方

业务用例 vs 系统用例（易混必背）：业务用例站在组织视角（「客户完成门店退货」），系统用例站在软件边界内（「系统记录退货单并回写库存」）；一个业务用例可对应多个系统用例。用例内的「步骤 1/2/3」不是子用例。

OOA 产物清单（交卷口径）：用例模型（用例图+用例规约）→ 分析类模型（领域类图 + BCE 职责划分）→ 交互图（序列图描述用例流程）。

SA vs OOA 怎么选（题干信号）：

题干信号 选谁
给 DFD 图让补全/改错、强调数据流与加工 SA（结构化分析）
给用例图/类图、强调参与者目标与对象职责、需求易变、交互密集 OOA
数据流清晰的批处理/传统 MIS SA 更顺手
界面交互复杂、业务对象多、团队面向对象技术栈 OOA 更顺手

对比一句（答卷）：SA 以加工与数据流为中心，OOA 以对象与职责为中心；二者都服务于「系统做什么」的分析结论，可按题干信号择一并说明理由。

三、UML 与用例 · 定义 / 作用 / 用法 / 效果（试题一 OO 线）

A. UML 总览

  • 定义（答卷）：统一建模语言（UML）是用标准化图形符号对软件系统进行可视化建模的规范语言。
  • 作用（答卷）：统一分析与设计的表达口径；结构看静态（结构图）、行为看动态（行为图），图随问题选。
  • 用法：需求阶段用用例图定功能范围；分析阶段用类图/序列图/状态图/活动图建分析模型；设计阶段延伸到组件图/部署图。

B. 用例图（★★★★★ 必考）

  • 定义（答卷）：用例图是描述系统边界外参与者与系统内用例及其关系的行为图。
  • 作用（答卷）：界定系统功能范围，说明「谁与系统交互、系统为参与者完成哪些有价值目标」。
  • 用法（构建四阶段）：识别参与者 → 合并需求获用例 → 细化用例描述 → 调整模型。
  • 元素：参与者（人 / 外部系统 / 硬件设备 / 时钟）、用例（椭圆，命名「动词短语+名词短语」）、通信关联、系统边界框。
  • 效果：需求阶段与用户对齐功能范围；用例宜编号，便于需求跟踪。

include vs extend（答卷必背）：

定义 作用 箭头方向
«include» 基用例必然包含另一用例的行为 抽取每次都必须执行的公共子流程（如身份认证） 基用例 → 被包含用例
«extend» 特定条件下由扩展用例为基用例增加行为 表示可选增值或条件触发的扩展（如发送短信） 扩展用例 → 基用例

用例规约六段（案例简答标准答）：①名称 ②参与者 ③前置条件 ④基本事件流 ⑤备选/异常事件流 ⑥后置条件。

案例填空三看：边界外空白 → 参与者；椭圆空白 → 用例名（动宾）；虚线旁 → 先判必经/可选，再写 include 或 extend。

易错：用例 ≠ 界面按钮级操作步骤（用例是目标导向的完整交互）；区分业务用例与系统用例；include/extend 箭头方向勿画反。

C. 类图（★★★★★ 必考）

  • 定义（答卷）：类图是描述类、接口及其属性、操作与静态关系的结构图。
  • 作用（答卷）：展示问题域或设计中的概念结构，说明有哪些类、类之间如何关联；静态结构首选。
  • 用法：类盒三格（类名 / 属性 / 操作()）；可见性 + public、- private、# protected；多重性写在对方端，读法=「一个本端对应几个对端」（如家属 1..* ↔ 老人）。

六种关系（定义 · 作用 · 符号）：

关系 定义（答卷） 作用（答卷） 符号
关联 分类器间结构关系，实例经链接相连 表达实例间稳定结构连接 实线
依赖 客户端对供应者的较弱使用/创建/调用关系 表示临时使用，不强调长期持有 虚线开放箭头
泛化 一般与特殊的 is-a 关系，子继承父并可特化 建立类型层次与多态 实线空心三角（三角在父端）
实现 实现端兑现规约端契约（类实现接口） 表示实现与规约的对应 虚线空心三角（三角在接口端）
聚合 弱拥有：整体不负责部分生命周期，部分可独立、可共享 可分离的整—部分关系 实线空心菱形在整体端
组合 强拥有：整体负责部分存在与存储，生命周期绑定 表示构成关系，部分不能独立存在 实线实心菱形在整体端

强度排序（答卷可写）：依赖 < 关联 < 聚合 < 组合；菱形永远画在整体一端。

判定口诀：部分随整体销毁 → 组合（如订单与明细、档案与老人）；可收回再分配 → 聚合（如手环与老人）；各自独立存在 → 关联；「用一下」→ 依赖；「是一种」→ 泛化；「兑现接口」→ 实现。

分析类 BCE 三角色（答卷·定义/作用）：

角色 定义 作用
边界 Boundary 系统与参与者（外部系统/设备）之间的交互接口类 收发输入输出、适配交互，隔离系统内外
控制 Control 协调某一用例控制流程的编排类 按顺序调度对象、处理分支异常；不持久保存数据
实体 Entity 问题域中具持久业务意义的信息及规则载体 保存业务状态与约束，供控制类读写

口诀：界面收发、控制编排、实体存业务；一条用例常对应 1 边界 + 1 控制 + 若干实体。

D. 序列图（★★★★★ 必考）

  • 定义（答卷）：序列图是按时间顺序描述对象之间消息交互的行为图（教材别名「顺序图」）。
  • 作用（答卷）：说明某一场景下对象如何依次发消息、协作完成一次交互。
  • 用法/口径（必记）：
    • 选择题答「三大」：对象、生命线、消息（2014 上午真题口径）
    • 案例简答答「四大」：参与者、对象、生命线、消息（2026 上案例真题口径；参与者作为消息发起/接收源头、界定系统边界）
  • 易错：泳道是活动图元素，不属于序列图基本构成（经典干扰项）。

E. 状态机图（★★★★）

  • 定义（答卷）：状态机图是描述某一个对象在生命周期中状态及迁移的行为图（旧称状态图）。
  • 作用（答卷）：说明对象在何种事件下从一状态转到另一状态。
  • 用法：先列状态清单与事件清单 → 画迁移弧并标注触发事件/条件/动作 → 检查不可达与无出口状态。
  • 适用效果：事件驱动、状态复杂的对象（订单：待支付→已支付→已完成/已取消）。
  • 易混：DFD 管「数据怎么流」，状态图管「状态怎么变」；与 STD 同源。

F. 活动图（★★★★）

  • 定义（答卷）：活动图是描述业务流程中动作、分支、合并与并行的行为图。
  • 作用（答卷）：说明工作如何推进、何处分支或并行、角色如何分工。
  • 用法：动作节点 + 分支/合并（菱形）+ 分叉/汇合（粗横线）+ 泳道（按角色/对象划分职责）。
  • 易混（必背）：分支/合并 = 选一个做（条件判断，菱形）；分叉/汇合 = 同时做（并发，粗横线）。

G. 选图口诀（题干信号 → 选图）

题干问什么 选什么图

概念类、属性、多重性、静态关系 类图
按时间顺序的对象交互 序列图
对象状态随事件迁移 状态机图

四、Web 高并发 · 逐项定义与效果

① 架构链（从外到内，每件「是什么+干什么」）

组件 定义 作用效果
CDN 内容分发网络：静态资源缓存到边缘节点 就近返回静态资源，降低源站压力与延迟；动态数据不可走 CDN
负载均衡 LB 把请求按算法分摊到多台后端服务器 消除单点、水平扩容、提高吞吐
API 网关 系统统一入口，做鉴权、路由、限流、协议转换 集中横切关注点，屏蔽内部服务结构
注册中心 服务实例注册与发现（健康检查、上下线） 支持动态扩缩容，调用方实时感知实例
Redis 缓存 内存键值存储，放热点数据 读请求挡在 DB 前，响应毫秒级
消息队列 MQ 异步消息中间件（削峰填谷、解耦、最终一致） 流量洪峰先入队，后端按能力消费，防打垮
分库分表 数据按维度拆到多个库/表 突破单库容量与写入瓶颈
读写分离 主库写、从库读，复制同步 读多写少场景大幅提升读吞吐

架构填空口诀：CDN（静态）→ LB → 网关 → 应用集群（注册中心）→ Redis → MQ → 分库分表。

② 负载均衡四算法（定义+适用）

算法 定义 适用场景与效果
加权轮询 按权重顺序分配请求 机器性能不均时让强机多扛
最少连接 发给当前连接数最少的节点 长短请求混杂时负载更均衡
源地址哈希 同一客户端 IP 固定打到同一节点 会话粘滞，免 Session 共享
一致性哈希 哈希环+虚拟节点定位节点 扩缩容时仅少量数据迁移

分层：四层（传输层，按 IP/端口转发，代表 LVS，性能高）vs 七层（应用层，可按 HTTP 内容路由，代表 Nginx，灵活）；经典组合 LVS + Nginx。

③ 缓存三问题（定义+对策+效果）

问题 定义 对策 效果
缓存穿透 查询不存在的 key，每次都打到 DB 布隆过滤器拦截 / 空值缓存 无效请求不再穿透到库
缓存击穿 热点 key 过期瞬间大量并发直击 DB 互斥锁重建 / 逻辑过期不删 同一时刻只有一个请求回源
缓存雪崩 大量 key 同时过期或缓存宕机 过期时间加随机抖动 / 多级缓存 / 集群高可用 过期点分散，DB 压力平滑

④ 业务一致性三连（大题 10 分）

  1. 防超卖：Redis 原子扣减（Lua 脚本/DECR）+ DB 条件更新 UPDATE ... SET 剩余=剩余-1 WHERE 剩余>0 + MQ 异步落库。效果：扣减在内存原子完成，DB 层条件更新兜底，永不卖超。
  2. 防重复下单：前端防连点 + 幂等令牌（SETNX 抢占）/ 数据库唯一索引。效果：同一请求重放只产生一次扣减。
  3. 超时释放（15 分钟未支付订单归还号源）：延迟队列或 Redis ZSet 按到期时间检查 + 支付/取消用条件更新 + 定时对账兜底。效果：号源及时回流，极端漏单可对账修复。

五、微服务 · 逐项定义与效果

微服务（总定义）：把单一应用拆为一组小型服务，每个服务独立进程、独立数据库、围绕业务能力构建，轻量通信（通常 REST/RPC/消息）协作。

① 拆分策略（定义+效果）

策略 定义 效果
按业务能力拆 一个业务域一个服务 边界清晰，变更局部化
按 DDD 限界上下文拆 以统一语言与聚合根划定上下文边界 模型与业务一致，减少跨域耦合
按变更频率/团队拓扑拆 高频变更与独立团队对应独立服务（康威定律） 组织与架构对齐，独立发布提效
❌ 技术层拆分 按 UI/API/DB 分层拆服务 = 分布式单体：改一处动全身，诊断题见此必写

② 治理五件套（定义+用法+效果）

组件 定义 用法 效果
注册发现 服务实例上线注册、下线摘除，调用方查询可用实例 健康检查+心跳剔除 动态扩缩容，故障实例自动摘除
API 网关 统一入口：鉴权、路由、限流、协议转换 外部请求全部经网关 横切能力集中，内部结构对外屏蔽
配置中心 配置集中管理、动态下发 改配置实时推送不重启 灰度切换、运行时调参
熔断/降级 依赖故障时快速失败并启用兜底逻辑 超时→熔断→降级→限流四步 防止故障沿调用链雪崩蔓延
Service Mesh 流量/安全/可观测能力下沉到 Sidecar 代理 业务容器旁挂 Sidecar 接管通信 业务代码与治理逻辑解耦

③ 单体 vs 微服务对比五维（论证题万能表）

维度 单体 微服务
耦合度 模块内紧耦合 服务间松耦合
独立部署 整体发布 单服务独立发布
数据一致性 本地事务强一致 分布式最终一致，代价高
运维复杂度 低（一个进程） 高（监控/链路/编排）
团队自治 全队改同一代码库 小团队独立负责服务

结论句式：结合题干（工期紧/遗留系统/峰值流量）给出选型与理由，不可只列表不收口。

④ 典型诊断句式（问题诊断与改进）

  • 现象：服务拆分过细、调用链长、一处慢全线慢 → 改法：合并过细服务 + 熔断/降级/限流 + 超时重试（重试须幂等前提）。
  • 现象：跨服务数据不一致 → 改法：最终一致性——本地消息表 / MQ 事务消息 + 定时对账补偿；强一致场景用分布式事务（TCC/Seata）并说明代价。

六、数据库 · 一条龙套路（定义全补）

① 范式（定义+判定）

范式 定义 判定方法
1NF 属性不可再分（原子性） 表里无重复组/多值字段即满足
2NF 1NF + 消除非主属性对候选键的部分依赖 非主属性是否只依赖候选键的一部分？是 → 违反
3NF 2NF + 消除非主属性间的传递依赖 非主属性 A→B→C 链条？有 → 违反

三类异常（定义+例子）：插入异常（新教练未开课则无法入库）；删除异常（删最后一门课连带丢教练信息）；修改异常（教练姓名多处冗余，改一处漏一处）。

② SQL 关键字（作用一句话）

  • DDL 三件：CHECK（列值约束）、PRIMARY KEY（实体完整性）、REFERENCES（参照完整性/外键）
  • 统计四件：JOIN（多表连接）、GROUP BY（分组）、HAVING（组间筛选）、ORDER BY（排序）

③ 反规范化与索引（定义+效果）

手段 定义 效果
冗余列 把他表常用列复制到本表 免连接查询，读更快
派生列 预计算并存储统计值（如已预约人数） 免实时聚合计算
汇总表 定期物化分组统计结果 报表类查询直接读结果

⚠️ 一致性保障三句缺一扣分：同一事务内更新两处、触发器联动、定期对账。

索引：定义=加速查询的有序数据结构（B+树）。用法：对高频查询条件建联合索引（如 (会员号,预约时间)、(课程号,签到状态)）。效果：等值/范围查询走索引；最左前缀原则——只查第二列无法用上该联合索引。

七、规划计算 · 公式保底（定义全补）

公式 定义 写法与判据
静态回收期 不考虑资金时间价值，累计净现金流转正所需年数 整数年 + 上年缺口/当年净流（例：3 + 30/150 = 3.2 年）；越短越好
动态回收期 考虑折现，用现值累计流转正的年数 同上但逐年折现累计；动态 ≥ 静态
NPV 净现值 各年净现金流按折现率折现求和再减初始投资 NPV > 0 → 经济可行；例 10% 折现 ≈ 100.62 万
可行性四/五分类 项目立项前的多维可行性论证 技术（能不能做）/ 经济（值不值）/ 法律与社会（合不合规）/ 操作（用户会不会用）/ 组织与政策
BPR 业务流程再造 对业务流程进行根本性再思考与彻底性再设计 关键词：根本性、彻底性、以顾客为中心；案例写「并联审批、一次采集、串改并、信息推送」
