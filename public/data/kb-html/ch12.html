二、架构概述

软件架构（答卷·定义）：软件架构是软件系统的构件、连接件、集成模式及其约束的集合，规定了系统的组织结构与拓扑关系。

软件架构（答卷·作用）：主要作用是体现早期设计决策、明确实现约束、制约并权衡质量属性，并为干系人沟通、开发组织划分与系统演化提供依据。

定义：构件 + 连接件 + 集成模式及约束；指定组织结构与拓扑，显示需求与构件对应关系。

架构九大意义（常考）：

  1. 干系人交流手段
  2. 早期设计决策体现
  3. 明确实现约束
  4. 决定开发维护组织结构
  5. 制约质量属性
  6. 使推理和控制更改更简单（局部/非局部/架构级变更）
  7. 支持渐进原型
  8. 培训基础
  9. 可传递可复用模型

架构发展史四阶段：无架构 → 萌芽（DFD/控制流图）→ 初级（UML）→ 高级（4+1）。

3.1 五种模型

结构模型、框架模型、动态模型、过程模型、功能模型。
最常用：结构 + 动态。

3.2 4+1 视图

4+1 视图（答卷·必背）：

视图 答卷句（是……关注……用于……） 受众
逻辑视图 逻辑视图是面向功能需求的架构视图，关注系统应提供的业务能力与对象协作，用于向最终用户与分析师说明系统做什么。 最终用户
开发视图（实现/模块） 开发视图是面向软件组织与模块划分的架构视图，关注代码结构与包依赖，用于指导编程人员分工与实现。 编程人员
进程视图 进程视图是面向运行时的架构视图，关注性能、并发、分布与进程通信，用于指导系统集成与部署调优。 系统集成人员
物理视图（部署） 物理视图是面向部署的架构视图，关注硬件拓扑、安装位置与通信链路，用于指导系统工程人员完成物理部署。 系统工程人员
场景（用例） 场景视图是以用例串联上述四视图的架构视图，关注典型交互与关键需求，用于验证架构是否满足需求并沟通所有干系人。 所有人

开发视图（实现/模块） 软件组织管理 编程人员

四、软件架构风格（核心）

架构风格（答卷·定义）：架构风格是特定应用领域内反复使用的系统组织方式的惯用模式，由构件类型、连接件类型及其组合约束（词汇表 + 约束）构成。

架构风格（答卷·作用）：主要作用是为架构设计提供可复用的组织模板，简化设计决策并影响系统的质量属性与演化能力。

定义：特定领域系统组织方式的惯用模式 = 词汇表 + 约束。

4.1 数据流风格

风格 特点 典型
批处理 成批处理，顺序执行，无交互 传统文件批处理
管道-过滤器 过滤器 + 管道；数据流驱动 Unix 管道、编译器

4.2 调用/返回风格

风格 特点
主程序/子程序 单线程控制
面向对象 对象 + 方法调用
层次结构 层间调用，上层依赖下层
C/S 资源不对等、共享；二层或三层
B/S 三层 C/S 的实现，浏览器客户端

C/S、B/S、三层架构（答卷·必背）：

架构 定义（是……） 作用 / 适用（用于……）
C/S 架构 C/S 架构是客户端与服务器资源不对等、通过网络共享数据的调用/返回式架构，常见二层或三层划分。 适用于需丰富客户端交互、局部高性能处理的场景；主要作用是集中管理核心数据与业务逻辑。
B/S 架构 B/S 架构是以浏览器为客户端的三层 C/S 实现，表示层由 Web 浏览器承担。 适用于广域网部署、免客户端安装与易维护升级的场景；主要作用是降低客户端部署与维护成本。
三层架构 三层架构是将系统划分为表示层、功能（业务逻辑）层与数据层的 C/S 组织方式。 适用于需逻辑独立、并行开发与跨平台选型的中大型系统；主要作用是隔离界面、业务与数据，提升可维护性与可扩展性。

二层 C/S 缺点：开发成本高、客户端复杂、界面不一、移植难、维护升级难、扩展性差、安全性难保证。

三层 C/S 优点：

  • 逻辑相对独立
  • 灵活选平台
  • 并行开发、多语言
  • 功能层隔离表示与数据

B/S 不足：动态页面支持弱、安全性较 C/S 低、交互性不强。

4.6 面向服务 SOA

SOA（答卷·定义）：SOA（面向服务架构）是将系统功能封装为可独立发布、发现与调用的松散耦合服务的架构风格。

SOA（答卷·作用）：主要作用是实现跨系统、跨平台的业务集成与复用，三角色为服务提供者、服务请求者与注册中心。

要点：功能定义为独立服务；松散耦合；三角色=提供者/请求者/注册中心。

关键技术：UDDI（注册）、SOAP（消息：Envelope/Header/Body）、WSDL（描述）、REST（无状态资源操作）。

REST 展开：约束、HTTP 动词、与 SOAP 对比及案例表 5-2 → 速查/REST架构风格-体系化学习卡.md。

ESB（答卷·定义）：ESB（企业服务总线）是 SOA 中连接各服务与遗留系统的标准化通信与集成中间件。

ESB（答卷·作用）：主要作用是以非侵入方式集成异构系统，提供消息转换、路由、协议适配与服务编排能力。

五、架构实现与质量属性

ABSD 六子过程：需求 → 设计 → 文档化 → 复审 → 实现 → 演化。

变更三类：局部 / 非局部 / 架构级（改部分关系或整个系统）。

质量属性（答卷·定义）：质量属性是描述系统在运行期或开发期非功能需求满足程度的可度量特征（如性能、安全、可用性等）。

质量属性（答卷·作用）：主要作用是作为架构设计与评估的核心依据，架构风格与关键决策直接制约并权衡各类质量属性。

质量属性场景（答卷·定义）：质量属性场景是用结构化方式描述特定质量属性需求的情境化实例，六要素为：刺激源→刺激→环境→制品→响应→响应度量。

质量属性场景（答卷·作用）：主要用于架构评估（如 ATAM）中明确「在什么条件下系统应如何响应」，使非功能需求可验证、可量化。

质量属性场景六要素：刺激源→刺激→环境→制品→响应→响应度量。

开发期属性：易理解、可扩展、可重用、可测试、可维护、可移植。
运行期属性：性能、安全、可伸缩、互操作、可靠、可用、健壮。

可修改性 vs 可变性：快速高性价比变更 vs 扩充成为新架构的能力。

六、第12章易混对比

对比 要点
批处理 vs 管道-过滤器 整体成批 vs 流式逐段处理
仓库 vs 黑板 共享数据 vs 知识源协作求解
二层 vs 三层 C/S 二层 C/S 仅分表示层与数据层，业务逻辑常耦合在客户端或服务器端；三层 C/S 增加独立功能层，用于隔离界面、业务与数据，便于维护与扩展
C/S vs B/S C/S 使用专用客户端，交互能力强但部署维护成本高；B/S 以浏览器为客户端，适用于广域网免安装部署，动态交互与安全能力通常弱于专用 C/S
解释器 vs 规则系统 虚拟机解析 vs 规则匹配
进程通信 vs 事件系统 显式消息 vs 隐式事件
SOA vs 微服务 服务粒度、治理方式不同（微服务见第20章）
可修改性 vs 可变性 改现有 vs 变成新架构

应试钩子

案例可能怎么问：给定场景选架构风格（管道-过滤器/仓库/黑板/C-S/B-S/SOA 等）并说明权衡；ESB 集成遗留系统时答「非侵入、消息转换、服务注册」；质量属性场景六要素填空或补响应度量。

论文怎么用：ABSD、面向服务/SOA（20下、24上）——写「需求→架构风格选型→4+1 视图/关键决策→质量属性场景验证→演化」；与微服务对比时强调粒度、治理与集成方式差异。
