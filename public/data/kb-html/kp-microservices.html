概述

微服务 属本科目大纲考点。常考：对比维度 · 单体（Monolithic） · SOA · 微服务。

速懂

  • 一句话：微服务是将大型应用拆分为多个小型、自治、可独立部署的服务，每个服务围绕特定业务能力，通过 HTTP/REST、gRPC 或消息等轻量通信协作的架构风格。
  • 考什么：Service Mesh、网关、熔断限流、最终一致（教程第 20 章）。
  • 别搞混：| 对比 | 区别 |

定义

  • 微服务：微服务是将大型应用拆分为多个小型、自治、可独立部署的服务，每个服务围绕特定业务能力，通过 HTTP/REST、gRPC 或消息等轻量通信协作的架构风格。作用：主要用于应对单体应用在扩展性、部署频率与技术异构方面的瓶颈，使各服务可独立演化、弹性伸缩并按域隔离故障。
  • 与 SOA 关系：微服务是 SOA 的细粒度实现；强调去 ESB 中心化、去共享 DB、智能端点+简单消息。作用：用于辨析集成方式与数据边界。
  • Service Mesh（服务网格）：是在 Sidecar 代理层统一处理服务间流量、安全、观测与弹性的基础设施层。作用：用于解耦业务代码与通信治理（熔断、重试、mTLS）。
  • API 网关：是对外统一入口，负责路由、鉴权、限流与协议转换的组件。作用：用于客户端与微服务集群之间的边界控制。
  • 最终一致性：是跨服务协作允许短暂不一致、通过消息/补偿异步收敛的一致级别。作用：用于替代分布式 2PC 提升可用性（Saga/TCC 等）。

步骤与流程

微服务治理步骤（案例/论文）

  1. 拆分——按业务能力边界划分服务与独立数据库。
  2. 通信——REST/gRPC/消息；API 网关对外。
  3. 治理——注册发现、配置中心、Service Mesh（Sidecar 治理流量）。
  4. 弹性——限流、熔断、降级、扩缩容。
  5. 一致性——Saga/TCC/幂等/对账，接受最终一致。
  6. 可观测——日志、指标、分布式追踪。

要点

场景特征

定义：将大型应用拆分为小型、自治、独立部署的服务，每个服务围绕特定业务能力，通过轻量通信（HTTP/REST、gRPC、消息）协作。

典型场景：电商、金融、流媒体（Netflix）、大型互联网后台

核心特征：

  1. 服务粒度小、职责单一
  2. 独立部署与演化
  3. 松耦合
  4. 分布式部署（跨数据中心）
  5. 技术异构（Java/Python/Go 混用）
  6. 弹性伸缩
  7. 独立演化和部署

与 SOA 关系：微服务是 SOA 的细粒度实现；强调去 ESB 中心化、去共享 DB、智能端点+简单消息

微服务 vs SOA vs 单体（答卷·易混）

对比维度 单体（Monolithic） SOA 微服务
定义 全部功能集中于单一部署单元 以独立服务为单位、通过标准接口实现跨系统集成的架构思想 SOA 的细粒度实现，强调小服务、独立 DB、去中心化集成
服务粒度 无服务边界，模块级 较粗，常按企业级业务域 较细，常按单一业务能力
集成方式 进程内调用 常经 ESB 集中路由与编排 智能端点 + 简单消息，API 网关/消息队列，去 ESB 中心化
数据存储 通常共享同一数据库 可能共享 DB 或通过 ESB 转换 每服务独立数据库，跨服务用 API 或异步消息
适用场景 简单、低流量、小团队 异构遗留系统集成、企业级复用 高并发、复杂业务、需独立扩展与频繁发布
主要代价 扩展难、小改全量部署 ESB 成为瓶颈与单点 运维复杂、分布式一致性难保障

易混辨析

对比 区别
微服务 vs 单体 单体全部功能单部署、共享 DB，适合简单场景；微服务多服务独立部署、各管各库，适合高并发与频繁发布，但运维与一致性成本更高。
微服务 vs SOA SOA 强调企业级服务集成，常经 ESB 集中编排；微服务粒度更细、去 ESB 中心化，强调智能端点 + 简单消息与每服务独立 DB。
强一致 vs 最终一致 强一致要求任意时刻读到最新数据（如 2PC），代价是可用性与性能；最终一致允许短暂不一致、异步同步，是微服务跨服务协作的常见取舍。
