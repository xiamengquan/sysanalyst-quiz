一、REST 是什么（答卷·定义）

REST（Representational State Transfer，表述性状态转移） 是一种 Web 架构风格（不是某一家公司的产品协议），核心思想是：

  • 把系统里的 名词（资源） 用 URI 标识；
  • 用 HTTP 标准方法（GET/POST/PUT/DELETE 等）表达对资源的 操作语义；
  • 服务器 不在请求之间保存客户端会话状态（无状态），每个请求应 自包含 完成操作所需信息。

助记：资源 + URI + 统一接口 + 无状态 —— 与「远程过程名 + 信封消息体」的 SOAP/RPC 思路不同。

二、架构约束（选择题高频）

约束 要点 题干信号
客户端-服务器 界面与存储分离，各自演化 前后端、多端复用 API
无状态（Stateless） 服务端不保存会话上下文；请求须自带令牌、资源标识等 「不在请求之间保存客户端会话」
可缓存 响应可标为可缓存或不可缓存 CDN、GET 缓存
统一接口 资源标识（URI）+ 标准动词 + 自描述消息 URI + GET/POST/PUT/DELETE
分层系统 客户端不知连的是末端还是中间代理 网关、负载均衡
按需代码（可选） 可选下发脚本 较少单独考

无状态 vs 统一接口（易混）：无状态强调 服务端不记会话；统一接口强调 用 URI 标识资源、用 HTTP 动词表达操作。

三、HTTP 方法与语义（综合知识 + 设计题）

方法 典型语义 安全 幂等 案例/设计提示
GET 查询资源 是 是 只读，可缓存
POST 创建资源 / 非幂等动作 否 否 下单、提交问卷
PUT 全量更新（或指定 URI 的替换） 否 是 弱网重试仍安全
DELETE 删除资源 否 是 删除调查、订单
PATCH 部分更新 否 视设计 大纲较少深挖

幂等（答卷·白话）：同一请求 重复执行多次，资源状态与执行一次一致（如 PUT 覆盖、DELETE 删已删）。POST 创建通常 不幂等（多次可能产生多条记录）。

URI 设计惯例（2018 上 · 资源抽象）：

  • 用 名词复数 表资源集合：/surveys、/questions
  • 用 路径参数 表实例：/surveys/{id}
  • 编辑模式 / 视图模式 可建模为资源或子资源（如 /surveys/{id}?mode=edit 或 /surveys/{id}/edit），与业务状态机一致即可自洽。

四、REST vs SOAP vs RPC（对比速记）

维度 REST 风格 SOAP / 传统 RPC
抽象 资源 + HTTP 动词 过程/对象 + 操作名
协议载体 常用 HTTP/HTTPS HTTP/SMTP 等 + XML 信封
状态 强调 无状态 可支持 会话/上下文 的有状态多步流程
负载与耦合 相对 轻量，易与浏览器/CDN 协作 消息体规范重，工具链完整
扩展 无状态 + HTTP → 横向扩展、负载均衡 较自然 企业级 WS-Security 等安全规范成熟
安全 常靠 HTTPS + 应用层鉴权（OAuth2/JWT）补 规范层安全能力 更直接

2016 上 · 选 REST 集成云平台（表 5-2 判题口径，摘要）：

常见表述 是否合理
GET/POST/PUT/DELETE 映射配置与监测数据的 CRUD 无状态操作 合理
REST 缺少 像 WS-Security 那样 开箱即用的服务安全规范（需额外设计） 合理
SOAP 一定比 REST 更适合所有无状态场景 需看题干，不能绝对化
无状态请求可在任意服务器处理，利于 HTTP 负载均衡与横向扩展 合理

五、与 SOA / 微服务的关系

  • 第12章 SOA：REST 与 SOAP、WSDL、UDDI 并列，表示 面向资源的轻量服务暴露方式。
  • 第16章 Web：前后端分离、SPA 通过 RESTful API 访问后端。
  • 第20章 微服务：服务间同步调用常用 HTTP/REST + OpenAPI；异步用消息队列。

答卷句：微服务对外暴露 标准 REST API 并做 版本控制，用于降低协作成本、支持独立部署与演进。
