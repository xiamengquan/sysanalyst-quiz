二、核心知识点

2.1 需求定义与层次（答卷·必背）

软件需求（答卷·定义）
软件需求是用户（及干系人）对新系统在功能、行为、性能、设计约束等方面的期望与约定。
作用：用于指导后续分析、设计、实现、测试与验收，并作为变更与跟踪的基准。

三层需求总览：业务需求 → 用户需求 → 系统需求（由战略到可实现规格，逐层细化）。

层次 关注点 主要读者 典型产物
业务需求 组织为什么做、做成什么样（目标/范围） 投资人、客户、管理层 项目视图与范围、愿景、业务目标
用户需求 角色要完成什么任务、达成什么目标 最终用户、业务代表 用例/用户故事、场景、任务描述
系统需求 系统必须具备哪些可验证能力与约束 分析/设计/开发/测试 SRS：功能 + 非功能 + 设计约束

业务需求（答卷）

定义：业务需求是组织或投资方希望通过系统建设达成的高层业务目标、收益与项目范围描述。
作用：用于界定「为什么做、做到什么程度、不做什么」，为项目立项、范围控制与优先级提供依据。
常见内容：业务目标（如缩短办理时限、提升跨厅协同）、成功标准、范围边界、主要干系人与约束（工期/预算/政策）。
举例：某市要「支持 15 个分厅跨厅取号办理，高峰响应 ≤1 秒，记录保存 ≥5 年」——这是业务层目标与约束，尚未落到具体界面操作或表结构。

用户需求（答卷）

定义：用户需求是最终用户（或角色）为完成其工作任务而对系统提出的目标、任务与交互期望。
作用：用于说明「谁要用系统做什么」，是连接业务目标与系统规格的桥梁，常以用例、场景、用户故事表达。
常见内容：角色、任务目标、主成功场景、备选/异常流、业务规则（用户可感知部分）。
举例：「办事群众可在 A 厅取号后到 B 厅办理同类型业务，并在小程序查看排队进度」——强调用户任务与体验，仍不等于详细接口/性能指标写法。

系统需求（答卷）

定义：系统需求是为实现业务与用户需求，对系统必须具备的功能、非功能属性及设计约束所作的、可验证的规格说明。
作用：用于作为开发、测试与验收的直接依据，把「用户要做什么」落实为「系统必须怎样表现」。
常见内容：

  • 功能需求：系统应提供的具体能力（输入/处理/输出、接口行为）
  • 非功能需求：性能、可靠性、安全性、可用性、可维护性等（常对应 FURPS+）
  • 设计约束：必须采用的技术/标准/平台、法规与互操作限制等
    举例：「排队记录须持久化保存至少 5 年；跨厅办理时目标分厅须能按业务类型+分厅定位原取号记录；热点排队人数查询经 Redis 缓存」——可设计、可测试。

三者关系与易混（答卷）

对比 业务需求 用户需求 系统需求
问的是 组织要什么结果 角色要完成什么事 系统必须具备什么能力/约束
抽象度 最高 中 最低（可实现、可验证）
典型错答 写成按钮/字段细节 写成组织战略口号 写成不可测形容词（「好用」「美观」）

推导关系（答卷一句）：业务需求规定方向与范围；用户需求把方向落实为角色任务；系统需求再把任务落实为可开发、可测试的功能/非功能/约束。三者应可跟踪（业务 ↔ 用户 ↔ 系统），变更时同步评估影响。

与 QFD「常规/期望/意外」易混：那是按用户满意度类型分类；本处三层是按抽象层次与读者分类，不要混答。

2.2 质量功能部署 QFD

类型 含义 未满足后果
常规需求 用户明确期望的功能/性能 实现越多越满意
期望需求 用户认为理所当然但未说清 未实现 → 不满意
意外需求（兴奋需求） 范围外但开发者可赋予的特性 未实现不影响购买；实现则更高兴

2.3 FURPS+ 分类

FURPS 内容
F 功能性 特性、功能、安全性
U 可用性 人性化、帮助、文档
R 可靠性 故障频率、可恢复性、可预测性
P 性能 响应时间、吞吐量、准确性、资源利用率
S 可支持性 适应性、可维护性、国际化、可配置性

“+”辅助因素：实现、接口、操作、包装、授权。

2.4 好需求特性（IEEE）

  • 单条需求：正确、无歧义、可检验、可跟踪
  • 需求集合：完整、一致、可修改
  • 高品质：正确性、完整性、一致性、明确性、可验证性、优先级排序、可修改性、可追溯性、可理解性

2.5 需求工程

两大工作：需求开发 + 需求管理。

需求开发四阶段：

  1. 需求获取
  2. 需求分析
  3. 需求定义（文档化）→ 用户原始需求说明书 + 软件需求规格说明
  4. 需求验证

需求管理：需求基线、变更控制、需求跟踪。

需求工程五活动（含管理）：获取 → 分析 → 规格 → 确认验证 → 管理。

需求基线：评审批准后的需求约定，是开发与管理的桥梁。

三、需求获取技术（答卷·案例高频）

案例常要求从需求广度、需求深度、信息集成度、用户参与度等维度比较获取方法，并结合题干选型。速查卡：速查/案例必答-需求获取五法对比卡.md。

3.1 需求获取（答卷）

需求获取（答卷·定义）
需求获取是通过调查、交流与观测等手段，从干系人处收集并初步整理业务目标、用户任务与约束条件，形成原始需求素材的过程。
作用：用于把隐含的业务与用户期望显性化，为后续需求分析、建模与规格说明提供输入。

3.2 比较维度（答卷·四维必背）

需求广度（答卷·定义）
需求广度是一次获取活动所能覆盖的干系人范围、业务领域或需求条目面的宽窄程度。
作用：用于衡量「能覆盖多少人/多少面」——面越宽，越利于发现共性问题与统计分布，但单点深入往往不足。

需求深度（答卷·定义）
需求深度是对某一角色、任务或业务规则所能挖掘到的细节、动机与异常场景的充分程度。
作用：用于衡量「挖得够不够细」——深度高利于澄清复杂流程与例外，但覆盖面通常较窄、成本较高。

信息集成度（答卷·定义）
信息集成度是多方信息能否在同一场合被对照、冲突被当场暴露并初步收敛为一致认识的程度。
作用：用于衡量「信息是否拼得拢」——集成度高利于消解矛盾、形成共识；集成度低则信息分散，需事后综合。

用户参与度（答卷·定义）
用户参与度是最终用户（或业务代表）在获取过程中直接投入时间、表达意见并影响结论的程度。
作用：用于衡量「用户是否真的进来了」——参与度高利于验收对齐与减少误解；参与度低则易出现「文档有、现场不对」。

维度 一句话抓手 高意味着 低意味着
需求广度 覆盖面 多人/多部门/多样本 仅少数角色
需求深度 挖得细 动机、例外、规则清楚 只得表面诉求
信息集成度 当场对齐 冲突可见、共识快 信息孤岛、事后拼
用户参与度 用户在场 共创、可确认 间接、易偏差

助记（不当答卷正文）：广看面、深看细、集成看冲突、参与看人在不在。

3.3 常用需求获取技术（答卷）

用户访谈

定义：用户访谈是分析人员与干系人进行一对一（或小范围）交流，通过结构化/非结构化提问收集需求的技术。
作用：用于深入了解特定角色的目标、任务与痛点，澄清模糊表述。
四维倾向：广度中；深度高；信息集成中；用户参与中高。
要点：准备→主持→后续整理；结构与非结构结合。

联合需求计划 JRP / 联合应用设计 JAD

定义：JRP/JAD 是在引导人主持下，于短时间内召集关键干系人共同研讨需求（或设计）并当场达成一致的工作坊式获取技术。
作用：用于快速收敛多方观点、暴露并处理冲突，缩短需求确认周期。
四维倾向：广度中高；深度高；信息集成度高（当场冲突）；用户参与度高。
要点：严格议程、控制发言、避免堆砌术语；适合干系人多、分歧大、工期紧。

问卷调查

定义：问卷调查是向较大范围对象发放统一题项并回收统计结果，以批量收集需求或态度的技术。
作用：用于在短时间内扩大样本面、获取可量化的共性倾向。
四维倾向：广度高；深度低；信息集成低；用户参与中（间接）。
要点：宜与访谈结合；题项须可理解、可统计；难挖深层动机。

文档分析

定义：文档分析是通过研读现有制度、报表、接口说明、遗留系统文档等，提取业务规则与数据需求的技术。
作用：用于低成本复用已有知识、发现书面规则与现状差距。
四维倾向：广度中；深度中；信息集成中；用户参与低。
要点：文档可能过时；须与访谈/观察交叉验证。

观察 / 实地调研

定义：观察（实地调研）是分析人员到业务现场跟随真实操作，记录实际流程、例外与环境约束的技术。
作用：用于发现用户「说不清」或「不好意思说」的真实做法与隐性规则。
四维倾向：广度低中；深度高（真实操作）；信息集成中；用户参与中。
要点：注意被观察效应；适合操作复杂、口头描述与现场不一致的场景。

采样（答卷）

定义：采样是从总体中按规则抽取代表性样本进行调查的技术（简单随机、分层、聚类、系统采样等）。
作用：用于在问卷/访谈等活动中控制成本，并以样本结果推断总体特征。
四维倾向：广度取决于样本设计（可高可中）；深度低中；信息集成低；用户参与中（间接）。
要点：常与问卷调查组合；答题须写清抽样方法是否与总体匹配。

情节串联板（答卷）

定义：情节串联板是用故事板、分镜或场景串联呈现用户交互与业务流程的获取与确认手段（被动、主动、交互式）。
作用：用于消除用户对界面与流程的想象盲区，便于讨论与确认需求。
四维倾向：广度低中；深度中高（场景与交互）；信息集成中；用户参与中高（尤其交互式）。
要点：适合界面/流程复杂、口头描述难以对齐的场景；可与原型、JAD 配合。

3.4 获取技术 × 四维对照表（答卷默写）

方法 需求广度 需求深度 信息集成度 用户参与度
访谈 中 高 中 中高

问卷 高 低 低 中（间接）

3.5 选型口诀（答卷）

  • 要大面统计/多人意见 → 偏问卷（广度高；可写采样控成本）
  • 要挖清某人任务与例外 → 偏访谈或观察（深度高）
  • 要多方当场对齐、消冲突 → 偏 JRP/JAD（集成度+参与度高）
  • 文档多、用户难约 → 先文档分析，再访谈/观察验证
  • 界面/流程难描述、想象不一致 → 偏情节串联板（或原型），再 JAD 确认
  • 答题结构：先按四维对比表 → 结合题干约束选型 → 每点回扣干系人/工期/预算

四、结构化分析（DFD / STD / 数据字典）

由简入深：速查/结构化与面向对象分析-体系化学习路径.md（L0–L2）；刷题路径选「结构化与OO分析（L0→L4）」。

5.1 DFD 在需求阶段的三作用

  1. 理解表达用户需求
  2. 概括内部逻辑，是设计基础
  3. 存档材料，修改开发计划依据

5.2 DFD 绘制步骤

  1. 画系统输入输出（边缘标出）
  2. 画内部，从输入连接处理
  3. 为每个数据流命名（避免空洞词）
  4. 为加工命名（动宾短语）
  5. 逐层分解

5.3 状态转换图 STD

  • 描述系统状态及状态间转换
  • 初态：实心圆；终态：双同心圆（内实心）
  • 可表示循环过程或单程生命期

5.4 数据字典六类条目

条目 要点
数据元素 最小单位，类型/长度/取值
数据结构 组合关系；[] 任选、{} 必选、* 重复
数据流 来源、去处、组成、流通量
数据存储 结构、数据流、查询要求
加工逻辑 编号、名称、I/O；可用判定树/表/结构化语言
外部实体 名称、I/O 数据流、数量

四作用：列表、相互参照、内容检索、一致性检验。专人（数据管理员）维护。

五、面向对象需求与需求管理

由简入深：速查/结构化与面向对象分析-体系化学习路径.md（L3–L4）；用例符号见 速查/UML-体系化学习指南.md。

系统分析建模（答卷·定义 / 作用）：

  • 定义：系统分析建模是在系统分析（需求分析）阶段，用图形与文字模型描述待建系统的功能、数据或对象及其关系与行为，以准确理解问题域并形成可交付分析模型的过程。
  • 作用：用于澄清并结构化需求，发现遗漏与冲突，形成对「系统做什么」的共同理解，并为后续设计、实现与测试提供可跟踪依据。
  • OO 建立系统分析模型四步：①定义概念类 ②确定类关系 ③为类添加职责 ④建立交互图（前三步=CRC）。详解见路径 §4.0。

6.1 用例模型

用例图符号、include/extend、案例填空见：速查/UML-体系化学习指南.md · L2.1。

元素：参与者、用例、通信关联（箭头表示主动方）。

构建四阶段：识别参与者 → 合并需求获用例 → 细化描述 → 调整模型。

参与者类型：人、其他系统、硬件设备、时钟。

用例命名：动词(短语)+名词(短语)；宜编号便于需求跟踪。

注意：

  • 不混淆用例与用例内步骤
  • 区分业务用例 vs 系统用例

用例规约：名称、说明、主/备选事件流、非功能需求、前置/后置条件。

分析类 BCE（答卷·定义 / 作用；写法见 SA/OOA 路径 §0.1 准则）：

  • 边界类：是系统与参与者（或其他外部系统、设备）之间的交互接口类。作用：用于接收外部输入、返回结果并适配交互，隔离系统内外。
  • 控制类：是协调完成某一用例（或其中控制流程）的编排类。作用：用于按规定顺序调用相关对象、处理分支，实现用例流程；不长期保存业务数据。
  • 实体类：是问题域中具有持久业务意义的信息及其规则的载体类。作用：用于表达并保存业务状态与约束，供控制类读写。
  • 采用 BCE 的作用：按职责分离界面交互、流程编排与业务数据，避免职责混杂，便于建立分析模型并衔接序列图与设计。
  • 详解：速查/结构化与面向对象分析-体系化学习路径.md · §4.4

CRC 建模（答卷）：CRC 是类–责任–协作者建模方法；作用是识别概念类并厘清职责与协作。建立分析模型四步——①定义概念类 ②确定类关系 ③为类添加职责 ④建立交互图；前三步合称 CRC。勿与网络 CRC（循环冗余校验）混淆。

需求管理：变更控制（CCB 审批）+ 需求跟踪矩阵（需求↔设计↔代码↔测试；正向/反向跟踪）。
