  • 别搞混：题干锚词：需求分析。

定义

  • 需求分析：是对已获取需求进行整理、澄清、建模与协商，形成无冲突、可验证、可跟踪需求集合的活动。作用：用于消歧、冲突消解与优先级筛选，衔接需求获取与规格说明（SRS）。
  • 需求验证：是对需求文档进行评审、原型确认或测试用例推导，以确认需求正确满足用户意图的活动。作用：用于在实现前发现遗漏、矛盾与不可测表述。
  • 需求规格说明（SRS）：是将分析结果文档化、形成供设计与测试使用的正式需求描述。作用：用于作为开发与验收的契约基线。
  • 需求跟踪矩阵：是需求来源、设计、实现与测试用例的双向映射。作用：用于变更影响分析与覆盖率审计。

步骤与流程

需求工程

  1. 需求定义（文档化）→ 用户原始需求说明书 + 软件需求规格说明

DFD 绘制步骤

  1. 画系统输入输出（边缘标出）
  2. 画内部，从输入连接处理
  3. 为每个数据流命名（避免空洞词）
  4. 为加工命名（动宾短语）

DFD 在需求阶段的三作用

  1. 理解表达用户需求
  2. 概括内部逻辑，是设计基础
  3. 存档材料，修改开发计划依据

要点

需求分析是对已获取需求进行整理、澄清、建模与协商，形成无冲突、可验证、可跟踪需求集合的活动。

  • 相对需求获取：获取偏收集原始素材；分析偏消歧、冲突消解、优先级与可行性筛选。
  • 需求开发链：获取 → 分析 → 规格说明（SRS）→ 验证；分析输出是规格化的前置。
  • 常用方法：结构化分析（DFD/数据字典）、面向对象（用例/领域类）、原型与评审。
  • 质量关注：一致性、完整性、可验证性、可追溯性（IEEE 好需求特性）。

应试

案例可能怎么问：给出干系人多、工期紧、说法冲突等约束，要求用四维比较访谈 / JRP(JAD) / 问卷 / 文档分析 / 观察（及采样、情节串联板若题干涉及大样本成本或界面流程确认），并说明应优先采用哪一种及理由。

论文怎么用：需求获取段落可写「先问卷（+采样）扩面 → 访谈/观察加深 → 情节串联板或原型对齐界面 → JAD 收敛冲突」，并回扣四维与题干约束。

案例三件套（编制稿 v0.18 · 依据 case-map 真题蒸馏）

  • 怎么考：问「需求分析的任务是什么」，或给一段混乱、互相冲突的原始需求，要求整理归类并说明冲突处理过程。
  • 怎么答：任务写完整句——需求分析用于把获取到的原始需求转化为完整、一致、可验证的系统需求规格；冲突处理按流程作答：识别冲突类型（术语歧义 / 目标冲突 / 约束冲突）→ 追溯需求来源 → 组织 JRP 协商 → 记录决策与理由并更新基线。
  • 易错与扣分：任务只答「写文档」；冲突处理只答「开会讨论」无流程；需求歧义与需求变更两个概念混用。
