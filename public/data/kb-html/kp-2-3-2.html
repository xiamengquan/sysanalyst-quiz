嵌入式 OS（调度、优先级反转）

大纲：17.3 · 教程：第17章 · 分组：科目2 · 2. 嵌入式系统分析与设计 · 状态：结构式重写 v2.0 · 审计通过

概述

嵌入式 OS（调度、优先级反转）：常见问题：测试滞后于编码、理解不足漏测、文档差、缺自动化、修一处引新错。

速懂

  • 一句话：设计验证：测试评估设计是否符合要求。
  • 考什么：嵌入式实时、调度与资源约束（教程第 17 章）。
  • 具体理解：
    • 验证 vs 确认：验证=符合设计要求（做得对）；确认=满足用户需求（做对了东西）。
  • 别搞混：题干锚词：嵌入式 / OS。

定义

  • 设计验证：测试评估设计是否符合要求。
  • 嵌入式 OS（调度、优先级反转）：- 设计验证：测试评估设计是否符合要求 - 设计确认：确认产品满足用户需求 常见问题：测试滞后于编码、理解不足漏测、文档差、缺自动化、修一处引新错 语句覆盖：每条语句至少执行一次 未覆盖代码处理： - 有需求无用例 → 增用例 - 无需求 → 增需求+用例。
  • 未覆盖代码处理：是有需求无用例 → 增用例；无需求 → 增需求+用例；死代码 → 问题报告。作用：用于与本节相关的模型选型、特点对比与案例论述。

步骤与流程

场景特征

  1. 专用性强：软硬件紧密结合，生命周期长
  2. 实时性强：限时间内响应；分硬实时/软实时
  3. 软硬件依赖强：协同设计
  4. 专用处理器：低功耗、高集成（SoC）
  5. 多技术融合：计算机+半导体+电子+机械
  6. 系统透明性：用户常感知不到嵌入式存在
  7. 资源受限：存储、I/O、处理能力有限

开发与协同设计

  1. 明确实时性指标
  2. 可调度性分析
  3. 确定任务优先级

语句覆盖：每条语句至少执行一次

未覆盖代码处理：

  • 有需求无用例 → 增用例
  • 无需求 → 增需求+用例
  • 死代码 → 问题报告

基于系统的构件测试：集成级验证，关注接口与实时约束

功能安全（如 ISO 26262）：ASIL 等级、FTTI、失效模式、确认前提条件
