## 一、场景特征

**定义**：将大型应用拆分为**小型、自治、独立部署**的服务，每个服务围绕特定业务能力，通过轻量通信（HTTP/REST、gRPC、消息）协作。

**典型场景**：电商、金融、流媒体（Netflix）、大型互联网后台

**核心特征**：
1. 服务粒度小、职责单一
2. 独立部署与演化
3. 松耦合
4. 分布式部署（跨数据中心）
5. 技术异构（Java/Python/Go 混用）
6. 弹性伸缩
7. 独立演化和部署

****：微服务是 SOA 的细粒度实现；强调去 ESB 中心化、去共享 DB、智能端点+简单消息

**微服务 vs SOA vs 单体（答卷·易混）**

| 对比维度 | 单体（Monolithic） | SOA | 微服务 |
|----------|-------------------|-----|--------|
| **定义** | 全部功能集中于单一部署单元 | 以独立服务为单位、通过标准接口实现跨系统集成的架构思想 | SOA 的细粒度实现，强调小服务、独立 DB、去中心化集成 |
| **服务粒度** | 无服务边界，模块级 | 较粗，常按企业级业务域 | 较细，常按单一业务能力 |
| **集成方式** | 进程内调用 | 常经 ESB 集中路由与编排 | 智能端点 + 简单消息，API 网关/消息队列，去 ESB 中心化 |
| **数据存储** | 通常共享同一数据库 | 可能共享 DB 或通过 ESB 转换 | 每服务独立数据库，跨服务用 API 或异步消息 |
| **适用场景** | 简单、低流量、小团队 | 异构遗留系统集成、企业级复用 | 高并发、复杂业务、需独立扩展与频繁发布 |
| **主要代价** | 扩展难、小改全量部署 | ESB 成为瓶颈与单点 | 运维复杂、分布式一致性难保障 |

## 二、架构原则与模式

### 2.1 九大架构原则

| 原则 | 要点 |
|------|------|
| 单一职责 | 一服务一业务域 |
| 隔离性 | 独立进程+独立 DB，容器封装 |
| 自治性 | 独立生命周期，组件化 |
| 弹性 | 自动扩缩容、容错转移 |
| 可观察性 | 日志、指标、链路追踪 |
| 可测试性 | 单元/集成/契约测试、CI/CD |
| 可维护性 | 标准 API（REST/OpenAPI）、版本控制 |
| 安全性 | TLS、OAuth2、JWT、RBAC |
| 智能端点+简单消息 | 去中心化集成，异步消息 |

****：单一职责原则是指每个微服务只围绕一项明确的业务能力构建；**用于**控制服务边界，避免「大而全」服务带来的耦合与发布风险。

****：隔离性原则是指各服务以独立进程运行并拥有自己的数据存储，常用容器封装；**用于**故障隔离，防止单服务异常拖垮整个系统。

****：自治性原则是指每个服务拥有独立的生命周期，可独立开发、测试、部署与演化；**用于**提升团队并行效率与发布频率。

****：弹性原则是指系统具备自动扩缩容与故障转移能力；**用于**应对流量波动，保障高可用。

****：可观察性原则是指通过日志、指标与分布式链路追踪等手段掌握系统运行状态；**用于**快速定位分布式环境下的故障与性能瓶颈。

**可测试性原则（答卷）**：可测试性原则是指各服务须支持单元测试、集成测试与契约测试，并纳入 CI/CD 流水线；**用于**在频繁独立发布下仍保障质量。

**可维护性原则（答卷）**：可维护性原则是指服务对外暴露标准 API（如 REST/OpenAPI）并实施版本控制；**用于**降低服务间协作成本，支持平滑升级。

**安全性原则（答卷）**：安全性原则是指服务间通信加密（TLS）、身份认证（OAuth2/JWT）与访问控制（RBAC）；**用于**保障分布式环境下的数据与接口安全。

**智能端点 + 简单消息原则（答卷）**：智能端点 + 简单消息原则是指业务逻辑放在服务端点、消息通道保持轻量简单，以去中心化方式集成；**用于**替代 ESB 重度编排，降低集成中间件单点风险。

### 2.2 六种架构模式（案例对比高频）

| 模式 | 机制 | 优点 | 注意 |
|------|------|------|------|
| **聚合器** | 收集多服务数据聚合返回 | 减延迟、减依赖、提高可靠 | 聚合器成为瓶颈 |
| **代理** | 网关转发+治理（LB/熔断/限流） | 解耦客户端与后端 | 不做数据聚合 |
| **链式** | 请求顺序经过多服务 | 流程清晰 | 客户端阻塞等待 |
| **分支** | 链式扩展，条件分支 | 灵活业务路径 | 复杂度上升 |
| **数据共享** | 共享 DB 或数据代理(Kafka) | 数据一致 | 并发与一致性风险 |
| **异步消息** | 消息队列+EDA | 高吞吐、松耦合 | 最终一致性 |

### 2.3 开发与运维组件

| 组件 | 代表技术 | 作用 |
|------|----------|------|
| 容器化 | Docker、Kubernetes | 隔离、编排、自动部署 |
| 服务注册发现 | Consul、Eureka、Nacos | 动态地址 |
| 服务通信 | REST、gRPC、Kafka | 同步/异步 |
| API 网关 | Zuul、Kong | 路由、鉴权、限流 |
| 安全 | OAuth2（4 模式）、JWT、TLS | 认证授权 |
| 监控 | ELK（Logstash→ES→Kibana）、Prometheus+Grafana、APM | 日志/指标/告警 |

**OAuth2 四种模式**：授权码、密码、客户端、隐式

**gRPC 四种 RPC**：Unary、Server Streaming、Client Streaming、Bidirectional Streaming

**Kafka 核心概念**：Broker、Topic、Partition、Producer、Consumer、Consumer Group

## 三、开发与测试要点

### 3.1 测试特点

- 服务多、依赖链长
- 需契约测试（Consumer-Driven Contract）
- 需测试替身（Mock/Stub）与测试容器
- 分布式环境搭建复杂

### 3.2 测试过程与类型

**过程**：单元（单服务）→ 集成（服务间）→ 端到端 → 性能 → 容错 → 安全

| 类型 | 要点 |
|------|------|
| 功能 | API 正确性、业务规则 |
| 性能 | 单服务与链路延迟、吞吐 |
| 容错 | 熔断、降级、故障注入 |
| 安全 | 认证授权、传输加密、漏洞扫描 |
