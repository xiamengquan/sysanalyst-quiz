## 定义

- **CAP定理**：是一致性(C)、可用性(A)、分区容错(P)，最多同时满足两个。
- **数据均衡性原则**：数据均衡性原则是指分片后各节点的数据量与访问压力应尽可能均匀。
- **业务相关性原则**：业务相关性原则是指分片键与分片边界应紧贴核心业务场景与高频访问路径来设计。
- **可扩展性原则**：可扩展性原则是指分片方案应支持业务增长时通过新增节点实现横向扩展。
- **数据分片**：数据分片是把逻辑上统一的数据集合按既定规则划分到多个物理节点存储与访问的技术。**作用**：用于提升容量与并发扩展能力，并支撑故障隔离与按片备份恢复。
- **分片键**：分片键是用于决定一条（或一组）数据路由到哪一个分片的属性或属性组合。
- **跨厅（跨站点）数据共享**：跨厅数据共享是指不同业务网点之间能够按统一规则访问与使用同一业务域下的共享数据（如 A 厅取号、B 厅办理时读取原取号记录）。**作用**：用于支撑跨网点连续办理与实时协同，避免各厅数据孤岛。
- **数据持久化**：数据持久化是将业务数据可靠写入可长期保存的存储介质，并在进程重启、节点故障后仍可恢复访问的能力。**作用**：用于满足长期保存、审计统计与故障后数据不丢等需求（如排队记录保存 ≥5 年）。

## 要点

### 非关系数据库(NoSQL)

| 类型 | 特点 | 代表 |
|------|------|------|
| 列数据库 | 列存储，分析型 | HBase |
| 文档数据库 | JSON/BSON | MongoDB |
| 键值数据库 | 简单KV，高性能 | Redis |
| 图数据库 | 关系网络 | Neo4j |

**适用场景（选择/案例）**：

| 类型 | 适用 | 慎用 |
| 键值 | 会话、计数、热点缓存（**Redis**） | 复杂关联查询 |
| 文档 | 模式多变、JSON 业务对象（**MongoDB**） | 强一致跨文档事务 |
| 列族 | 海量列、时序/日志分析（**HBase**） | 频繁随机小更新 |
| 图 | 社交/风控/知识图谱（**Neo4j**） | 简单 CRUD 为主 |

**性能优化（与 `kp-3-3` 衔接）**：索引与执行计划、读写分离、缓存（注意击穿/穿透）、分片键（均衡+业务相关）、反规范化换读性能。

## 应试

**案例可能怎么问**：给定业务表与函数依赖，要求判断范式级别并分解至 3NF/BCNF；或给出并发/死锁场景，选隔离级别与加锁策略；备份恢复题常考「完全+增量/差异」组合与 RPO 对应关系；**分布式库案例**常考「分片设计核心原则（至少 2 个）」——答**数据均衡性、业务相关性、可扩展性**并稍作展开；再问分片键选型，回扣「跨厅/跨站点共享」与「长期持久化/审计保存」。

**论文怎么用**：数据迁移/多源集成类（23上、24上）可写「源库→中间层→目标库」割接步骤、一致性校验与回滚；OLTP/OLAP 分离、读写分离、缓存与索引优化可作为性能段落素材；多网点政务/连锁类可写分片键与故障隔离。

**常考结论**

- 授权粒度：**库→表→行→列**（4级，由大到小）。
- 审计=**事后**；标识鉴别=**事前**。
- ACID：**原一隔持**。
- 范式递进：**1→2→3→BCNF→4NF**。
- 备份口诀：**物逻分，冷热全增异**。
- 增量备份基于"上次任意备份"，差异备份基于"上次完全备份"（易混！）。
- 分片**设计**原则口诀：**均衡、相关、可扩展**（写全名：数据均衡性 / 业务相关性 / 可扩展性）。
- 分片**正确性**准则：**完备、重构、不相交**（勿与上条混答）。


## 案例三件套（编制稿 v0.18 · 依据 case-map 真题蒸馏）

- **怎么考**：给高并发 / 海量数据场景问「NoSQL 选型与理由」「如何用 CAP 理论权衡」。
- **怎么答**：CAP 三性定义誊写——一致性（C）、可用性（A）、分区容忍性（P）；分布式系统分区容忍不可避免，只能在 C 与 A 之间权衡，结论常写「保证 AP、最终一致 + 补偿机制兜底」；选型按数据形态对应——键值库用于会话与缓存，文档库用于半结构化与 schema 灵活场景，列存用于宽表写多读多，图库用于关系网络。
- **易错与扣分**：声称「CAP 三者可以兼得」；选型与数据形态不匹配（如把图库用于缓存）；漏最终一致与补偿机制这一兜底采分点。
