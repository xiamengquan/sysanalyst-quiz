# 演练 · 需求工程步骤链

> **域**：软件工程 · 需求
> **情境**：需求链条（获取→分析→定义→验证→管理）是案例第一高频步骤链，几乎每套案例都有一问。练法：先默写各环节作用，再对照「辨析」抠出相邻环节的差异句——这正是小问「XX 与 XX 的区别」的得分点。
> **故事线**：把需求工程当成业主委托你装修房子，五道关：听唠叨（获取）→ 画图纸（分析）→ 签合同（定义）→ 开工前验收图纸（验证）→ 施工期管变更（管理）。装修界铁律「改图纸一块橡皮、铺完瓷砖砸墙」同样适用于软件——这也解释了为什么验证要赶在开发前。

## 1 · 需求获取
- **问**：需求获取环节的任务是什么？五种常用方法如何选型？
- **要点**：用户访谈 / 问卷调查 / 观察采样 / 原型 / 联合需求计划
- **范例**：首先进行需求获取：以用户访谈为主干摸清业务目标，对分散的大群体配合问卷调查，对说不清的场景用观察采样与原型引导，关键决策节点用联合需求计划（JAD）集中拍板，形成原始需求素材。
- **作用**：一句话——收集原始需求，决定「系统的目标对不对」。
- **故事**：蹲在业主家听唠叨：单聊深挖心结（访谈）、全家发问卷（问卷）、跟着他过一天看旧厨房怎么用（观察）、先做个样板间让他摸（原型）、全家加工长开碰头会当场拍板（JAD）——唠叨听不全，后面全白搭。
- **辨析**：访谈 vs 问卷——访谈深而慢、适合关键干系人；问卷广而浅、适合大群体统计。原型 vs 观察——原型适合「用户提不出明确需求」的场景，观察适合「用户习而不察」的现场流程。
- **易错**：把「原型」只归入设计手段——它同样是获取手段；五法只答得出三种。
- **溯源**：速查/案例必答-需求获取五法对比卡.md

## 2 · 需求分析
- **问**：需求分析环节做什么？与获取的差异在哪？
- **要点**：建模 / 数据流图 / 用例 / 一致性 / 完整性 / 优先级
- **范例**：第二步进行需求分析：对获取的原始需求进行提炼与建模（结构化用 DFD、面向对象用用例图），检查一致性与完整性，与用户确认优先级，把「用户的话」翻译成「系统的模型」。
- **作用**：一句话——消除歧义、暴露矛盾，形成结构化的需求模型。
- **故事**：把唠叨翻译成图纸：业主说「要亮堂」，你画成「主卧三回路照明」；收来的话自相矛盾（又要浴缸又要淋浴房）必须在图纸阶段清干净。注意：这一步不新增素材，只加工——所以它叫分析不叫收集。
- **辨析**：获取 vs 分析——获取是「从用户处拿来」（发散），分析是「拿来了加工建模」（收敛）；分析不新增需求素材，而是提炼验证已有素材。
- **易错**：答「分析就是继续收集」；漏掉「与用户确认」的闭环动作。
- **溯源**：points/kp-requirements-engineering.md

## 3 · 需求定义与规约
- **问**：需求规格说明书（SRS）的作用与特征是什么？
- **要点**：SRS / 准确 / 一致 / 完整 / 可验证 / 基线
- **范例**：第三步进行需求定义：把分析模型写成需求规格说明书 SRS，做到准确、一致、完整、可验证，经评审确认后形成需求基线，作为设计与测试的合同依据。
- **作用**：一句话——把需求「白纸黑字化」，是后续开发与验收的法律依据。
- **故事**：图纸定稿写合同（SRS）：「亮堂」写不进合同，「主卧 3 盏灯 + 2 回路」写得进——每条可验收（可验证）。签字即基线，从此没人能随手改。
- **辨析**：分析 vs 定义——分析产出「模型」，定义产出「文档」；SRS 是给「读的人」看的，模型是给「建的人」用的，两者互补不可互替。
- **易错**：漏「可验证」特征——不可验证的需求等于没有验收标准。
- **溯源**：points/kp-requirements-engineering.md

## 4 · 需求验证
- **问**：需求验证（确认）环节用什么手段？验证什么？
- **要点**：评审 / 原型演示 / 测试用例 / 一致性 / 完整性 / 可行性
- **范例**：第四步进行需求验证：组织需求评审（正式走查 SRS 与模型），必要时以原型演示让用户确认，检查需求的正确性、一致性、完整性与可行性，不通过项回溯修改。
- **作用**：一句话——在动手开发前确认「我们理解的需求就是用户要的需求」。
- **故事**：开工前让业主验收图纸签字（确认）：此时改图一块橡皮，铺完瓷砖再改就是砸墙——需求验证必须赶在开发动手之前。
- **辨析**：验证 vs 确认——验证对文档与模型（设计未开始），确认由用户背书（签字认可）；需求验证发生在事前，系统测试验证发生在事后，两层验证缺一不可。
- **易错**：与系统测试混淆——需求验证针对 SRS，系统测试针对产品。
- **溯源**：points/kp-requirements-engineering.md

## 5 · 需求管理
- **问**：需求进入开发后如何管理变更？核心机制是什么？
- **要点**：基线 / 变更控制 / 影响分析 / 需求跟踪矩阵 / 版本控制
- **范例**：第五步进行需求管理：以需求基线为参照，所有变更走变更控制委员会审批并做影响分析，用需求跟踪矩阵维护「需求—设计—代码—测试」的双向追溯，保证任何变更可查可控。
- **作用**：一句话——让需求变更「有门槛、有代价、可追溯」，防止范围失控。
- **故事**：施工期业主说「马桶挪十公分」：不许口头答应！走变更单（变更控制）、算加钱加天数（影响分析）、记台账防扯皮（跟踪矩阵）——范围就是这样才不失控的。
- **辨析**：管理 vs 验证——验证管「内容对不对」，管理管「变更怎么控」；跟踪矩阵是双向追溯（前向到设计测试、后向到需求来源）。
- **易错**：只答「开会评审变更」漏掉影响分析与跟踪矩阵两个得分点；跟踪矩阵写成单向。
- **溯源**：points/kp-requirements-engineering.md
