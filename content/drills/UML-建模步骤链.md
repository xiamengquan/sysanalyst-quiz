# 演练 · UML 建模步骤链

> **域**：软件工程 · UML
> **情境**：案例题高频问法——「你会按什么步骤建模？每步用什么图、起什么作用、与相邻步骤有什么差异？」。练法：每格先自己写出「这一步做什么 + 作用句」，再对照范例与辨析，把「记住了」变成「写得出来」。
> **故事线**：把建模当成导演一部电影《新系统上线》：先定剧本大纲（用例图）→ 选拍演员写人设（类图）→ 排分镜（顺序图）→ 给主角写心理线（状态图）→ 排片场调度表（活动图）→ 定档期装厅发行（部署图）。工序错了就拍不出片子——这也是「为什么按这个顺序」的答案。

## 1 · 用例图
- **问**：需求分析阶段的第一步通常是绘制用例图——它的作用与产出是什么？
- **要点**：参与者 / 用例 / 系统边界 / 功能需求 / 交互
- **范例**：首先绘制用例图：识别参与者与用例，界定系统边界，捕获系统的功能性需求，为后续静态结构与动态行为建模提供依据。
- **作用**：一句话——锁定功能范围，用例是后续所有图的公共输入。
- **故事**：开拍前先定剧本大纲：哪些角色（参与者）和系统演对手戏、每场戏讲什么（用例）、片场围栏在哪（系统边界）。大纲不定就开拍，全组白忙——所以它是第一步。
- **辨析**：与类图——用例图是功能视图、类图是静态结构视图；与 DFD——用例图属面向对象方法学，DFD 属结构化分析，同答一题不要混用两套符号。
- **易错**：include 是必然包含的公共行为、extend 是可选扩展，箭头方向常写反；参与者是外部角色，不是系统内部模块。
- **溯源**：速查/UML-体系化学习指南.md · §3.1

## 2 · 类图
- **问**：用例图之后进入静态建模画类图——它的作用与产出是什么？
- **要点**：类 / 属性 / 操作 / 关系 / 静态结构
- **范例**：第二步绘制类图：从用例与名词分析中抽象出核心类，定义类的属性与操作，建立类之间的关联、聚合、泛化等关系，形成系统的静态结构模型。
- **作用**：一句话——定义系统的骨架（数据与职责划分），直接映射到代码结构。
- **故事**：按大纲选演员、写人设卡：属性是背景、操作是会干什么，再定人物关系（血缘=泛化、组队=关联）。人设卡（类）定了，后面所有戏都按它演。
- **辨析**：与对象图——类图是抽象模板，对象图是某一时刻的实例快照；与序列图——类图看「有什么」，序列图看「怎么交互」。
- **易错**：聚合（可独立）与组合（同生共死）强度写反；多重性 1..* 与 0..* 混用。
- **溯源**：速查/UML-体系化学习指南.md · §2.2

## 3 · 顺序图
- **问**：动态建模第一步画顺序图——它的作用与产出是什么？
- **要点**：时间顺序 / 消息 / 生命线 / 对象交互 / 场景
- **范例**：第三步绘制顺序图：针对关键用例按时间顺序排列对象间的消息传递，刻画一次典型场景中对象的协作过程，验证类图职责分配是否合理。
- **作用**：一句话——把用例「演一遍」，暴露职责分配与接口设计的漏洞。
- **故事**：写分镜：这场戏谁先开口、谁接话，按时间一格一格排。分镜一排，人设卡上漏写的台词（职责）立刻暴露——这就是顺序图「验证类图」的作用。
- **辨析**：与通信图——两者语义等价、可互转：顺序图强调时间次序，通信图强调对象间链接（结构关系）；与活动图——顺序图围绕对象消息，活动图围绕业务流程。
- **易错**：同步消息与异步消息箭头（实心/开口箭头）混淆；忘记画出生命线上的激活条。
- **溯源**：速查/UML-体系化学习指南.md · §3.3

## 4 · 状态图
- **问**：对生命周期复杂的对象要补状态图——它的作用与产出是什么？
- **要点**：状态 / 事件 / 转换 / 单个对象 / 生命周期
- **范例**：第四步绘制状态图：针对状态复杂的单个对象，描述其在外部事件触发下的状态转换序列，覆盖对象从创建到销毁的完整生命周期。
- **作用**：一句话——检查单个对象的行为完整性（漏状态、死状态）。
- **故事**：给主角写内心戏线：他经历哪些心境（状态）、什么事件让他转变（转换）。一条线只写一个角色的心路，别把配角的戏混进来——所以状态图是「单对象」视角。
- **辨析**：与活动图——状态图是单对象视角、事件驱动；活动图是多对象跨流程视角、活动驱动（状态图描述「一个对象的一生」，活动图描述「一件事的流水线」）。
- **易错**：状态图只有一个起点可以有多个终点；把「活动」画成「状态」。
- **溯源**：速查/UML-体系化学习指南.md · §3.4

## 5 · 活动图
- **问**：业务流程类需求用什么图收尾建模——它的作用与产出是什么？
- **要点**：活动 / 分支 / 并发 / 泳道 / 业务流程
- **范例**：第五步绘制活动图：将业务流程分解为活动序列，用分支表达判断、用分叉汇合表达并发，必要时用泳道划分职责区域，形成可执行层面的流程模型。
- **作用**：一句话——把跨角色的业务流程讲清楚，是工作流与审批流建模的首选。
- **故事**：排片场调度表：各部门（泳道）在什么节点干什么，哪里能并行赶工（分叉）、哪里必须等齐再开机（汇合）。跨部门的大场面，就看这张表。
- **辨析**：与流程图 DFD——活动图支持并发与泳道（面向对象阵营），传统流程图不支持并发；与序列图——活动图侧重「做了什么」，序列图侧重「谁发给谁」。
- **易错**：并发（分叉/汇合）与普通分支（菱形判断）混画；泳道对应的是职责主体而非技术层次。
- **溯源**：速查/UML-体系化学习指南.md · §3.5

## 6 · 部署图
- **问**：进入实施规划阶段，用什么图表达物理拓扑——它的作用与产出是什么？
- **要点**：节点 / 构件 / 部署 / 物理拓扑 / 硬件
- **范例**：最后绘制部署图：把软件构件映射到硬件节点，刻画网络拓扑与构件间的通信方式，为系统实施与运维提供部署依据。
- **作用**：一句话——回答「软件装在哪、怎么连」，是开发视图到实施视图的桥梁。
- **故事**：定档发行：拷贝（构件）装进哪些影厅设备（节点）、影院之间怎么联网。观众看到的不是分镜而是排片表——软件落不落得下、跑不跑得通，就看部署图。
- **辨析**：与构件图——构件图描述软件自身的组装（逻辑模块依赖），部署图描述软件到硬件的落位（物理拓扑）。
- **易错**：节点与构件混淆——节点是硬件资源，构件是被部署的软件单元。
- **溯源**：速查/UML-体系化学习指南.md · §3.6
