# 论Agent辅助开发技术及其应用

> 结构：摘要→一项目→二理论→三实践→四结束语（五篇共用一、三.1首段与结束语骨架）

## 摘要

2024年11月至今，本人参加某二次元周边定制企业「全渠道定制商城与履约协同系统」建设，担任自营商城、分销商城与微信小程序侧的系统分析与核心研发。系统覆盖自营商城、分销商城与微信小程序等交易定制核心入口，并支持外部平台订单接入，另含自研在线图片编辑器、支付与审图履约，并对接企业ERP/MES；建设周期约10个月，相关人员约15人。本文结合实践论述Agent辅助开发技术及其应用：首先说明相关概念与要点；随后归纳常用分类或方法；最后阐述本项目如何选择并落地文档、骨架与测试运维草稿及治理。实践表明，在保障交易正确、多渠一致与高峰可用的前提下，预期目标得到落实，系统运行平稳。

## 一、项目背景与本人主要工作

公司以二次元周边定制生产为主，原先依赖第三方店铺与线下沟通确认图案，存在改稿慢、规格误解、库存与产能信息不透明、多渠道订单难统一等问题。为提升转化与履约可控性，企业建设「全渠道定制商城与履约协同系统」：以自营商城、分销商城与微信小程序作为交易与定制的核心入口，并支持外部平台订单接入，各类订单归一到统一订单中心；图片处理采用自研在线图片编辑器（图层、裁剪、滤镜、出血线/安全区预览与生产稿导出）；履约链为审图通过后经企业ERP下达计划、MES回传工序/完工进度，商城侧展示进度与交期（本人侧重商城侧与对接契约，不介入车间排产）。系统面向C端用户、分销商与内部运营，建设周期约10个月，研发与测试相关约15人，展会与联名期间存在流量高峰。

本人主要工作包括：（1）参与干系人访谈与需求澄清，输出流程、用例与验收要点；（2）参与总体方案与模块边界设计，明确前后端及外部平台/ERP/MES对接契约；（3）负责自营/分销商城与小程序关键模块及编辑器相关能力的分析设计与实现；（4）参与质量门禁、发布协作与问题闭环；（5）推动Agent辅助开发试点，制定提示词规范、产物评审与安全红线（密钥与客户原图不进提示词）。下文围绕「Agent辅助开发技术及其应用」展开论述。

## 二、Agent辅助开发技术概述

### 2.1 内涵与能力边界

Agent 辅助开发，是指在软件工程活动中引入具备大模型推理与工具调用能力的智能代理，协助完成需求整理、代码生成、测试用例草拟、缺陷定位建议、脚本与文档起草等任务，并由人进行确认、修订与决策。它不同于传统代码补全：Agent 可在多文件上下文中理解意图、给出方案草稿，甚至调用检索、终端或仓库工具完成多步任务；但也不同于"自动交付系统"——对资金、库存、隐私与生产印刷等关键路径，最终责任仍在工程人员与质量体系。

从系统分析师视角，引入 Agent 首先要回答三个问题：它解决什么约束（人力、重复劳动、知识检索成本）？可能引入什么新风险（幻觉、泄密、错误合入）？如何嵌入现有需求—设计—实现—测试—发布闭环而不削弱控制点？只有把 Agent 定位为"加速草稿生产的协作者"，而不是"替代分析与验收的决策者"，新技术才能与高级工程师职责相匹配。

### 2.2 适用场景、协同模式与治理要点

按活动类型，常见适用场景包括：需求分析阶段的访谈纪要归纳、流程图/用例草稿；设计实现阶段的样板代码、设计模式骨架、接口说明；测试阶段的等价类边界用例、单测草稿；运维阶段的流水线片段、告警规则与排障清单。相对不适用或需严格限制的场景包括：直接修改生产配置与密钥、自动合并未评审代码、自动处理客户隐私原图、自动做出业务规则最终解释（如促销互斥、印刷可行性判定）等。

人机协同可概括为「意图澄清 → Agent 产草稿 → 人工评审修订 → 门禁验证 → 度量改进」。治理要点包括：明确白名单场景与禁区；提示词中禁止粘贴密钥、证书、客户上传原图与未脱敏订单；产物必须可追溯到需求/缺陷单；关键模块保持测试与灰度策略不变；定期复盘误导案例，更新团队规范。评价维度建议同时看效率（交付周期、草稿采用率）与质量（缺陷密度、回滚次数、安全事件），避免只报提效数字。

## 三、本项目中Agent辅助开发的选择与应用

### 3.1 总体思路

本项目质量属性优先级为：交易与资金正确、多渠订单与库存一致、高峰可服务、规则可演进。主要约束包括：团队规模有限；小程序发版受审核影响；外部平台、支付、ERP/MES等多依赖；分销与活动规则变更频繁；自研编辑器与印刷约束强。下文措施均在该约束下展开。

据此确定策略为「分场景试点、关键路径加固、度量驱动扩大」：先在文档、单测、非资金样板代码试点；支付、库存预占、印刷出血校验等核心逻辑以人工设计与测试为主，Agent 仅允许辅助查阅与解释，不得直接生成后无审合入；所有合入仍走代码评审与 CI 门禁，发布仍走灰度。

### 3.2 需求与流程文档辅助：加快对齐，不替代确认

业务流程涉及运营、客服、审图、生产等多角色，访谈材料琐碎。我们使用 Agent 将会议纪要归纳为痛点列表、As-Is/To-Be 要点与待确认问题清单，并生成跨职能流程草稿，供评审会讨论。分析师职责是核对是否遗漏驳回重提、产能限流、版权争议等例外支路，修正后再入库需求基线。该做法将文档起草时间明显压缩，同时坚持"业务签字确认前，模型输出只是草稿"，避免把幻觉写进范围说明书。对自研编辑器相关需求（图层、撤销、出血预览、导出规格），亦先由 Agent 整理验收条目初稿，再由印厂与审图同事校准印刷术语与阈值。

### 3.3 编码与设计骨架辅助：服务变化点，严控关键域

在工厂方法配置器、促销/运费策略类、订单状态类等结构稳定、重复度高的位置，允许开发人员用 Agent 生成类骨架与单测草稿，再按领域模型裁剪。对 ERP/MES 与外部平台适配层报文映射，可用 Agent 辅助生成字段对照表草稿，但必须与 ERP/MES 实施方及平台对接文档核对主数据编码、回传节点、售后状态与幂等规则后再开发；商城侧只消费约定事件，不生成车间作业指令，也不在未评审情况下自动改写分销结算规则。对图片编辑器中的命令模式（撤销重做）、组合模式（图层）等，Agent 可加速样板实现，但交互细节、性能与小程序画布差异仍由熟悉端侧的同事主导。明确规定：涉及金额计算、支付回调验签、库存/产能预占的代码，必须人工编写或逐行审计；Agent 建议仅作对照。代码评审增加检查项——是否出现无业务意图的过度生成、是否引入不明依赖、是否把提示词中的临时逻辑留在主干。

### 3.4 测试与运维辅助：草稿进库前必须过门禁

测试侧用 Agent 根据需求描述生成等价类、边界值与异常路径用例草稿，再由测试/分析人员按判定表、支付状态机与编辑器印刷约束补全，通过后方可进入回归库。运维侧允许 Agent 起草流水线步骤说明、告警规则草案与常见故障排障清单，但合并到正式流水线与告警平台前需评审；严禁在提示词中提供云密钥、数据库连接串。大促期间，Agent 可用于整理值班备忘与复盘纪要，不参与自动扩容或自动限流阈值变更——弹性策略变更仍按预案人工执行并记录。

### 3.5 风险控制、度量与效果

主要风险包括：生成代码似是而非导致隐蔽缺陷；提示词泄密；过度依赖造成设计能力退化；以及把编辑器/印刷等强领域问题交给通用模型导致"外行建议"。对应措施为：关键路径加强测与灰度；提示词与知识库脱敏规范；要求责任人对合入代码能讲清设计意图；印刷与出血相关结论必须以工艺规范或印厂确认为准。度量上跟踪：试点模块平均交付周期、Agent 草稿采纳率（经修改后合入比例）、相关模块缺陷密度与回滚次数。结果显示，文档与样板代码类任务耗时下降明显；核心交易缺陷未因引入 Agent 出现异常抬升；曾出现个别"生成用例遗漏重复支付回调"的问题，经评审制度拦截，反证了人工确认环节不可取消。总体效果是：在活动密集月份仍能保持迭代节奏，重复劳动减少，新人通过"Agent 草稿 + 规范 + 评审"更快熟悉模块结构。不足在于：团队提示词质量参差，复杂编辑器缺陷定位仍依赖经验；知识库未系统沉淀印刷与工艺约束，模型偶发外行建议。后续计划建设经审定的领域知识条目，并继续收紧禁区清单。

## 四、结束语

综上，Agent辅助开发的选择与应用必须服务业务约束与质量目标。本项目在统一的全渠道定制商城背景下完成了相关方法落地。作为系统分析师，应先澄清变化点与风险，再选型并设置评审/门禁/度量，使技术手段服从正确性与可持续交付，而不是堆砌名词。
