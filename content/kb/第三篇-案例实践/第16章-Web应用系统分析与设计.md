## 一、场景特征

**Web 应用系统（答卷·定义）**：Web 应用系统是以 Web 浏览器（或支持 Web 技术的可视化界面）为用户入口、基于 Web 技术与 W3C 标准、通过 HTTP/HTTPS 等协议向用户提供内容与服务的应用程序。

**Web 应用系统（答卷·作用）**：主要用于降低客户端安装与维护成本，实现跨平台、易访问的信息交互与业务处理；典型场景包括电子商务、企业门户、SaaS 与社交网络等。

**定义**：用户界面驻留于 Web 浏览器（或支持 Web 技术的可视化界面）的应用程序，基于 Web 技术与 W3C 标准，通过 HTTP 等协议提供内容与服务。

**典型场景**：
- 电子商务（购物车、支付、供应链集成）
- 企业门户、SaaS 服务、社交网络
- 从小规模工具到 Internet/Intranet/Extranet 大规模分布式应用

**Web 应用核心优势**（案例可列举）：
| 特征 | 说明 |
|------|------|
| 易于访问 | 任意浏览器、多设备，无需安装客户端 |
| 开发高效 | 单代码库多平台，开发周期短 |
| 使用简单 | 自动更新，用户无维护负担 |
| 扩展性强 | 按需增用户，数据多存云端 |

**新式 Web 应用特征**（与案例架构选型相关）：
1. **云托管与可扩展性**：低内存、高吞吐，容器/微服务友好
2. **跨平台**：Linux/macOS/Windows，Docker 部署
3. **自动化测试**：脚本模拟用户操作，可重复、可回归
4. **传统应用 + SPA 并存**：服务端渲染 MVC vs 客户端 SPA（Blazor WebAssembly 等）
5. **CI/CD 友好**：Azure DevOps、GitHub Actions 等持续交付

**两种构建方式**：
- **传统 Web 应用**：大部分逻辑在服务器，每次操作完整页面重载
- **SPA**：静态 HTML 初始化 + JavaScript + Web API，极少服务端页面加载

## 二、架构原则与模式

### 2.1 通用设计原则（案例「架构设计」高频）

> 助记，不当答卷正文：分离、封装、反转、显式、单一、DRY、持久性无知、有界上下文。

| 原则 | 要点 | 案例答题提示 |
|------|------|-------------|
| 分离关注点 | 业务逻辑与 UI、基础设施分离 | 分层/分模块理由 |
| 封装 | 接口稳定、实现可替换 | 松耦合、可维护 |
| 依赖关系反转 | 依赖抽象而非具体实现 | 便于测试与替换 |
| 显式依赖 | 构造函数注入所需协作对象 | 降低隐式全局依赖 |
| 单一责任 | 一个类/服务只做一件事 | 微服务拆分依据 |
| 避免自我重复 | DRY，逻辑只在一处维护 | 重构方向 |
| 持久性无知 | 业务模型不绑定 ORM/持久化技术 | POCO 设计 |
| 有界上下文 | 每个应用独立持久化，跨上下文用 API | 微服务边界 |

**分离关注点原则（答卷）**：分离关注点原则是指将业务逻辑、用户界面与基础设施等不同职责分开设计与实现；**用于**降低模块间耦合、便于独立演化与测试。

**封装原则（答卷）**：封装原则是指对外暴露稳定接口、隐藏内部实现细节；**用于**实现松耦合，使实现可替换而不影响调用方。

**依赖关系反转原则（答卷）**：依赖关系反转原则是指高层模块依赖抽象接口而非具体实现；**用于**便于单元测试、组件替换与架构扩展。

**显式依赖原则（答卷）**：显式依赖原则是指通过构造函数等方式明确声明所需协作对象；**用于**消除隐式全局依赖，提高代码可读性与可测试性。

**单一责任原则（答卷）**：单一责任原则是指一个类或一个服务只承担一项明确的职责；**用于**控制复杂度，也是微服务按业务能力拆分的依据。

**避免自我重复原则（答卷）**：避免自我重复（DRY）原则是指同一业务逻辑只在一处维护；**用于**减少重复代码带来的不一致与维护成本。

**持久性无知原则（答卷）**：持久性无知原则是指业务领域模型不绑定具体 ORM 或持久化技术；**用于**保持领域模型纯净（如 POCO），便于迁移存储方案。

**有界上下文原则（答卷）**：有界上下文原则是指每个应用或子系统拥有独立的数据持久化边界，跨上下文仅通过 API 协作；**用于**划定微服务或模块边界，避免共享数据库导致的紧耦合。

### 2.2 架构分类

| 类型 | 特点 | 适用场景 | 缺点 |
|------|------|----------|------|
| **整体式（Monolithic）** | 单一代码库，统一部署 | 简单、低流量、内部工具 | 难扩展、单点故障、小改需全量部署 |
| **微服务** | 独立服务 + RESTful API，各自数据库 | 高并发、复杂功能、预期流量增长 | 运维复杂、分布式事务一致性 |
| **无服务器（Serverless）** | 按执行付费，云托管基础设施 | 多媒体、流处理、CI 管道、IoT 消息 | 冷启动、厂商锁定 |

**整体式架构（答卷·定义）**：整体式架构是将全部功能置于单一部署单元的架构形态；**用于**业务简单、流量较低、团队规模较小的场景，以降低初期开发与运维复杂度。

**微服务架构（答卷·定义）**：微服务架构是将应用拆分为多个独立部署、通过轻量 API 协作的服务集合；**用于**高并发、功能复杂且需独立扩展与演化的 Web 应用。

**无服务器架构（答卷·定义）**：无服务器架构是由云厂商托管运行时、按函数执行量计费的架构形态；**用于**事件驱动、短时突发、无需常驻进程的任务（如流处理、CI 管道、IoT 消息）。

**选型口诀**：简单低流量 → 整体式；复杂高并发 → 微服务；事件驱动短时任务 → 无服务器。（助记，不当答卷正文）

### 2.3 架构模式

**B/S 三层**：
- 表现层：用户交互
- 逻辑层：业务处理（Web 服务器）
- 数据层：数据库（MySQL、Oracle 等）

**B/S 三层架构（答卷·定义）**：B/S 三层架构是以浏览器为客户端、将系统划分为表现层、逻辑层与数据层的 Web 应用结构；**用于**实现职责分离，便于并行开发与独立扩展各层。

**P2P**：客户端直接通信；完整连接拓扑 vs 环形拓扑；节点对等、容错好。

**MVC / MVP**：
- MVC：Model-View-Controller，视图与模型通过控制器解耦
- MVP：Presenter 承担逻辑，View 被动；比 MVC 更利于单元测试

**MVC 模式（答卷·定义）**：MVC 模式是将应用划分为模型（Model）、视图（View）与控制器（Controller）的架构模式，视图与模型通过控制器解耦；**用于**分离数据、展示与交互控制，便于 Web 页面组织与维护。

**MVP 模式（答卷·定义）**：MVP 模式是由 Presenter 承担业务逻辑、View 仅负责被动展示的架构模式；**用于**进一步解耦界面与逻辑，通常比 MVC 更利于单元测试。

**前后端分离（答卷·定义）**：前后端分离是将用户界面（前端）与业务逻辑/数据服务（后端）独立开发、通过 API 通信的架构方式；**用于**前后端并行开发、技术栈解耦，并支撑 SPA、多端（Web/小程序）复用同一后端。

**BFF（答卷·定义）**：BFF（Backend for Frontend，前端专用后端）是为特定客户端（如 Web 端、小程序端）定制的聚合 API 层，位于通用领域服务与前端之间；**用于**按端裁剪数据与接口、避免前端直接对接多个微服务，并防止多端各自拼装导致业务规则不一致。

**微服务配套机制**：
- 服务注册与发现
- 服务监控（Metrics/Logging/Trace）
- 服务容错（熔断、隔离、限流、降级、超时）

### 2.4 开发框架（案例技术选型）

| 栈 | 代表框架 | 角色 |
|----|----------|------|
| Java EE | Spring + Struts + Hibernate（SSH） | MVC + IoC + ORM |
| Java EE | JSF | 标准 Web 框架，FacesServlet |
| .NET | CLR + ADO.NET + ASP.NET | 微软全栈 |
| Web 层 | jQuery/Prototype/Ext JS/AJAX | 前端异步交互 |

**SSH 轻量架构**：浏览器 → Struts(Controller) → Spring(Business) → Hibernate(DAO) → 数据库

### 2.5 Web + AI 智能体 · 后端架构四维度选型（2026 案例）

> 详解与负载均衡/中间件要点 → `速查/Web与AI智能体-架构选型四维度卡.md`

**场景**：Web 平台提供对话、任务执行、**多智能体协同**、知识库检索、API 调用；需 **高并发、低延迟、安全、高可用** 与 Agent **动态扩缩容**。

**案例常比两种栈**：**微服务（Spring Cloud）** vs **轻量快速（FastAPI + Node.js）**。按下列四维度 **分别填各自特点**（勿混为一谈）：

| 维度 | 轻量快速栈 | 微服务栈 |
|------|------------|----------|
| **并发适配 / 实时性** | 开发快、轻量高效；**高并发稳定性较弱** | 治理组件全，更适合 sustained 高并发 |
| **智能体调度** | 多 Agent 调度/协同多需自建 | **分布式调度、多 Agent 协同、动态扩缩容**（注册发现 + K8s） |
| **安全与权限** | 基础安全具备；**企业级风控需额外开发** | 网关 + Security 生态，细粒度 RBAC/审计 |
| **扩展性与分布式** | 适合中小规模、快速验证 | **服务拆分、弹性扩缩**，适合大型分布式平台 |

**AI 智能体（答卷·定义）**：智能体是感知环境、**自主决策并执行动作** 的计算实体；大模型时代还可 **规划任务、调用工具/API**（非仅对话）。

**Agent 平台关键中间件（列举题）**：Nginx/网关、Redis、Kafka/RabbitMQ、Nacos、Elasticsearch、Sentinel、**Kubernetes**（容器化调度 Agent）。

## 三、开发与测试要点

### 3.1 通信协议

| 协议 | 用途 |
|------|------|
| HTTP/HTTPS | 基本 Web 通信，无状态；Session 跟踪用 Cookie/URL 重写 |
| RTP/RTSP | 音视频流媒体 |
| SMTP/POP3 | 邮件收发 |

**HTTP 无状态（答卷·定义）**：HTTP 是无连接、无状态的请求-响应协议，服务器默认不保留客户端历史请求上下文；**用于**简化服务器设计，但跨请求的用户状态须借助 Session/Cookie 等机制维护。

**Session（答卷·定义）**：Session 是服务器端为识别同一用户会话而维护的状态存储机制，通常通过 Session ID（常存于 Cookie）关联；**用于**在无状态 HTTP 之上跟踪登录态、购物车等跨请求业务状态。

### 3.2 数据存储与性能

**缓存四级模型**：
1. 应用服务器缓存（单节点内存）
2. 全局缓存
3. 分布式缓存（一致性哈希）
4. CDN（静态内容，如 CloudFront）

**Web 缓存（答卷·定义）**：Web 缓存是将热点数据或静态资源暂存于离用户更近的存储层（内存、分布式缓存或 CDN）的技术；**用于**降低数据库与源站压力、缩短响应时延，是 Web 性能优化的高频手段。

**CDN（答卷·定义）**：CDN（内容分发网络）是将静态资源（图片、CSS、JS 等）缓存至边缘节点的分布式网络；**用于**就近交付内容，减轻源站带宽压力并提升全球/广域用户访问速度。

**性能三板斧**：负载均衡、数据库连接池、高速缓存

**负载均衡类型**：
- TCP/IP 级 / 基于 DNS
- 应用级 / 基于应用负载

**负载均衡（答卷·定义）**：负载均衡是将 incoming 请求分发到多台服务器或实例的机制；**用于**提升系统吞吐与可用性，避免单点过载。

### 3.3 部署要点

- 管理客户对增量的期望
- 安装与测试交付包
- 交付前建立支持制度
- 先修正缺陷再交付
- 版本控制与内容管理（变更跟踪、快速重建、回滚）

### 3.4 Web 测试特点

1. 用户量大，需跨平台全局访问与并发事务处理
2. 超文本链接关系须人工校验
3. 多层架构，需综合分析各层结果
4. 集成 Web 服务器、DB、中间件、第三方组件
5. 浏览器导航（back/forward/refresh）影响状态
6. 技术种类多，测试模型粒度难定义
7. 分布式、动态、多平台、交互、超文本

**测试过程**：需求分析 → 定义策略 → 确定环境/用例/工具 → 描述细节（用例、进度、错误等级）

**功能测试要点**：表单标识与强制域、输入校验、异常处理、默认项、浏览器后退不破坏数据

**性能测试**：超正常点击率（如 500/s vs 100/s）、递增数据输入率、最大资源用例、极限/崩溃用例

**可靠性测试**：确认需求实现、数据准确性、找出高影响错误

**安全测试**：事务日志、CPU 占用、异常进程、失败注册记录、盗卡使用、事务完成保存

**Web 服务测试**：WSDL、SOAP/REST 接口、互操作性

**Web 鉴权（答卷·定义）**：Web 鉴权是对用户身份进行认证并依据权限控制资源访问的机制（如 Session/Cookie、OAuth2、JWT）；**用于**保障 Web 应用安全，防止未授权访问与越权操作。

## 五、易混对比

| 对比 | 区别（答卷短句） |
|------|------------------|
| **MVC vs MVP** | MVC 由 Controller 协调 View 与 Model；MVP 由 Presenter 承担逻辑、View 被动，通常更利于单元测试。 |
| **传统 Web vs SPA** | 传统 Web 每次操作多完整页面重载、逻辑主要在服务端；SPA 初始化后由 JavaScript 调用 API、极少整页刷新，交互更流畅。 |
| **整体式 vs 微服务 vs 无服务器** | 整体式单库单部署，适合简单低流量；微服务多服务独立部署，适合高并发复杂业务；无服务器按执行付费、无常驻进程，适合事件驱动短时任务。 |
| **前后端分离 vs BFF** | 前后端分离指前后端独立开发与 API 通信；BFF 是在此基础上为特定客户端再设一层聚合 API，避免前端直连多个后端服务。 |
| **Session vs Cookie** | Session 状态存于服务器、通过 Session ID 关联；Cookie 是浏览器端存储的小段数据，常用来携带 Session ID 或偏好设置。 |
| **应用缓存 vs CDN** | 应用/分布式缓存用于动态或半动态热点数据；CDN 主要用于静态资源就近分发，减轻源站带宽压力。 |

## 六、应试钩子

**案例可能怎么问**
- 「请说明 Web 应用架构设计应遵循的核心原则（至少 2 个）」→ 直接誊写 §2.1 八大原则答卷句。
- 「对比 MVC 与 MVP / 传统 Web 与 SPA / 整体式与微服务」→ 用 §五 易混对比表展开。
- 「如何提升 Web 应用性能？」→ 负载均衡 + 连接池 + 缓存（含 CDN）三板斧，各写定义+作用。
- 「多端（Web/小程序）如何统一业务规则？」→ 前后端分离 + BFF 或统一领域服务，避免双端两套逻辑。
- 「对比两种 Web 后端架构（并发、Agent 调度、安全、扩展）」→ 用 §2.5 四维度表 + `Web与AI智能体-架构选型四维度卡`。
- 「Agent 场景负载均衡 / 常用中间件」→ 七层 vs 四层 vs 网关；Redis/MQ/Nacos/K8s 按类别列举。

**论文怎么用**
- 背景：电商/门户/ SaaS 的 Web 化改造；痛点为扩展性、维护成本或多端不一致。
- 方案：B/S 三层 + MVC/前后端分离；性能侧写缓存/CDN/负载均衡；安全侧写 Session/OAuth2。
- 成效：可用性、响应时延、发布效率、运维成本等可量化指标。
