# 案例133 · 微服务 · 技术方案论证

> track: P0 · depth: deep · batch: tracks-v1

## 题干

某出行平台（网约车 + 顺风车）现有系统为一个大单体：用户、订单、派单、计价、支付、评价全部耦合在一个部署单元里，数据库为共享单库。近一年问题频发：
1. 早晚高峰派单模块成为瓶颈，但每次扩容都要带着整个单体一起扩，评价模块改一行代码也要全量回归、全站发布；
2. 派单高峰期任何一个小模块的故障（如评价服务慢查询）都会拖垮整个进程；
3. 出故障后排查困难：一次"下单慢"要横跨 8 个模块翻各自散落的日志；
4. 历史上曾按技术层拆过一次（前端服务/逻辑服务/数据库服务），结果每次改动仍要三方联动发布，失败告终。
团队现倾向于按业务重新拆分微服务，并引入注册中心与网关。

## 问题

**问题1** 针对（1）（4），说明从单体演进到微服务的判据与正确路径，指出历史拆法的问题；并对比微服务与传统 SOA 的本质区别，说明内部高性能调用与跨服务旁路通知分别适合的通信方式。

**问题2** 针对引入的注册中心，说明其核心机制（注册、发现、健康检查）与两种发现模式的区别；针对（3），给出让"一次下单慢在哪一环"可被分钟级定位的观测手段三支柱。

**问题3** 针对（2），给出高峰期保护系统的四个手段并各配一句职责（含断路器三态）；说明"改限流阈值不重启"依赖的基础设施与容器编排的三大能力；针对共享单库，说明微服务下的数据管理原则，并为"下单-扣减优惠券-记账"跨服务链路设计合适的一致性方案并说明失败时如何处理。

## 参考作答要点（非唯一答案）

**问题1要点：** 演进判据：模块耦合发布互相拖累、局部热点需独立扩展、团队并行受限；路径：先模块化单体解耦，再按业务边界（限界上下文）拆分，粒度以一个小团队可独立开发部署运维为准，反对一步到位。历史按技术层拆 = 分布式单体，未解除业务耦合。SOA：ESB 集中智能总线、大粒度服务；微服务：去中心化、轻量通信（REST/消息）、每服务一库。内部高性能调用选 gRPC（二进制、多路复用）；旁路通知选消息队列异步（解耦削峰，消费幂等）。

**问题2要点：** 注册中心：服务启动注册元数据 → 消费者查询实例列表 → 心跳健康检查自动剔除故障实例。客户端发现：消费者拉取列表自行负载均衡；服务端发现：中间负载均衡器代选。观测三支柱：日志（集中聚合检索）、指标（时序监控告警）、链路追踪（全局 TraceId 贯穿跨服务调用链，定位慢点与故障环）。

**问题3要点：** 四保护：限流（入口过载，令牌桶允许突发）、熔断（依赖故障快速失败，断路器关闭→打开→半开试探）、降级（保核心弃边缘返回兜底）、灰度（按比例放量可秒回滚）。不重启改阈值：配置中心动态下发；容器编排三大能力：滚动更新、自愈、弹性伸缩。数据管理：每服务一库，跨服务只走 API/事件，禁直连他库，必要字段冗余 + 事件最终同步。跨服务一致性：业务允许秒级不一致 → Saga（本地事务序列 + 失败逐环补偿）或消息最终一致（本地消息表 + 重试 + 幂等）；失败时执行补偿事务逆向回滚（如恢复优惠券额度、冲正记账）。

**领域提示：** 微服务 · D3 主背域；按"发布拖累/故障级联/排障难"对号判据，四保护各管一摊，收尾回扣题干。
