# 案例136 · Web · 连锁健身房会员小程序

> track: P0 · depth: deep · batch: tracks-v2

## 题干

某连锁健身房企业（30 家门店，会员 20 万）拟建设"会员服务小程序"，提供在线购卡约课、门店店内大屏显示约课情况、会员积分兑换商城等功能。技术团队现状如下：
1. 后台原有一套 PHP 单体系统，前端页面由后端模板直接渲染，每次改一个按钮都要整个系统重新发版；新团队希望前端独立开发、后端只提供数据接口；
2. 约课接口大促期间出现"先查缓存没有、大量请求直打数据库"导致数据库 CPU 打满；运营又反馈"每周一早 8 点开放团体课预约，瞬时流量是平日 50 倍"；
3. 会员登录态目前存在单台服务器的 Session 中，扩容后经常出现"刚登录又提示未登录"；
4. 小程序积分商城上线后，安全团队在会员昵称处发现可以注入脚本弹窗，同时担心第三方页面伪造会员请求兑换积分；
5. 架构组讨论：接口是直接暴露给小程序，还是加一层统一入口；门店间"约课成功后同步扣库存"目前用服务间同步 HTTP 调用，高峰期经常因一个门店服务慢拖垮整体。

## 问题

**问题1** 针对（1）说明前后端分离的架构方式与收益，并指出该场景下视图与模型不直接对话、视图通过展示器（Presenter）中转的模式属于 MVC/MVP/MVVM 中的哪一种；针对（2）指出约课接口遭遇的是缓存哪一类典型问题及对策；说明每周一早 8 点的瞬时洪峰应通过负载均衡的哪个层次与何种策略吸收。

**问题2** 小程序后端计划采用 REST 风格 API。请给出 REST 的五条核心约束，并针对（3）说明 Session 方案在扩容场景下的问题与 JWT 方案如何解决；针对（4）分别指出昵称注入脚本属于哪类攻击及服务端防护措施，第三方页面伪造请求属于哪类攻击及防护措施。

**问题3** 针对（5）说明 API 网关应承担的职责与一种限流算法；比较"同步 RPC"与"异步消息队列"两种服务间通信方式的特点，说明"约课成功后扣库存"改用异步消息（事务消息）的好处；最后指出该单体系统演进到微服务的判断信号，以及拆分应遵循的原则与粒度标准。

## 参考作答要点（非唯一答案）

**问题1要点：** 前后端分离：后端只输出数据 API（JSON），前端独立负责渲染与交互；收益：前后端并行开发、独立发布，接口复用（小程序/大屏/管理端共用），职责清晰。视图不直接对话、经 Presenter 中转 → MVP（Presentation 模式，V 与 M 完全解耦，逻辑进 P）。缓存问题：缓存穿透（查不存在的数据绕过缓存直打 DB）→ 布隆过滤器/空值缓存。洪峰吸收：反向代理层（Nginx）做负载均衡入口；策略用加权最少连接或轮询 + 弹性扩容，结合应用服务层水平扩展分流瞬时流量。

**问题2要点：** REST 五约束：①资源由 URI 唯一标识；②统一接口（GET/POST/PUT/DELETE 表达语义）；③无状态（请求自包含全部上下文）；④分层系统；⑤可缓存。Session 问题：状态存服务端，扩容后请求落到不同机器导致登录态丢失，需粘滞会话或集中存储（Redis）；JWT：自包含签名令牌，服务端无状态，任意节点验签即可，天然适合水平扩展。昵称注入脚本 → XSS（跨站脚本），防护：输出转义/编码、CSP 内容安全策略、HttpOnly Cookie；第三方伪造请求 → CSRF（跨站请求伪造），防护：CSRF Token、SameSite Cookie、校验 Referer/Origin。

**问题3要点：** API 网关职责：路由转发、统一鉴权、限流熔断入口、响应聚合、日志与监控；限流算法可用令牌桶（允许突发流量平滑通过）或计数器窗口。同步 RPC：实时、强一致，但耦合高、故障级联（一个门店服务慢拖垮整体即其典型问题）；异步消息队列：削峰填谷、解耦、故障隔离，"约课成功扣库存"改为本地事务 + 事务消息（最终一致），高峰期消息堆积消化而不压垮库存服务。演进信号：模块耦合导致发布互相拖累（改按钮全系统发版）、局部热点需要独立伸缩（约课洪峰）、团队规模扩大需并行交付。拆分原则：按业务能力/限界上下文拆（不按技术层拆）、数据库随服务走；粒度标准：一个小团队能独立负责一个服务的设计、开发、部署与运维。

**领域提示：** Web · 架构风格辨析为主；缓存三问题、Session/JWT、XSS/CSRF 必须成对记忆，答完回到"30 门店/20 万会员/周一洪峰"场景收口。
