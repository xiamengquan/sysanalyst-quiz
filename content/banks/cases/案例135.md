# 案例135 · 需求 · 智慧社区养老服务台

> track: P0 · depth: deep · batch: tracks-v2

## 题干

某养老服务企业拟在全市 40 个社区建设"智慧养老服务平台"，整合社区食堂订餐、上门照护预约、健康档案查询、紧急呼叫等业务。企业总经理提出："让老人用手机一键叫服务、让子女远程看得见父母的照护记录，两年内覆盖全市 40 个社区。"

项目组前期工作情况如下：
1. 上门照护的老人多数不使用智能手机，只能口头描述"想要个方便的呼叫办法"，说不清具体操作流程与界面形态；
2. 服务涉及食堂承包商、护理站、社区居委会、医院四类机构，各方对"服务响应时限""费用结算口径"分歧很大；
3. 照护员每天纸质工单流转，实际派单流程与企业制度文件描述不一致；
4. 需求分析员已把首轮收集整理成 260 条需求清单，其中一条写着"平台应安全可靠、老人用起来没有障碍"；
5. 需求评审通过形成基线后，护理站站长又口头提出"希望给失能老人加一个跌倒自动报警"，开发人员认为改动不大，准备直接排进下个迭代。

## 问题

**问题1** 针对（1）～（3）三种调研情形，分别指出最合适的需求获取方法并说明理由；结合本案例说明需求包含哪几个层次，并指出总经理提出的目标属于哪一层。

**问题2** 分析组就"用 DFD 建模还是用用例建模"产生分歧。请分别说明两种方法的核心模型与适用场景；并指出"提交订餐后必然生成结算单"与"老人按下紧急呼叫才触发的报警流程"在用例建模中分别应表示为哪种关系，画出（或文字描述）二者与基本用例的关系图。

**问题3** 针对（4）中"安全可靠、老人用起来没有障碍"这条需求，指出其存在的问题并给出改进写法；针对（5）的口头加需求，说明正确的需求变更处理流程，并说明需求跟踪矩阵在其中如何支撑影响范围评估；最后指出需求状态在跟踪矩阵中从"建议"到"完成"的流转过程。

## 参考作答要点（非唯一答案）

**问题1要点：** （1）老人说不清操作流程 → 原型法（把设想做成可操作原型，边看边确认，迭代澄清）；（2）四类机构对响应时限、结算口径分歧大 → 联合需求计划 JRP（workshop 式多方高效达成共识）+ 关键干系人访谈深挖；（3）实际派单流程与制度文件脱节 → 现场观察（到派单现场拿一手真实流程）。需求三层：业务需求（组织目标，为什么做）→ 用户需求（用户要完成的任务）→ 系统需求（功能 + 非功能）；"两年覆盖 40 个社区、子女远程可看照护记录"是业务需求层。

**问题2要点：** DFD：结构化分析方法，核心是数据流图（外部实体/加工/数据存储/数据流）+ 数据字典，面向数据加工与流转，适合刻画订餐、结算这类业务数据流转过程；用例建模：面向对象方法，核心是参与者 + 用例（辅以 include/extend 关系），面向交互与目标，适合交互式系统与迭代开发。必然执行的子流程"生成结算单"是 include（包含）关系；有条件触发的可选扩展"跌倒报警流程"是 extend（扩展）关系。关系描述：基本用例「提交订餐」--<<include>>-->「生成结算单」；扩展用例「紧急报警」--<<extend>>--> 基本用例「紧急呼叫」（扩展指向被扩展的基本用例）。

**问题3要点：** 问题："安全可靠、没有障碍"无量化标准，不可验证、有二义性（违反可验证性与无二义性）。改进写法："紧急呼叫端到端响应不超过 5 秒、呼叫成功率 ≥99.9%；70 岁以上用户在 3 次引导内独立完成一次订餐（可用性测试通过率 ≥90%）；敏感健康数据传输与存储符合等保三级要求"。变更流程：护理站站长提交书面变更申请 → CCB（变更控制委员会）评估对成本/进度/质量/风险的影响 → 决定批准或拒绝 → 批准后更新需求基线并纳入配置管理 → 通知全部干系人；开发人员不得绕过 CCB 直接排期。跟踪矩阵支撑：正向跟踪沿"需求→设计→代码→测试用例"查出跌倒报警会波及哪些模块与用例，反向跟踪查受影响的设计文档与已有测试，评估工作量与风险。需求状态流转：建议 →（CCB 批准）→ 批准/基线 → 实现 → 验证 → 完成（或拒绝/延期），每步在跟踪矩阵中登记状态与版本，基线化后任何修改必须走变更控制。

**领域提示：** 需求 · 试题一必答域；获取方法按"说不清/有分歧/流程脱节"对号入座，include 必然执行、extend 条件触发，变更必走 CCB，答完回扣题干场景。
