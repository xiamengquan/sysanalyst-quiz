# 案例132 · Web · 技术方案论证

> track: P0 · depth: deep · batch: tracks-v1

## 题干

某连锁茶饮品牌计划升级线上点单系统，目标形态：小程序 + App 双端点单、会员积分、门店库存联动。当前系统为服务端模板渲染的单体应用，前后端耦合在同一发布流程中。

约束与背景：
1. 新版要求 Web 管理后台、小程序、App 三端复用同一套业务能力，前端团队与后端团队分属两个部门，需要并行开发；
2. 大促（新品首发）峰值 QPS 达日常 30 倍，历史大促中出现过：某爆款商品缓存键过期瞬间数据库被打垮、恶意请求查询不存在的商品编号绕过缓存、整批缓存同时失效三种故障；
3. 安全侧曾发生过：攻击者在评论区注入脚本；会员被诱导点击外站链接后以登录态发起了非本人操作的积分划转；
4. 运维侧要求：网关统一接入，改限流阈值不能重启服务；发布出新功能要能小比例放量、出问题秒级回滚。

## 问题

**问题1** 针对（1），论证是否应采用前后端分离，说明收益与代价及缓解措施；并为富交互的管理后台选择一种前端架构模式，说明其核心机制与另外两种常见模式的区别。

**问题2** 针对（2），逐一识别三种缓存故障的名称与对策；说明网关在峰值场景下应承担哪些职责，以及在"下单成功后加积分、发短信、记日志"上应选同步还是异步并说明理由。

**问题3** 针对（3）（4），分别指出两类安全攻击的名称与防护手段；给出入口层与数据层的负载均衡/扩展手段；说明发布期"小比例放量、秒级回滚"对应的机制，以及"改阈值不重启"依赖的基础设施。

## 参考作答要点（非唯一答案）

**问题1要点：** 前后端分离：后端只出数据 API（JSON），前端独立渲染。收益：多端复用同一 API、前后端并行演进、独立发布；代价：首屏与 SEO 变弱、接口契约管理成本。缓解：SSR 服务端渲染救首屏。管理后台选 MVVM：ViewModel 通过双向绑定（观察者）自动同步视图与数据；MVC 视图可直接读模型；MVP 由 Presenter 手动中介、视图与模型隔离——判据是视图与模型是否直接对话。

**问题2要点：** 爆款键过期瞬间 = 缓存击穿 → 互斥重建/逻辑过期/热点永不过期；查不存在的数据 = 缓存穿透 → 布隆过滤器/空值缓存；整批同时失效 = 缓存雪崩 → TTL 加随机错峰/多级缓存/缓存集群高可用。网关职责：路由、统一鉴权、限流（令牌桶支持突发）、聚合、监控日志（业务逻辑不下放网关）。加积分/短信/日志走异步消息队列：解耦 + 削峰，主链路只做核心交易，消费端保证幂等，最终一致。

**问题3要点：** 注入脚本 = XSS → 输出转义、CSP、HttpOnly Cookie；诱导点击以登录态发请求 = CSRF → CSRF Token、SameSite Cookie、校验 Referer。入口：DNS 地理分流 + Nginx 反向代理负载均衡（会话粘滞用源哈希，或改用无状态 JWT 服务端不存会话）；数据层：读写分离。小比例放量、秒级回滚 = 灰度发布（配合熔断/降级保核心）；改阈值不重启 = 配置中心动态下发。

**领域提示：** Web · 第一大选做域；三种缓存故障按"单个热点/不存在/一大片"对号，安全按"注入脚本/借身份"分辨，收尾回扣题干。
