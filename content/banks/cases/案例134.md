# 案例134 · 数据库 · 建模与设计

> track: P0 · depth: deep · batch: tracks-v1

## 题干

某三甲医院拟建设互联网诊疗平台，核心业务：患者在线预约挂号、视频问诊、医生在线开处方、药品配送。项目组完成首轮概念设计，摘录关键内容如下：
1. 概念模型中：患者与医生之间是多对多的"问诊"联系（带诊断结论与时间属性）；一个科室聘用多名医生（1:N）；每个患者拥有唯一的健康档案；
2. 设计的"问诊记录"关系模式为：问诊（患者编号、医生编号、患者姓名、医生姓名、科室名、诊断结论、药品清单）；函数依赖：患者编号→患者姓名、医生编号→医生姓名与科室名、（患者编号、医生编号）→诊断结论；药品清单是逗号分隔的多个药品名；
3. 为提速，团队考虑在"预约"表中冗余保存"就诊时的医生姓名与挂号费快照"，并统一开放若干视图给报表系统；为分散读压力准备引入读写分离，一名成员担心"支付扣费成功后立即查余额"可能读到旧值；
4. 远期规划接入区域医疗云：本院与医保结算系统之间需要跨库事务（结算与记账），订单类数据量预计三年过亿，团队在讨论直接按行哈希拆表、还是先按业务垂直拆库。

## 问题

**问题1** 针对（1），给出各联系转化为关系模式的正确做法（含"问诊"联系的转化并说明理由）；针对（2），判定该关系最高满足第几范式并给出规范化路径；针对（3）中的冗余设计，说明其名称、合理性与需要付出的代价。

**问题2** 针对（2）中"药品清单"属性，判定其违反的范式并给出改进；说明视图在其中的作用与数据库中实际存储的内容，以及索引加速查询的原理与代价；针对"支付扣费成功后立即查余额"的担心，说明读写分离下的问题名称与对策，并给出并发场景下三种读问题的判据。

**问题3** 针对（4）跨库事务，比较 2PC 与基于消息最终一致的适用场景并说明 2PC 的缺陷，为"医保结算（资金强一致）"与"药品配送通知（允许秒级延迟）"分别选型；结合 CAP 说明注册类中间件常见的取舍；给出数据量增长时"先垂直后水平"的拆分路径与分片键选择原则。

## 参考作答要点（非唯一答案）

**问题1要点：** 患者一健康档案 1:1 → 并入任意一端；科室—医生 1:N → 外键并入 N 端（医生表加科室号）；患者—医生 M:N 问诊 → 必须单独建立问诊关系模式（患者编号+医生编号为主码 + 诊断结论、时间），多对多无法塞进任一端。判定：药品清单非原子违反 1NF；患者编号→患者姓名（对联合码部分依赖）不满足 2NF。规范化：先拆出患者表、医生表（消除部分依赖，达到 2NF），再消除医生编号→科室名的传递依赖（医生表拆出科室信息或医生表存科室号，达到 3NF）。冗余设计：反范式（快照式冗余），合理性：免 JOIN、定格历史事实、读多写少；代价：冗余数据一致性维护（快照不变则天然规避）。

**问题2要点：** 药品清单 = 重复组/非原子属性，违反 1NF → 拆出"处方明细"子表（问诊号+药品编号+数量）。视图：简化报表查询、行列权限（安全）、逻辑独立性；数据库只存视图的定义不存数据。索引：B+ 树有序 → 等值/范围查询快；代价：写入放大（每索引一棵树要维护）+ 空间；联合索引最左前缀。读写分离问题：复制延迟 → 支付后立即查余额应强制读主库。三读问题判据：读到未提交=脏读；同一行值改变=不可重复读；行数增减=幻读；隔离级别：读未提交＜读已提交＜可重复读（MySQL 默认）＜串行化。

**问题3要点：** 2PC：准备（投票）+提交两阶段，强一致；缺陷：同步阻塞、协调者单点、资源锁定时间长。选型：医保结算（资金强一致）→ 2PC 或 TCC（Try 预留/Confirm 提交/Cancel 释放，应用层两阶段不锁库）；配送通知（允许秒级延迟）→ 消息队列最终一致（本地消息表 + 重试 + 幂等）。CAP：分区容错 P 为网络必然，实际在 C 与 A 间权衡；注册类中间件常用 AP（可用优先，略旧无害）。拆分路径：先垂直按业务拆库（诊疗/结算/物流），数据量单表过大再水平按行分片；分片键：选查询最高频且分布均匀的列（如患者编号哈希，同一患者数据落单片），并接受跨片 JOIN/跨片事务与全局唯一 ID 的代价。

**领域提示：** 数据库 · 第二主力选做域；联系转化先判 1:1/1:N/M:N，范式按"非原子→部分→传递"三步判，收尾回扣题干。
